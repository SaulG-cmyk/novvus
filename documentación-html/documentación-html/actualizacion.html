Actualización y releases

Nivel básico

Cómo subir de versión sin perder nada: la demo local con install.py, una instalación de cliente con sudo novvus update, un despliegue manual con docker-compose.prod.yml, y —para quien construye módulos— cómo publica un release el equipo y cómo se actualiza un módulo propio.

Primero: ¿qué tipo de instalación tienes?

En Instalación viste que hay tres formas de tener NOVVUS CORE corriendo. Cada una se actualiza distinto, y confundirlas es el error más común. Identifica la tuya antes de seguir:

InstalaciónCómo la reconocesComando de actualización
Demo local Clonaste el repo y corriste python install.py. La web abre en localhost:3000 y entras con demo@novvus.dev. python install.py update
Cliente (CLI) Un servidor Linux con /opt/novvus/novvus.json, instalado con sudo novvus install. La web escucha en :8077. sudo novvus update
Manual (compose) Copiaste docker-compose.prod.yml y un .env a mano a /opt/novvus, sin CLI. Editar NOVVUS_VERSION + docker compose pull + up -d
Dos comandos llamados novvus. El CLI administrativo (Rust, en el servidor del cliente) tiene install, update, status y version. El CLI del SDK (Python, en tu máquina de desarrollo) tiene new-module, deploy, run, makemigration y seed. Nunca conviven en un servidor. En esta página, cuando digamos sudo novvus update hablamos del primero.

1. Actualizar la demo local

La demo se construye desde el código fuente del repositorio, así que actualizar significa traer el código nuevo y reconstruir las imágenes:

cd Novvus-Core
python install.py update

Por dentro hace exactamente dos cosas: git pull --ff-only (solo si el directorio es un repo Git) y docker compose -f docker-compose.full.yml up -d --build --wait. Eso reconstruye las imágenes que cambiaron, reinicia los servicios y espera a que reporten salud.

  • Tus datos se conservan. Los volúmenes novvus_full_pgdata (base de datos) y novvus_tokens (tokens de servicio de los módulos) no se tocan.
  • El servicio bootstrap vuelve a correr al arrancar: es idempotente, re-registra los módulos y aplica las migraciones pendientes que traiga la versión nueva.
  • El kernel aplica sus propias migraciones al arrancar (van embebidas en el binario).
  • No hay backup automático ni rollback. Si es una demo de verdad, no importa; si alguien la usa como QA compartido, respalda antes (ver Mantenimiento).
No confundas update con reset. python install.py reset borra contenedores, imágenes locales y volúmenes; pide que escribas BORRAR para confirmar. Es la única operación de install.py que destruye datos.

2. Actualizar una instalación de cliente: sudo novvus update

Aquí está el trabajo serio. Una instalación hecha con el CLI se actualiza con un solo comando que hace backup, aplica, verifica y —si algo falla— vuelve solo al estado anterior. Lo único que necesitas es ser root y tener red hacia downloads.novvus.dev y ghcr.io.

# A la última versión publicada
sudo novvus update

# A una versión concreta (SemVer numérico; los downgrades se rechazan)
sudo novvus update 0.1.6

# Sin pregunta de confirmación (automatización)
sudo novvus update --yes

Si ya estás en la última versión responde Novvus Core is already up to date. y termina. Si no, esto es lo que pasa, paso a paso:

1
El CLI viejo delega en el CLI nuevo. El binario instalado solo resuelve la versión objetivo (downloads.novvus.dev/latest o la que pediste), descarga el CLI de esa versión, verifica su SHA-256 contra el manifest.json del release y lo re-ejecuta. La regla es: la versión X es la única que sabe desplegar la versión X; un CLI viejo nunca aplica una plantilla vieja a un despliegue que no conoce. Desde aquí toma un lock en /opt/novvus/.update/lock: dos update simultáneos son imposibles.
2
Preflight. El CLI nuevo comprueba que la instalación actual está sana (los 6 servicios healthy, con hasta 60 s de espera), que existen docker-compose.yml y .env, que el release existe para tu arquitectura y que hay espacio en disco. Si la instalación no está sana se detiene: arregla primero, actualiza después.
3
Descarga de imágenes sin tocar lo vivo. Escribe el compose y el .env nuevos en /opt/novvus/.update/ (docker-compose.next.yml, .env.next) y hace docker compose pull contra esos archivos de staging mientras la versión actual sigue sirviendo. Si un pull falla: Update aborted. Current installation was not modified. y no hay nada que revertir.
4
Backup obligatorio. Se crea /opt/novvus/backups/<fecha>-<desde>-to-<hasta>/ (directorio 0700, archivos 0600) con: postgres.dump (pg_dump -Fc, tomado con la versión actual aún sirviendo y verificado con pg_restore --list), roles.sql (pg_dumpall --roles-only), files.tar.gz (volumen de adjuntos), tokens.tar.gz (tokens de servicio), .env, el compose en uso, novvus.json y un backup.json con el SHA-256 de cada pieza. Nunca se borran solos: tú decides cuándo limpiarlos.
5
Migración del .env, línea a línea. No se regenera: se preserva cada línea existente (comentarios incluidos), solo se reescribe NOVVUS_VERSION y se añaden las claves que falten con su default (NOVVUS_BOOTSTRAP_TOKEN se genera si no existe —llegó en 0.1.3—, NOVVUS_WEB_PORT=8077, NOVVUS_LOG_LEVEL=info, POSTGRES_USER/POSTGRES_DB). Un secreto que ya existe jamás se regenera: tus sesiones, tus firmas internas y tu base siguen siendo válidas.
6
Swap atómico y arranque. Los archivos de staging reemplazan a los reales por rename (si había un docker-compose.prod.yml manual se conserva como .pre-update) y se hace docker compose up -d --remove-orphans. El kernel aplica sus migraciones al arrancar; bootstrap re-registra los módulos y aplica sus migraciones pendientes vía POST /api/core/modules/{id}/migrate, y falla ruidosamente si alguna no pasa.
7
Verificación. Espera hasta 420 s a que los 6 servicios estén healthy (bootstrap cuenta como listo cuando termina con exit 0) y comprueba que /health del kernel reporta "version": "<objetivo>". Solo entonces novvus.json avanza a la versión nueva y el binario /usr/local/bin/novvus se reemplaza por rename atómico. Si Core falla, el CLI no cambia.
8
Rollback automático si algo falla después del backup: baja el stack, restaura compose y .env, restaura la base completa desde el dump (DROP + CREATE + pg_restore), restaura volúmenes si cambiaron y levanta la versión anterior verificando su salud. Verás Update failed. Novvus Core was restored to 0.1.5. con la ruta del backup y del log.

Códigos de salida y qué hacer con cada uno

Exit codeSignificadoQué haces
0Actualización correcta (o ya estabas al día).Nada. Abre la web y verifica con novvus status.
1Falló, pero el rollback dejó la versión anterior sana. También es 1 si el preflight rechazó (instalación no sana, downgrade, sin root).Lee /opt/novvus/logs/update-*.log, corrige la causa y vuelve a correr sudo novvus update.
2CRITICAL: automatic rollback failed. La instalación puede estar en estado intermedio.Ver abajo: no reintentes a ciegas.

Si sale 2 (rollback fallido)

  1. No repitas update todavía. Corre novvus status: mostrará un aviso WARNING: an update 0.1.5 → 0.1.6 was interrupted during '<fase>' con la ruta del backup, y la tabla de servicios te dirá cuál no levanta.
  2. Abre el log /opt/novvus/logs/update-*.log (no contiene secretos): registra cada fase, la salida de los servicios que no estuvieron healthy y el error del rollback.
  3. Con el backup en /opt/novvus/backups/… tienes todo para restaurar a mano: .env y compose de la versión anterior, postgres.dump para pg_restore, y los volúmenes en .tar.gz. El procedimiento manual está en Mantenimiento → Restaurar.
  4. Cuando la instalación vuelva a estar sana, borra el marcador de actualización interrumpida (el propio mensaje de update te dice qué archivo bajo /opt/novvus/.update/ quitar) y podrás actualizar de nuevo.
Un Ctrl + C o un reinicio a mitad del proceso dejan ese mismo marcador. novvus status y el siguiente update lo muestran con la ruta del backup para que nunca te quedes sin saber en qué fase se cortó.

Transición única desde 0.1.4

El CLI 0.1.4 no tenía update. Si tu servidor está en esa versión, una sola vez reinstala el CLI y luego actualiza; a partir de ahí el ciclo es solo novvus update:

curl -fsSL https://install.novvus.dev/install.sh | bash
sudo novvus update

3. Actualizar un despliegue manual (compose)

Si instalaste sin CLI copiando docker-compose.prod.yml, no tienes backup ni rollback automáticos: eres tú quien los hace. La secuencia recomendada es:

1
Respalda base de datos y volumen files (ver Mantenimiento). Como mínimo: 
cd /opt/novvus
docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" > backup-$(date +%F).dump
2
Cambia la versión en .env. Producción siempre fija X.Y.Z, nunca latest; las imágenes X.Y.Z son inmutables (nunca se re-publica una versión existente): 
NOVVUS_VERSION=0.1.6
Revisa también .env.prod.example de la versión nueva por si añadió variables obligatorias: el compose se niega a arrancar si falta alguna.
3
Descarga y levanta. Primero el pull (si falla, no has tocado nada) y después el arranque con espera de salud: 
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d --wait
docker compose -f docker-compose.prod.yml ps
Todos los servicios deben quedar healthy y bootstrap en Exited (0). Confirma qué imágenes corren con docker compose -f docker-compose.prod.yml images (la columna de tag debe ser la versión nueva). El kernel no está expuesto en el host: su /health solo lo ven los healthchecks de Docker y la web.
4
Si algo falla, vuelve atrás tú. Restaura NOVVUS_VERSION al valor anterior, up -d --wait de nuevo y, si la versión nueva alcanzó a aplicar migraciones, restaura la base desde el dump. Por eso el backup va antes, no después.
Si un servidor manual ya está en /opt/novvus, el CLI lo detecta: novvus status y novvus version funcionan sobre él (leen la versión del .env) y novvus install se niega a pisarlo. Para migrar de manual a CLI, respalda, baja el stack y reinstala con el CLI reutilizando tus secretos en el .env generado.

4. Cómo se publica un release

Si mantienes el producto (no solo lo operas) te conviene saber de dónde salen las imágenes que descargan los pasos anteriores. Todo gira alrededor de un archivo:

  • VERSION en la raíz del repo es la única fuente de la versión. cli/build.rs y el build.rs del kernel lo embeben en compile-time; el kernel lo reporta en /health; el CLI lo muestra en novvus version.
  • Un push normal a main solo corre ci.yml (8 jobs de pruebas). Nada se publica sin un tag.
  • Un tag vX.Y.Z dispara .github/workflows/release.yml, y su primer job falla si el tag no coincide con VERSION.

La secuencia para publicar, en orden:

# 1. Todo lo que va en el release ya está en main
git push origin main

# 2. Sube la versión (única fuente) y confírmala
echo 0.1.7 > VERSION
git commit -am "Bump version to 0.1.7"
git push origin main

# 3. Etiqueta y publica el tag: esto dispara release.yml
git tag -a v0.1.7 -m "Novvus Core v0.1.7"
git push origin v0.1.7

Jobs de release.yml y sus dependencias:

version ── ¿tag == VERSION? ──► tests (ci.yml completo)
                                   │
                    ┌──────────────┴───────────────┐
                    ▼                              ▼
              cli-build                        build-push
     (linux-x64 musl, linux-arm64 QEMU)   (5 imágenes → GHCR, tags X.Y.Z y latest)
                    │                              │
                    ▼                              │
               cli-dist                            │
   (dist/: install.sh, latest, <v>/manifest.json,  │
    <v>/linux-x64/novvus, <v>/linux-arm64/novvus)  │
                    │                              │
                    └──────────────┬───────────────┘
                                   ▼
                          publish-downloads (R2)
JobQué produce
versionVerifica que el tag y VERSION coinciden; exporta la versión al resto.
testsReutiliza ci.yml completo: kernel, CLI, instalador, Python, cobertura, mutation testing, web y E2E.
cli-buildBinarios estáticos del CLI (musl + rust-lld) para linux-x64 y linux-arm64, verificados con file y ejecutando novvus version (ARM64 bajo QEMU).
cli-distEl árbol dist/ con manifest.json (SHA-256 por plataforma), latest e install.sh.
build-pushImágenes ghcr.io/novvus/{core, web, bootstrap, crm, projects} con tags X.Y.Z y latest.
publish-downloadsSube dist/ al bucket R2 novvus-downloads, servido por downloads.novvus.dev e install.novvus.dev. Solo corre si las imágenes GHCR ya existen.

Reglas del job de publicación que conviene conocer porque explican el comportamiento de novvus update:

  • put-object archivo por archivo, nunca sync --delete: las versiones ya publicadas no se tocan (histórico inmutable).
  • Orden seguro: binarios → manifest → verificación pública de los checksums → install.sh → latest al final. Si algo falla antes, latest sigue apuntando a la versión anterior y ningún cliente ve una versión a medias.
  • Cache: carpetas versionadas max-age=31536000, immutable; latest no-cache; install.sh max-age=300.
  • Verificación final: el job descarga install.sh desde install.novvus.dev y lo ejecuta de verdad en el runner; debe reportar la versión recién publicada.

La cadena de confianza de install.sh

install.novvus.dev/install.sh            bootstrap bash público y auditable
        ↓
downloads.novvus.dev/latest              solo el número de versión (p. ej. 0.1.6)
        ↓
downloads.novvus.dev/<v>/manifest.json   SHA-256 de cada binario por plataforma
        ↓
downloads.novvus.dev/<v>/linux-x64/novvus   (o linux-arm64)
        ↓  SHA-256 obligatorio: si no coincide, se borra y aborta
/usr/local/bin/novvus
        ↓
sudo novvus install  →  ghcr.io/novvus/*  →  Novvus Core

novvus update reproduce exactamente este protocolo desde Rust (cli/src/release.rs), sin curl ni sha256sum en el servidor: nunca se ejecuta un binario sin verificar. Los binarios son públicos y no contienen Novvus Core ni credenciales. Lo que hoy no existe es firma criptográfica del release (solo SHA-256 contra un manifest del mismo origen); está en el BACKLOG.

5. Actualizar un módulo propio

Esto ya es terreno de desarrollador (si no has construido un módulo, empieza por el tutorial). Un módulo se actualiza con tres piezas: una versión nueva en el manifiesto, una migración nueva si cambió el modelo, y un re-registro para que el kernel aplique lo pendiente.

1
Sube la versión SemVer en novvus.toml: version = "0.2.0". El registro con versión mayor re-valida dependencias, y la versión viaja en el meta que ven las vistas genéricas.
2
Genera la migración incremental. Cambia tus modelos y pide al SDK el diff contra tu base de desarrollo, donde ya está aplicado el esquema actual del módulo: 
cd modules/inventario
NOVVUS_DATABASE_URL=postgres://novvus:novvus_dev_password@localhost:5432/novvus \
  novvus makemigration -m add_min_stock
# Migración generada: migrations/0002_add_min_stock.sql
El SDK numera automáticamente (0002, 0003…), añade el bloque RLS a toda tabla nueva y responde Sin cambios: no se generó migración. si no hay diff. Revisa el SQL antes de confirmarlo: es el artefacto canónico.
3
Nunca edites una migración aplicada. El kernel guarda el checksum en core.module_migrations y rechaza el registro si cambia. Si 0001 tiene un error, lo corriges en 0002.
4
Re-registra y migra. En el stack Docker (demo o producción) basta con volver a construir la imagen del módulo y arrancar: bootstrap hace POST /api/core/modules con el manifiesto y todas las migraciones, y como el módulo ya existe, llama a POST /api/core/modules/inventario/migrate, que aplica solo las pendientes en orden, cada una en su transacción. Si una falla el módulo no se habilita y —en un cliente— el update hace rollback. 
# Demo local
python install.py update

# A mano, con un JWT de administrador (core.modules.manage), es lo mismo que hace bootstrap:
curl -s -X POST http://localhost:8000/api/core/modules \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d @registro.json           # {"manifest_toml": "...", "migrations": [{"version": "0001_init", "sql": "..."}, ...]}
curl -s -X POST http://localhost:8000/api/core/modules/inventario/migrate \
  -H "Authorization: Bearer $JWT"
# → {"applied_migrations": ["0002_add_min_stock"]}
5
Reinicia el runtime. El proceso del módulo hace handshake al arrancar y envía su meta nuevo; si añadiste campos a __novvus_views__, las vistas genéricas los verán en menos de 60 s (la shell revalida por ETag).
Ojo con el token de servicio. Actualizar un módulo no cambia su NOVVUS_SERVICE_TOKEN. Solo install emite uno (y se muestra una única vez). Si desinstalas para "empezar limpio", el esquema mod_inventario se borra con todo lo que contiene: eso es una reinstalación, no una actualización.

Antes de actualizar producción: lista corta

  • [ ] novvus status devuelve exit 0 (si no, el preflight te va a detener igual).
  • [ ] Hay disco para el backup: el dump de Postgres más el volumen files comprimido.
  • [ ] Avisaste una ventana: el arranque de la versión nueva implica unos segundos sin servicio.
  • [ ] Leíste las notas del release: si añade variables al .env, el CLI las agrega solo, pero un despliegue manual no.
  • [ ] Sabes dónde quedarán el backup (/opt/novvus/backups/) y el log (/opt/novvus/logs/).
