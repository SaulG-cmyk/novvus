La API

Nivel medio

Una sola puerta de entrada: el gateway del kernel. Debajo de /api/core/… viven la identidad, las organizaciones, el ciclo de vida de módulos, los metadatos, los adjuntos, las extensiones, los campos personalizados, el chatter y el tiempo real; debajo de /api/{módulo}/…, la API automática y los endpoints de negocio de cada módulo, reenviados con headers firmados. Esta página es la referencia completa de ambas superficies, verificada contra kernel/crates/novvus-gateway/src/lib.rs.

Cómo llegar al gateway

EntornoURL baseQuién responde
Desarrollo, directohttp://127.0.0.1:8000El kernel (NOVVUS_BIND_ADDR=0.0.0.0:8000). Ideal para curl.
Desarrollo, vía webhttp://localhost:3000/api/…Next.js reescribe /api/:path* → NOVVUS_KERNEL_URL/api/:path* (same-origin, sin CORS).
Producciónhttp://<servidor>:8077/api/…Solo la web escucha en el host (NOVVUS_WEB_PORT, contenedor 3000). El kernel y Postgres viven en la red interna de Docker; el rewrite de Next es la única ruta al kernel.
El rewrite se fija al compilar. NOVVUS_KERNEL_URL se lee durante next build y queda serializado en el manifiesto de rutas; cambiarlo en runtime con next start no tiene efecto. En Docker llega como build-arg (apps/web/Dockerfile).

Convenciones

  • JSON en ambos sentidos; identificadores UUIDv7; fechas ISO-8601 con zona.
  • Errores del kernel: {"error": {"code": "…", "message": "…"}}. Errores de módulos (FastAPI): {"detail": "…"}. El cliente lib/api.ts normaliza ambos en ApiError.
  • Códigos: 401 sin credenciales o token inválido · 403 sin permiso o token no ligado a la organización · 404 · 409 conflicto · 413 cuota de archivos · 422 validación · 429 rate limit en /auth/* · 503 módulo no habilitado o runtime desconectado.
  • Las rutas de /api/core/auth/* tienen rate limit por IP: 30 peticiones/minuto por defecto (NOVVUS_AUTH_RATE_LIMIT_PER_MINUTE).

Los cuatro actores

Flujo de sesión con curl

BASE=http://127.0.0.1:8000

# 1. Registro (201 → {"user": {...}})
curl -s -X POST $BASE/api/core/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"ana@acme.test","password":"una-clave-larga","display_name":"Ana"}'

# 2. Login → {"user", "tokens": {"access_token", "refresh_token", "org_id"}}
TOKENS=$(curl -s -X POST $BASE/api/core/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"ana@acme.test","password":"una-clave-larga"}')
ACCESS=$(echo $TOKENS | jq -r .tokens.access_token)
REFRESH=$(echo $TOKENS | jq -r .tokens.refresh_token)

# 3. Crear organización (201; Ana recibe el rol Owner con permiso "*")
ORG=$(curl -s -X POST $BASE/api/core/orgs -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' -d '{"name":"ACME","slug":"acme"}' | jq -r .id)

# 4. Re-emitir el par LIGADO a la organización (así se cambia de org)
TOKENS=$(curl -s -X POST $BASE/api/core/auth/refresh -H 'Content-Type: application/json' \
  -d "{\"refresh_token\":\"$REFRESH\",\"org_id\":\"$ORG\"}")
ACCESS=$(echo $TOKENS | jq -r .tokens.access_token)

# 5. ¿Quién soy y qué puedo?  → {"user", "org_id", "roles", "permissions": ["*"]}
curl -s $BASE/api/core/me -H "Authorization: Bearer $ACCESS"

# 6. Cerrar sesión (204): revoca el refresh presentado
curl -s -X POST $BASE/api/core/auth/logout -H 'Content-Type: application/json' \
  -d "{\"refresh_token\":\"$REFRESH\"}"
Los refresh tokens son de un solo uso. Cada /auth/refresh devuelve un refresh nuevo y quema el anterior (la base guarda solo el hash SHA-256). Reutilizar uno rotado se interpreta como robo y revoca la cadena completa de sesiones. login también acepta org_id opcional para salir ya ligado a una organización.

Referencia de /api/core

Todas las rutas van bajo /api/core. «Bearer + org» significa JWT con organización activa. Los cuerpos y respuestas se resumen a sus claves principales.

Autenticación e identidad

Método y rutaActorBody → respuesta
POST /auth/register— (rate limit){email, password, display_name} → 201 {user}. Argon2id; email único global.
POST /auth/login— (rate limit){email, password, org_id?} → {user, tokens}.
POST /auth/refresh— (rate limit){refresh_token, org_id?} → {tokens}. Rota el refresh y permite cambiar de organización.
POST /auth/logout— (rate limit){refresh_token} → 204.
GET /meBearer→ {user, org_id, roles, permissions[]}. Los permisos van ordenados y son los efectivos; sin org activa, lista vacía. Base del gating de UI.

Organizaciones y RBAC

Método y rutaActor / permisoBody → respuesta

POST /orgsBearer{name, slug} → 201 organización; el creador recibe el rol Owner.
GET /orgs/{org_id}/memberscore.members.manage; el token debe estar ligado a esa org→ [{membership_id, user_id, email, display_name, created_at, roles[]}].
POST /orgs/{org_id}/memberscore.members.manage{email} → 201 membresía. El usuario debe existir (invitaciones: BACKLOG).

GET /permissionsBearer + org→ catálogo global [{key, module_id, description}].

Módulos por organización, plan y configuración

Método y rutaActor / permisoBody → respuesta
GET /modulesBearer + org→ [{id, name, version, status, instance_status, manifest, base_url, …}]. status es el efectivo para la org (not-installed | installed | enabled | disabled); instance_status el de la instancia. La tienda y el launcher se arman con esto.
GET /orgs/{org}/modules/{id}/planBearer + org (cualquier miembro)→ {target, enable_order[], satisfied[], problems[]}: cierre transitivo de dependencias. Con problems no vacío el plan no es accionable.

POST …/enable · …/disablecore.modules.manage→ vista del módulo; hooks on_enable / on_disable. enable verifica dependencias por org.
POST …/uninstallcore.modules.manage→ 204. No destructivo: quita la fila de habilitación; el esquema y las filas del tenant sobreviven. El hook on_uninstall corre antes de borrar la fila.
GET /orgs/{org}/modules/{id}/configBearer + org→ {module_id, fields: [{key, type, label, options, permission, secret, value, is_set}]}. Solo los campos cuyo permission tiene el llamante.
PUT /orgs/{org}/modules/{id}/configpermiso de cada clave (default core.modules.manage){values: {clave: valor}} → vista actualizada. Validación de tipo y opciones de select.
GET /config · PUT /configtoken de servicio + x-novvus-orgEl propio módulo lee ({clave: valor}, sin enmascarar) o escribe ({values}) su configuración para ese tenant. Es lo que usan module.config() y module.set_config().

Ciclo de vida de instancia, handshake y status

Los seis primeros aceptan usuario con core.modules.manage o el token de bootstrap.

Método y rutaActorBody → respuesta
POST /modules (register)manage · bootstrap{manifest_toml, migrations: [{version, sql}]} → 201 ModuleRecord {id, name, version, status, manifest, base_url}. Valida id, semver, prefijos de permisos/eventos/config/cron/ui/extensions.
POST /modules/{id}/installmanage · bootstrap→ {module, applied_migrations[], service_token}. Crea mod_{id}, aplica migraciones, registra permisos y cron. El token de servicio se devuelve una sola vez.
POST /modules/{id}/migratemanage · bootstrap→ {applied_migrations[]}. Migraciones pendientes de una versión nueva; checksum inmutable.
POST /modules/{id}/enable · /disablemanage · bootstrap→ ModuleRecord. ENABLED: el gateway rutea y el bus entrega; DISABLED: 503 en su namespace, los eventos se acumulan.
POST /modules/{id}/uninstallmanage · bootstrap{"confirm": true} → 204. Destructivo (DROP SCHEMA … CASCADE), solo desde DISABLED.
POST /modules/handshaketoken de servicio{module_id, base_url, meta?} → {module_id, status, internal_hmac_secret, database_url, schema}. El token debe pertenecer a module_id. El meta viaja aquí; un meta inválido (serde estricto, ≤512 KB) rechaza el handshake.
GET /modules/statustoken de servicio→ {"crm": "enabled", "projects": "disabled", …}. Con esto un módulo reporta degraded en su /health.
Sobre confirm. El handler real (routes/modules.rs, UninstallBody) lo lee del cuerpo JSON; MODULE_CONTRACT.md §3 lo describe como query ?confirm=true. El código manda.
# Registrar + instalar con el token de bootstrap (lo que hace scripts/bootstrap.py)
curl -s -X POST $BASE/api/core/modules -H "x-novvus-bootstrap-token: $NOVVUS_BOOTSTRAP_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"manifest_toml\": $(jq -Rs . < modules/crm/novvus.toml), \"migrations\": [{\"version\":\"0001_init\",\"sql\":\"…\"}]}"
curl -s -X POST $BASE/api/core/modules/crm/install -H "x-novvus-bootstrap-token: $NOVVUS_BOOTSTRAP_TOKEN"
# → {"module": {...}, "applied_migrations": ["0001_init", ...], "service_token": "nvk_..."}

Metadatos (vistas genéricas)

Método y rutaActorRespuesta
GET /metaBearer + org→ {modules: [meta…]} de los módulos habilitados en la org, con los campos de extensión (ext.{extensor}.{campo}) y los campos personalizados (custom.{nombre}) ya fusionados, filtrado por el permiso read de cada modelo y con capabilities.create/update/delete=false si falta el write. Archivos (adjuntos)

Actor: usuario o módulo con token de servicio + x-novvus-org sobre sus propios modelos. El permiso es el del modelo padre, resuelto desde el meta (read para listar/descargar, write para subir/borrar).

Método y rutaBody → respuesta
GET /files?module_id=&model=&record_id=→ [{id, module_id, model, record_id, filename, mime, size_bytes, created_by, created_at}] (vivos, más recientes primero).
POST /filesmultipart en este orden: module_id, model, record_id, file (los metadatos deben preceder al archivo: el permiso se verifica antes de aceptar un byte). SHA-256 al vuelo, dedup por (org, sha256), MIME por sniffing (nunca el Content-Type del cliente), ejecutables rechazados (422), cuota por org (413). → 201 vista del adjunto.
GET /files/{id}Descarga en streaming con X-Content-Type-Options: nosniff; Content-Disposition: inline solo para PNG/JPEG/GIF/WebP verificados, attachment para todo lo demás (nunca HTML/SVG inline).
DELETE /files/{id}→ 204. Borrado lógico; el GC libera el blob tras la retención (30 días).
curl -s -X POST $BASE/api/core/files -H "Authorization: Bearer $ACCESS" \
  -F module_id=crm -F model=contacts -F record_id=$CONTACT -F file=@cotizacion.pdf

Extensiones y campos personalizados

Método y rutaActor / permisoBody → respuesta
GET /extensions?org_id=token de servicio→ [{extender_id, target_model, fields, ui}]: definiciones que apuntan a los modelos del módulo llamante. Con org_id, solo extensores habilitados en esa org (lo que el SDK necesita para validar escrituras). Caché TTL 60 s en el SDK.
GET /custom-fields?module_id=&model=Bearer + org (cualquier miembro)→ definiciones vivas [{id, module_id, model, name, field_type, label, config, required, position, active, created_at}].
POST /custom-fieldscore.custom_fields.manage{module_id, model, name, type, label, config?, required?, position?} → 201. name ∼ ^[a-z][a-z0-9_]{0,29}$ e inmutable; tipos string|text|integer|decimal|boolean|date|datetime; choices solo en string; el modelo debe existir en el meta y el módulo estar habilitado; 409 si el nombre ya existe; límite 50 por modelo (NOVVUS_CUSTOM_FIELDS_LIMIT).

Chatter, notificaciones y tiempo real

Prefijo por registro: /chatter/{module}/{model}/{record_id}. Leer y comentar exigen el permiso read del modelo padre. Actor: usuario o módulo (solo mensajes system sobre sus modelos).

Método y rutaBody → respuesta
GET …/messages?cursor=&limit=→ {items: [{id, record_id, author_id, kind, body, meta, attachment_ids, created_at, edited_at}], next_cursor}. Keyset por (created_at, id), más recientes primero; limit 1–200, default 50.
POST …/messages{kind?: "comment"|"note"|"system", body, meta?, attachment_ids?} → 201. Usuarios: comment/note; módulos: solo system. 1–10 000 caracteres. Menciones @[uuid] validadas contra la membresía. Autor auto-sigue el registro; fan-out síncrono en la misma transacción (mención → mention, seguidores → follower_message) y pg_notify('novvus_notify').
PATCH /chatter/messages/{id}{body} → mensaje. Solo el autor, dentro de 15 min (NOVVUS_CHATTER_EDIT_WINDOW_MINUTES); fuera de ventana, 403.
DELETE /chatter/messages/{id}→ 204. Solo el autor; lógico.
GET …/followers→ [{user_id, display_name, email}].
PUT …/followers/me · DELETE …/followers/meSeguir / dejar de seguir → 204.
GET …/activities→ [{id, record_id, activity_type, summary, due_date, assigned_to, state, done_by, done_at, note, created_by, created_at}]; abiertas primero.
POST …/activities{activity_type: call|meeting|email|todo, summary, due_date, assigned_to, note?} → 201. El asignado (si no es el creador) recibe activity_assigned.
POST /chatter/activities/{id}/done · /cancel→ actividad cerrada. Puede cerrar el asignado, el creador o quien tenga el write del modelo padre. Otra acción → 404.
GET /notifications?unread=1&cursor=&limit=Bearer + org → {items: [{id, kind, payload, created_at, read_at}], next_cursor, unread_count}; limit 1–100. Tipos: mention, follower_message, activity_assigned, activity_due (pasada horaria, una vez al día por actividad vencida).
POST /notifications/read · /read-all{ids: [...]} / sin body → 204.
GET /stream?token=SSE. Emite eventos con nombre notification (payload {org_id, user_ids, kind}), filtrados por org y usuario; keep-alive ping cada 25 s. Un solo LISTEN por proceso del gateway; si el receptor se rezaga, salta eventos y la shell reconcilia por polling.
curl -s -X POST $BASE/api/core/chatter/crm/contacts/$CONTACT/messages -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' -d '{"kind":"note","body":"Revisar con @[7d3f…] antes del viernes"}'

# Tiempo real (EventSource no manda headers → token por query)
curl -N "$BASE/api/core/stream?token=$ACCESS"

El proxy firmado a los módulos

Al llamar /api/crm/… el gateway exige que el módulo esté ENABLED y con base_url registrado por handshake (si no, 503), resuelve al llamante, y reenvía la petición con estos headers. El JWT nunca llega al módulo.

x-novvus-user:      <uuid del usuario>          # vacío en llamadas de servicio
x-novvus-org:       <uuid de la organización>
x-novvus-perms:     crm.contacts.read,crm.leads.write,...
x-novvus-timestamp: <unix seconds>               # ventana anti-replay de ±60 s
x-novvus-signature: HMAC-SHA256(user \n org \n perms \n ts \n MÉTODO \n ruta)
x-novvus-locale:    es-MX                        # informativo: FUERA de la firma, jamás autoriza
  • Solo cruzan content-type, accept y accept-language del cliente; cualquier x-novvus-* que intente colar un cliente muere en el gateway.
  • Cuerpo máximo proxyado: 10 MB. El SDK (security.verify_request) responde 401 a toda petición sin firma válida, así que llegar «por atrás» al puerto del módulo tampoco sirve.
  • El locale se toma de x-novvus-locale, si no del primer tag de Accept-Language, si no es-MX.

Llamadas módulo→módulo

GET /api/crm/contacts/{id}
x-novvus-service-token: nvk_...
x-novvus-org: <uuid de la organización>

El gateway inyecta como permisos los [dependencies] service_permissions del manifiesto del llamante (nunca core.*) y el usuario viaja vacío. Desde el SDK: await module.call("GET", f"/api/crm/contacts/{cid}", org_id=…) — así resuelve Proyectos el nombre del contacto al crear un proyecto.

La API automática de los módulos

Por cada modelo registrado con @module.model, el SDK monta siete rutas bajo /api/{módulo}/{recurso} (autoapi.py). Los permisos por defecto son {módulo}.{recurso}.read/write; __novvus_api__["permissions"] los cambia (las etapas del CRM usan crm.pipelines.*) y __novvus_api__["disabled"] apaga rutas (las tablas de unión contact_tags no exponen list).

MétodoRutaPermisoNotas
GET/{recurso}readLista paginada → {items, next_cursor}.
GET/{recurso}/group?by=readConteos por valor de un campo groupable (incluye custom.{nombre} con choices o booleano) → {groups: [{value, label, count}]}. Alimenta el kanban.
GET/{recurso}/export?format=csv|xlsxreadStreaming con labels traducidos según locale; columnas ext y custom al final. Más de 100 000 filas (__novvus_api__["export_max_rows"]) → 422 «acota el filtro».
POST/{recurso}write201. Esquema Pydantic con extra="forbid": cualquier campo desconocido → 422, así que org_id es imposible de inyectar (lo pone el contexto). Acepta ext y custom validados contra las definiciones de la org.
GET/{recurso}/{id}read404 si no existe o es de otra organización (RLS).
PATCH/{recurso}/{id}writeParcial. Los campos en __novvus_views__["track"] publican un mensaje system en el chatter con {field, old, new}.
DELETE/{recurso}/{id}write204. Borrado suave (deleted_at).

El DSL de filtros (?filter=)

{"and": [
  {"field": "stage_id", "op": "in", "value": ["…", "…"]},
  {"or": [
    {"field": "amount", "op": "gte", "value": "100000"},
    {"field": "expected_close_date", "op": "between", "value": ["2026-09-01", "2026-09-30"]}
  ]},
  {"field": "ext.salesmx.rfc", "op": "contains", "value": "XAXX"},
  {"field": "custom.segmento", "op": "eq", "value": "enterprise"},
  {"field": "closed_at", "op": "is_null", "value": true}
]}
  • Nodo = grupo {"and": [...]} / {"or": [...]} (una sola clave, lista no vacía) o condición {field, op, value}.
  • Operadores (whitelist cerrada, filters.py): eq ne in is_null para todo tipo filtrable; gt gte lt lte between para numéricos, date, datetime; contains ilike para string/text. in acepta hasta 100 valores; contains escapa % y _.
  • Límites: profundidad ≤ 5, ≤ 50 condiciones. Solo campos filterable del meta, más ext.{extensor}.{campo} y custom.{nombre} de definiciones activas (castings JSONB por tipo).
  • Todo rechazo es 422 con la ruta del nodo: {"detail": {"message": "…", "path": "and[1].or[0].value"}}. Nunca hay text() ni interpolación: solo expresiones de columna, y el tenant lo sigue poniendo la sesión + RLS.

CódigoCuándo
401Headers internos ausentes, firma inválida o timestamp fuera de ±60 s (el runtime solo acepta tráfico del gateway).

Rutas internas del runtime (no pasan por el gateway)

Las monta NovvusModule.create_app() (app.py). El gateway solo proxya /api/{módulo}/…, de modo que estas rutas no son alcanzables desde fuera; el kernel las llama directamente al base_url del handshake con headers firmados, y el middleware del SDK rechaza con 401 cualquier petición sin firma. La única excepción es el healthcheck.

Proyectos (modules/projects/module.py)

No declara endpoints custom: solo la auto-API de projects y tasks. Su valor es la interoperabilidad: escucha crm.opportunity.won, crea el proyecto enlazado con tres tareas (una sola vez por oportunidad, aun con reentregas), resuelve el nombre del contacto por module.call al CRM (service_permissions = ["crm.contacts.read"]; si el CRM no está, degrada a cadena vacía) y emite projects.project.created.

Consumir la API desde un sistema externo

1
Servidor a servidor con JWT. Usa el flujo de sesión de arriba contra http://<servidor>:8077/api/… (el rewrite de Next reenvía cualquier cliente HTTP, no solo navegadores) o contra :8000 en desarrollo. Crea un usuario dedicado con un rol mínimo; renueva con /auth/refresh antes de los 15 min y guarda siempre el refresh nuevo.
2
Desde un sitio web ajeno (navegador). Al ser otro origen necesitas CORS: fija NOVVUS_CORS_ORIGINS=https://tusitio.example,https://otro.example en el kernel (lista separada por comas; vacía = CORS deshabilitado; con valor se permiten todos los métodos y headers para esos orígenes). En producción el kernel no está expuesto, así que además tendrías que publicarlo detrás de tu reverse proxy o apuntar el sitio al puerto de la web.
3
Integración profunda: registra tu sistema como módulo. Un manifiesto mínimo (sin modelos, como salesmx) registrado e instalado te da un token de servicio nvk_ con el que llamar APIs de otros módulos por el proxy (x-novvus-service-token + x-novvus-org, permisos acotados por service_permissions), emitir eventos declarados y escuchar los de otros módulos en tu /_novvus/events.
No existen API keys personales. Las únicas credenciales son el JWT de usuario, el token de servicio de un módulo y el token de bootstrap (solo instancia). Tampoco hay webhooks salientes todavía (BACKLOG «Plataforma»).
Ver más: OpenAPI y exploración en desarrollo

Cada runtime es FastAPI y publica /openapi.json y /docs en su propio proceso, pero el middleware de firma bloquea el acceso directo. Las formas prácticas de explorar en desarrollo son tres: leer las rutas en autoapi.py/business.py; arrancar el módulo en modo offline (NOVVUS_DATABASE_URL + NOVVUS_INTERNAL_HMAC_SECRET, sin kernel) y firmar tus peticiones con novvus_sdk.security.sign() como hace el arnés de tests; o simplemente pasar por el gateway con un JWT, que es lo que hace modules/crm/requests.http. El kernel en Rust no genera OpenAPI: esta página es su referencia.
