Arquitectura

Nivel medio

NOVVUS CORE es un kernel de plataforma escrito en Rust sobre el que corren módulos de negocio en Python, con un frontend Next.js que solo administra módulos y una base PostgreSQL 16 compartida por todos los tenants. Esta página describe los cuatro planos, cómo viaja una petición y un evento, los tres canales de comunicación entre módulos, el ciclo de vida en dos ejes y el mapa del repositorio. El contrato normativo es documents/docs/ARCHITECTURE.md; el detalle de cada crate está en El kernel por dentro.

Idea central

La plataforma se lee en tres capas: core de plataforma (kernel) → sistema de módulos (SDK y contrato) → aplicaciones empresariales (CRM, Proyectos, SalesMX). Es un modelo comparable a Odoo en lo comercial, pero con contratos técnicos estrictos: los módulos no son mini-aplicaciones libres, son extensiones gobernadas por un manifiesto que el kernel valida, y el kernel es el único componente que emite credenciales, decide permisos, instala módulos y ejecuta sus migraciones.

Dos superficies de frontend

Desde la decisión del 2026-07-28 (DECISIONS.md) la shell de plataforma es solo un administrador de módulos; toda la UI de negocio vive en el frontend de su módulo. Ambas superficies comparten un guard de sesión en app/(protected)/layout.tsx (client-side, tokens en localStorage).

SuperficieRutasQué contiene
Shell de plataforma /, /apps, /apps/{moduleId}, /settings, /settings/custom-fields, /admin Login y first-run, launcher (grid de apps habilitadas + widgets [ui.dashboard]), tienda/instalador con plan de dependencias, configuración por módulo y de plataforma, administración de miembros y roles (/admin gatea por permiso a nivel de página).
Frontend por módulo /{module_id}/… y /m/{module_id}/{model}[/{id}] Cada módulo abre a pantalla completa con chrome propio (ModuleShell): barra superior con icono/accent de [presentation], navegación de [ui.nav] y app-switcher. Las vistas genéricas (lista, formulario, kanban, calendario, export) se montan bajo el chrome del módulo dueño mediante m/[moduleId]/layout.tsx.

Regla validada por el kernel (valid_ui_path en novvus-registry/src/manifest.rs): toda path de [ui] vive bajo /{id}; un item de ui.nav no puede apuntar a /m/…. Un módulo sin páginas dedicadas simplemente no declara nav y la shell deriva su navegación del meta bajo /m/{id}/….

Viaje de una petición

Ejemplo: un usuario lista contactos del CRM desde el navegador.

1
Navegador → web. El cliente llama GET /api/crm/contacts con Authorization: Bearer <access>. En producción solo la web escucha en el host (puerto NOVVUS_WEB_PORT, default 8077); apps/web/next.config.ts reescribe /api/:path* hacia NOVVUS_KERNEL_URL (same-origin, sin CORS). En desarrollo el navegador puede hablar directo con el kernel en :8000.
2
Gateway: JWT. La ruta /api/{module_id}/{*rest} cae en proxy::proxy_handler. Primero comprueba que el módulo está enabled a nivel instancia y que tiene base_url (handshake hecho); si no, 503. Luego decodifica el JWT con typ=access (HS256, NOVVUS_JWT_ACCESS_SECRET, leeway 5 s).
3
Gateway: RBAC vivo. Los roles del token son solo informativos. El gateway resuelve los permisos efectivos de (user, org) desde la caché RBAC (TTL 30 s, invalidación inmediata al mutar roles/membresías) y los serializa ordenados en X-Novvus-Perms.
4
Gateway: proxy firmado. Firma HMAC-SHA256 sobre user\norg\nperms\ntimestamp\nmethod\npath con NOVVUS_INTERNAL_HMAC_SECRET y reenvía a {base_url}{path?query} con X-Novvus-User/Org/Perms/Timestamp/Signature más X-Novvus-Locale (informativo, fuera de la firma). Solo cruzan content-type, accept y accept-language del cliente: cualquier X-Novvus-* entrante muere aquí. Cuerpo máximo 10 MiB; timeout 30 s.
5
SDK: verificación. El middleware del SDK recalcula la firma con el secreto recibido en el handshake y rechaza si no coincide o si |now − timestamp| > 60 s. Luego exige el permiso concreto del endpoint (crm.contacts.read).
6
SDK: sesión tenant. Abre una transacción y ejecuta SELECT set_config('app.org_id', $1, true) (equivalente a SET LOCAL, parametrizado). El módulo conecta como novvus_module, sin privilegios sobre core ni otros mod_*.
7
Postgres: RLS. La política tenant_isolation (USING + WITH CHECK, con FORCE ROW LEVEL SECURITY) filtra por org_id = current_setting('app.org_id')::uuid. Sin tenant fijado, current_setting falla: fail-closed.
8
Respuesta. El módulo devuelve JSON paginado por cursor; el gateway reenvía solo estado, content-type y cuerpo.
Lo esencial. El JWT nunca llega al módulo, el org_id nunca se acepta del body o la query, y RLS es la segunda barrera aunque el código del módulo olvidara un filtro.

Viaje de un evento

Ejemplo: el CRM gana una oportunidad y Proyectos reacciona.

CRM (SDK)                 Kernel / novvus-events               PostgreSQL            Projects (SDK)
  │ module.emit(...)             │                                 │                      │
  │ POST /api/core/events        │                                 │                      │
  │ x-novvus-service-token       │                                 │                      │
  ├─────────────────────────────►│ ¿event_type ∈ manifest.emits?   │                      │
  │                              │ BEGIN                           │                      │
  │                              │  INSERT core.events             │                      │
  │                              │  INSERT event_deliveries (una   │                      │
  │                              │   por módulo enabled|disabled   │                      │
  │                              │   con el tipo en listens)       │                      │
  │                              │  pg_notify('novvus_events', id) │                      │
  │                              │ COMMIT                          │                      │
  │◄── 202 Accepted ─────────────┤                                 │                      │
  │                              │◄── LISTEN novvus_events ────────┤                      │
  │                              │ Dispatcher: FOR UPDATE SKIP     │                      │
  │                              │ LOCKED (lote 20) → POST         │                      │
  │                              │ {base_url}/_novvus/events       │                      │
  │                              │ firmado (user="", perms="")     │                      │
  │                              ├─────────────────────────────────┼─────────────────────►│
  │                              │                                 │  verifica firma,     │
  │                              │                                 │  INSERT _processed_  │
  │                              │                                 │  events ON CONFLICT  │
  │                              │                                 │  DO NOTHING + handler│
  │                              │◄──────────── 2xx ───────────────┼──────────────────────┤
  │                              │ delivered (o attempts+1 y       │                      │
  │                              │ next_retry_at con backoff)      │                      │
  • At-least-once. La tabla es la fuente de verdad; NOTIFY solo acelera. Un barrido cada 5 s retoma deliveries pendientes aunque el NOTIFY se haya perdido o el módulo estuviera caído.
  • Backoff. base^attempts con exponente máximo 4 y tope 300 s (base 4: 4, 16, 64, 256 s). Tras 25 intentos la entrega pasa a failed.
  • Idempotencia. El SDK inserta event_id en mod_{id}._processed_events en la misma transacción del handler; un duplicado responde 200 sin re-ejecutar.
  • Módulos deshabilitados también reciben fila de delivery: acumulan mientras están abajo y se ponen al día al habilitarse; el despachador solo hace POST a los enabled con base_url.

Tres canales de comunicación entre módulos

CanalCuándoCómo se autoriza
Evento (asíncrono) Algo ocurrió y otros deben reaccionar sin esperar respuesta. El emisor solo publica tipos declarados en emits; el consumidor los declara en listens. Payload mínimo (IDs), tratado como no confiable.
API pública vía gateway (síncrono) Un módulo necesita leer o accionar sobre otro ahora. x-novvus-service-token + x-novvus-org. El gateway inyecta como permisos los service_permissions del manifiesto del llamante (nunca core.*) y el usuario viaja vacío.
Extensiones ([extensions]) Un módulo aporta campos y UI a modelos de otro sin tocar su esquema (p. ej. SalesMX añade RFC y régimen a crm.contacts). El target debe estar en [dependencies] modules; los datos viven en la columna ext JSONB del base y solo el base los escribe. Límites: 32 campos por extensor, 16 extensores por modelo.

Lo que nunca se permite: leer tablas de otro módulo. Proyectos no consulta mod_crm.contact; el rol novvus_module ni siquiera tiene USAGE sobre esquemas ajenos.

Un canal aparte: novvus_notify. Las notificaciones del chatter (menciones, seguidores, actividades) no pasan por el bus de módulos. El kernel hace fan-out síncrono a core.notifications en la transacción del mensaje y emite pg_notify('novvus_notify', …); el gateway mantiene una conexión LISTEN por proceso y reparte en memoria a las conexiones SSE (GET /api/core/stream?token=). Es plano kernel → usuarios, no módulo → módulo.

Pipeline de metadatos y vistas genéricas

Los modelos declarados en el SDK alimentan un documento de meta (modelos, campos tipados, vistas list/form/kanban/calendar, permisos, capacidades attachments/chatter). El SDK lo envía dentro del handshake; el kernel lo valida con tipos serde estrictos (deny_unknown_fields, máximo 512 KiB) y lo persiste en core.modules.meta. Un meta inválido rechaza el handshake completo. GET /api/core/meta lo sirve filtrado por módulos habilitados en la org y permiso read, fusionando extensiones y campos personalizados, con ETag y Cache-Control: private, max-age=60. Contrato en VIEWS.md; guía en Vistas genéricas y metadatos.

Ciclo de vida de módulos en dos ejes

Eje de INSTANCIA (core.modules.status) — JWT con core.modules.manage o token de bootstrap
  (no existe) ─register─► registered ─install─► installed ─enable─► enabled
                                                    ▲                  │
                                                    │ enable        disable
                                                    │                  ▼
        (DROP SCHEMA mod_{id} CASCADE) ◄─uninstall─ disabled ◄─────────┘

Eje por ORGANIZACIÓN (core.org_modules) — siempre un usuario de esa org
  not-installed (sin fila) ─install─► installed ─enable─► enabled ⇄ disabled
                                          ▲                            │
                                          └──────── uninstall (borra la fila; NO destruye datos)
TransiciónInstanciaPor organización
registerValida el manifiesto y guarda manifest + SQL de migraciones (core.module_migration_sources). Sin efecto en datos.—
installCrea mod_{id}, GRANT USAGE, CREATE al rol de módulo, aplica migraciones pendientes, registra permisos y jobs de cron, emite el token de servicio (una sola vez).Crea la fila installed y dispara el hook on_install (best-effort).
enableExige dependencias enabled y versión compatible. El gateway empieza a enrutar y el bus a entregar.Exige dependencias habilitadas para la misma org; hook on_enable.
disable503 en /api/{id}; los eventos se acumulan.Se bloquea si otro módulo habilitado de la org lo requiere; hook on_disable.
uninstallDestructivo: DROP SCHEMA … CASCADE, borra permisos y la fila de core.modules (cascada a migraciones y deliveries). Requiere {"confirm": true} en el body.No destructivo: solo elimina la fila; esquema y filas del tenant sobreviven bajo RLS. Hook on_uninstall antes de borrar.

GET /api/core/orgs/{org}/modules/{id}/plan calcula el cierre transitivo de dependencias (novvus-registry/src/resolver.rs): devuelve enable_order (dependencias primero), satisfied y problems (missing, unavailable, version_conflict, cycle). La tienda /apps lo usa para habilitar toda la cadena con una confirmación.

Multi-tenancy en una frase

Una sola base, org_id en toda tabla de negocio, SET LOCAL app.org_id por transacción y RLS con FORCE en mod_*; core no usa RLS porque solo el kernel la toca y filtra explícitamente por org_id en cada endpoint. Detalle completo en Base de datos.

Plano de distribución

Producción no compila nada ni necesita el repositorio. Un tag vX.Y.Z igual al contenido de VERSION dispara release.yml, que publica cinco imágenes (ghcr.io/novvus/core, web, bootstrap, crm, projects) y compila el CLI estático (musl) para linux-x64 y linux-arm64.

install.novvus.dev/install.sh ──► downloads.novvus.dev/latest ──► <v>/manifest.json
        │                                                          (SHA-256 por plataforma)
        ▼
/usr/local/bin/novvus  (solo si el SHA-256 coincide; si no, se borra y aborta)
        │
        ▼
sudo novvus install ──► /opt/novvus/{docker-compose.yml,.env} ──► docker pull ghcr.io/novvus/*
        │                      secretos generados con permisos 600
        ▼
postgres → kernel (migraciones core) → bootstrap (one-shot, NOVVUS_BOOTSTRAP_TOKEN) → crm/projects → web :8077
  • Publicación en Cloudflare R2 archivo por archivo (histórico inmutable) y latest al final, solo si las imágenes GHCR ya existen.
  • novvus update reutiliza el mismo protocolo desde Rust (cli/src/release.rs): descarga el CLI destino, verifica SHA-256, hace backup obligatorio y rollback automático si la verificación de salud falla.
  • Pendiente: firma criptográfica de releases (hoy solo SHA-256 contra un manifest del mismo origen). Ver Seguridad.
  • Nota: salesmx no forma parte de docker-compose.prod.yml ni de las imágenes publicadas; es un módulo de desarrollo/demo del contrato de extensiones.

Principios inquebrantables

Tal como los fija ARCHITECTURE.md §6:

  1. Los módulos son ciudadanos de segunda clase respecto al kernel: nunca tocan auth, permisos ni tablas ajenas; todo pasa por los contratos del kernel/SDK.
  2. Todo endpoint valida tenant (org_id) y permisos. Sin excepciones.
  3. Cada pieza incluye tests. Nada se considera terminado sin tests que pasen.
  4. Migraciones versionadas por módulo; el kernel orquesta su ejecución.
  5. Código y comentarios en inglés; documentación de usuario en español.
  6. Nada de fases futuras: lo que se detecte necesario se anota en BACKLOG.md.

Trade-offs de diseño

DecisiónVentajaCosto
Postgres como bus inicialEventos transaccionales, cero infraestructura extra.No apto para >500 ev/s sostenidos o fan-out masivo; criterios de migración a NATS/Redpanda en EVENTS.md §5.
Kernel central en RustContratos y seguridad consistentes; un solo validador.El gateway concentra tráfico y debe cuidarse (pool de 10 conexiones, rate limit solo en /auth).
RLS en una sola baseAislamiento fuerte sin multiplicar bases.Disciplina con org_id en índices y políticas; rol de módulo compartido (rol por módulo en BACKLOG).
UI declarativa + vistas genéricasUn módulo obtiene CRUD completo sin escribir React.Acepta los slots y componentes que la shell ofrece; las genéricas son default, con overrides registrables.
Módulos Python sobre kernel RustRust para el núcleo crítico, Python para velocidad de negocio.El contrato entre lenguajes (headers firmados, meta, handshake) debe mantenerse exacto.
Shell = administrador de módulosLa plataforma crece por módulos sin tocar la shell.La navegación global desaparece: el usuario cambia de app por el launcher o el app-switcher.
