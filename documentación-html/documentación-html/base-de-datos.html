Base de datos

Nivel avanzado

Una sola base PostgreSQL 16 para la plataforma, los módulos y todas las organizaciones. Esta página documenta las 27 tablas del esquema core tal como las crean las migraciones 0001–0011 del kernel, los esquemas mod_* que generan los módulos, los dos roles de base, el aislamiento multi-tenant con Row-Level Security explicado desde cero, el corredor de migraciones y un conjunto de consultas de diagnóstico. Fuente normativa: documents/docs/DATA_MODEL.md y MULTITENANCY.md.

Esquemas de módulos (mod_{id})

El kernel crea el esquema en install y otorga USAGE, CREATE a novvus_module; el contenido lo dictan las migraciones del módulo, generadas por el SDK. Toda tabla de NovvusModel lleva las columnas base:

id          UUID PRIMARY KEY            -- UUIDv7 generado por el SDK
org_id      UUID NOT NULL               -- tenant; índice ix_{tabla}_org_id
created_at  TIMESTAMPTZ DEFAULT now()
updated_at  TIMESTAMPTZ DEFAULT now()
deleted_at  TIMESTAMPTZ                 -- borrado lógico
ext         JSONB NOT NULL DEFAULT '{}' -- {extensor: {campo: valor}} (0002_ext_column)
custom      JSONB NOT NULL DEFAULT '{}' -- {campo_custom: valor} (0003_custom_column)
  • ext: un solo escritor por esquema. El extensor (p. ej. salesmx) declara campos; el base los valida y escribe. Índices GIN sobre ext son opt-in por modelo, no automáticos.
  • custom: valores de campos personalizados por organización; la definición tipada vive en core.custom_fields. El kernel jamás ejecuta SQL sobre mod_*: la limpieza de claves huérfanas es un barrido perezoso del SDK.
  • _processed_events (event_id uuid PK, processed_at): idempotencia de consumidores; el SDK inserta con ON CONFLICT DO NOTHING en la misma transacción del handler.
  • Un módulo sin modelos (salesmx) no tiene migraciones: install crea un esquema mod_salesmx vacío y el módulo vive solo de [extensions].

Tablas actuales: mod_crm tiene company, contact, tag, pipeline, stage, opportunity, lead, activity, contact_tag, opportunity_tag; mod_projects tiene project y task con UNIQUE(org_id, opportunity_id) para crear un solo proyecto por oportunidad ganada.

Multi-tenancy con RLS, desde cero

Row-Level Security es un mecanismo de Postgres por el que la base, no la aplicación, decide qué filas puede ver o modificar una sesión. NOVVUS lo usa para que ninguna consulta de un módulo pueda cruzar organizaciones, aunque el código tenga un bug.

Las tres piezas

1
org_id en toda tabla de negocio. El SDK la añade a cada modelo; no hay FK física hacia core.organizations porque el rol de módulo no ve core; el kernel garantiza la integridad (solo firma headers con orgs existentes).
2
El tenant en la sesión. Al inicio de cada transacción el SDK ejecuta SELECT set_config('app.org_id', $1, true): el tercer argumento true equivale a SET LOCAL, y el valor va parametrizado, nunca interpolado.
3
La política. Generada por el SDK en la migración inicial de cada tabla:
ALTER TABLE contact ENABLE ROW LEVEL SECURITY;
ALTER TABLE contact FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON contact
    USING (org_id = current_setting('app.org_id')::uuid)
    WITH CHECK (org_id = current_setting('app.org_id')::uuid);
CláusulaQué protege
USINGLecturas, updates y deletes: filas de otra org simplemente no existen para la sesión.
WITH CHECKInserts y updates: nadie puede crear o mover una fila hacia otra org.
FORCE ROW LEVEL SECURITYObligatorio: sin él, el dueño de la tabla (el rol de módulo, que ejecutó la migración) ignoraría la política.

Por qué SET LOCAL y no SET

Los pools reutilizan conexiones. Con SET el tenant sobreviviría al COMMIT y la siguiente petición que tomara esa conexión heredaría una organización ajena. Con SET LOCAL el valor muere con la transacción. El SDK no expone conexiones fuera de este contexto transaccional: no existe API para obtener una sesión "cruda".

Fail-closed

Si app.org_id no está fijado, current_setting('app.org_id') lanza error y la consulta falla (500). Nunca devuelve "todas las filas". Es intencional: preferimos un error visible a una fuga silenciosa.

Si ves un error con current_setting('app.org_id'), no lo "arregles" quitando RLS ni FORCE: significa que estás usando una conexión fuera del contexto del SDK (p. ej. un script suelto o psql). Fija el tenant dentro de una transacción como en la sección de psql más abajo.

core no usa RLS

Solo el kernel toca core, y cada endpoint filtra explícitamente por org_id y verifica que el token esté ligado a esa organización. Las tablas v2 con org_id (adjuntos, campos custom, chatter) siguen el mismo patrón: un id de otra org responde 404, no 403. Esta decisión corrigió planes de fase que proponían RLS en core (DECISIONS.md, 2026-07-18 y 2026-07-19).

Riesgos y mitigaciones (resumen de MULTITENANCY.md §5)

Índices y rendimiento: reglas prácticas

  • En tablas de negocio, anteponer org_id en los índices de endpoints frecuentes: (org_id, created_at DESC) para listas, (org_id, status) para estados, UNIQUE(org_id, name) para unicidad por organización.
  • Para workers, índices parciales sobre pendientes: event_deliveries_pending_idx, cron_runs_due_idx, activities_due_idx.
  • Para paneles por registro, índices compuestos con filtro de vivos: attachments_record_idx, messages_record_idx, custom_fields_lookup_idx.
  • No añadir índices "por si acaso"; la política del repo exige una consulta concreta y, para ext, evidencia de pg_stat_statements.

Consultas de diagnóstico

Solo lectura; en producción, ejecútalas con cuidado y evita cambios manuales sin ventana y respaldo. Sustituye <uuid-org> por el id real.

-- Módulos: estado de instancia, runtime conectado y si tienen meta
SELECT id, version, status, base_url IS NOT NULL AS connected, meta IS NOT NULL AS has_meta, updated_at
FROM core.modules ORDER BY id;

-- Estado por organización
SELECT o.name, om.module_id, om.status, om.enabled_at
FROM core.org_modules om JOIN core.organizations o ON o.id = om.org_id
ORDER BY o.name, om.module_id;

-- Migraciones aplicadas vs. fuentes registradas (detecta pendientes)
SELECT s.module_id, s.version, m.applied_at
FROM core.module_migration_sources s
LEFT JOIN core.module_migrations m USING (module_id, version)
ORDER BY s.module_id, s.version;

-- Deliveries pendientes o fallidas (las failed ya no se reintentan solas)
SELECT e.event_type, e.org_id, d.module_id, d.status, d.attempts, d.next_retry_at
FROM core.event_deliveries d JOIN core.events e ON e.id = d.event_id
WHERE d.status IN ('pending', 'failed')
ORDER BY d.next_retry_at LIMIT 50;

-- Cron vencidos que el scheduler aún no reclamó, y jobs en error
SELECT module_id, name, org_id, attempts, last_status, next_run_at
FROM core.cron_runs
WHERE next_run_at < now() - interval '1 minute' OR last_status = 'error'
ORDER BY next_run_at;
-- Permisos efectivos por rol de una organización
SELECT r.name AS role, p.key AS permission
FROM core.roles r
JOIN core.role_permissions rp ON rp.role_id = r.id
JOIN core.permissions p ON p.id = rp.permission_id
WHERE r.org_id = '<uuid-org>' ORDER BY r.name, p.key;

-- Uso de almacenamiento por organización (medida real de cuota: blobs tras dedup)
SELECT o.name,
       pg_size_pretty(COALESCE(SUM(b.size_bytes), 0)) AS used,
       COUNT(*) FILTER (WHERE b.refcount > 0) AS blobs
FROM core.organizations o LEFT JOIN core.attachment_blobs b ON b.org_id = o.id
GROUP BY o.name ORDER BY SUM(b.size_bytes) DESC NULLS LAST;

-- Adjuntos vivos por módulo/modelo de una org
SELECT module_id, model, COUNT(*) AS files, pg_size_pretty(SUM(size_bytes)) AS logical_size
FROM core.attachments
WHERE org_id = '<uuid-org>' AND deleted_at IS NULL
GROUP BY module_id, model ORDER BY files DESC;

-- Notificaciones sin leer por usuario
SELECT u.email, COUNT(*) AS unread, MIN(n.created_at) AS oldest
FROM core.notifications n JOIN core.users u ON u.id = n.user_id
WHERE n.read_at IS NULL AND n.org_id = '<uuid-org>'
GROUP BY u.email ORDER BY unread DESC;

-- Campos personalizados vivos de una org
SELECT module_id, model, name, field_type, required, active, position
FROM core.custom_fields
WHERE org_id = '<uuid-org>' AND deleted_at IS NULL
ORDER BY module_id, model, position;

-- Extensiones registradas: quién extiende qué
SELECT extender_id, target_module, target_model,
       jsonb_array_length(fields) AS fields, jsonb_array_length(ui) AS ui_sections
FROM core.model_extensions ORDER BY target_module, target_model, extender_id;

-- Actividades vencidas abiertas
SELECT module_id, model, record_id, summary, due_date, assigned_to
FROM core.activities
WHERE state = 'open' AND due_date < current_date AND org_id = '<uuid-org>'
ORDER BY due_date;

-- Auditoría reciente (auth, RBAC, ciclo de vida)
SELECT action, entity, user_id, detail, occurred_at
FROM core.audit_log
WHERE org_id = '<uuid-org>' OR org_id IS NULL
ORDER BY occurred_at DESC LIMIT 50;

Respaldos

La base contiene identidad, roles, módulos, configuración, eventos y datos de negocio; respaldar un solo esquema casi nunca basta. En producción hay además dos volúmenes: files (adjuntos con backend local) y tokens (tokens de servicio de los módulos: no respaldar es aceptable, borrarlo no). novvus update hace un pg_dump -Fc obligatorio antes de tocar nada y restaura si la verificación falla. El procedimiento manual está en Mantenimiento.

Qué NO hacer

  • No conectes un módulo como superusuario ni como novvus; no des BYPASSRLS a novvus_module.
  • No escribas SQL de módulo contra core ni contra otro mod_*; no ejecutes SQL del kernel sobre mod_* (ni siquiera para limpiar custom).
  • No quites FORCE ROW LEVEL SECURITY ni uses SET en lugar de SET LOCAL.
  • No aceptes org_id del body o la query.
  • No edites una migración aplicada; crea una nueva.
  • No borres filas de audit_log o events desde aplicación; no toques attachment_blobs.refcount a mano.
  • No cambies name o field_type de un campo personalizado con datos: crea uno nuevo.

Checklist para cambios de datos
