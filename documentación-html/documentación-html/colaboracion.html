Adjuntos, chatter y notificaciones

Nivel medio

Tres servicios que el kernel presta a todos los registros de todos los módulos: archivos adjuntos, un hilo de colaboración por registro (comentarios, notas internas, seguidores, actividades, cambios rastreados) y un buzón de notificaciones con entrega en vivo por SSE. Tu módulo solo declara dos banderas; el resto es infraestructura.

Lo que tienes que hacer como autor de módulo. Poner "attachments": True y/o "chatter": True en __novvus_views__, y opcionalmente "track": [...]. Nada más: ni tablas, ni endpoints, ni UI. El resto de esta página explica qué pasa por debajo para que sepas qué esperar y cómo usarlo desde tu código Python cuando lo necesites.

1. Adjuntos (servicio de archivos)

Contrato normativo: documents/docs/FILES.md. Implementación: crate novvus-files y kernel/crates/novvus-gateway/src/routes/files.rs.

Navegador ── multipart ──► Gateway (novvus-files)
                              │ 1. permiso {módulo}.{modelo}.write (RBAC)
                              │ 2. módulo habilitado y modelo presente en su meta
                              │ 3. streaming: sha256 + tamaño al vuelo, cuota de la org
                              │ 4. MIME por sniffing de los primeros 512 bytes
                              ▼
                       object_store (local o S3-compatible)
                         clave: org/{org_id}/{ab}/{cd}/{sha256}
                              │
                              ▼
                       core.attachments        (un registro por adjunto, borrado lógico)
                       core.attachment_blobs   (org_id, sha256, refcount)

Modelo de datos y deduplicación

TablaContenido
core.attachmentsid UUIDv7, org_id, module_id, model (resource del meta), record_id (sin FK: el registro vive en mod_*), filename, mime (detectado, no confiado), size_bytes, sha256, created_by, created_at, deleted_at. Índices attachments_record_idx (parcial sobre vivos) y attachments_sha_idx.
core.attachment_blobsPK (org_id, sha256), size_bytes, refcount. Es el contenido físico compartido: el mismo PDF subido diez veces en una organización ocupa el almacenamiento una vez. La dedup es por organización: dos orgs con el mismo archivo tienen dos blobs, así la cuota es justa y nadie infiere la existencia de un archivo ajeno.

Límites, MIME y descarga

ReglaValor / comportamiento
Tamaño por archivoNOVVUS_FILES_MAX_SIZE_BYTES, default 50 MB → 413 al excederlo.
Cuota por organizaciónNOVVUS_FILES_ORG_QUOTA_BYTES, default 10 GB → 413 con mensaje claro.
BackendNOVVUS_FILES_BACKEND=local|s3; local en NOVVUS_FILES_LOCAL_ROOT (volumen files en producción), S3-compatible con NOVVUS_FILES_S3_*.
Tipo MIMESniffing de magic numbers (SNIFF_BYTES = 512); el Content-Type del cliente es solo informativo. Denylist application/x-msdownload, application/x-elf → 422.
DescargaSiempre Content-Disposition: attachment, salvo imágenes raster verificadas (INLINE_MIMES: png, jpeg, gif, webp), que pueden ir inline. HTML o SVG jamás se sirven inline (XSS).
MiniaturasDel lado del cliente: el panel descarga la imagen (ya segura) y la muestra pequeña. No hay /thumb en el servidor: decodificar imágenes no confiables dentro del kernel sería superficie de ataque.
Borrado y GCDELETE es lógico. Un job horario del kernel (novvus-gateway/src/main.rs) borra las filas con deleted_at anterior a la retención (NOVVUS_FILES_GC_RETENTION_DAYS, default 30), decrementa el refcount y elimina el objeto físico cuando llega a 0.
AislamientoUn id de otra organización responde 404, nunca 403: no se filtra existencia.

  -H "Authorization: Bearer $ACCESS"

Desde el SDK: module.files

FilesHelper (sdk/src/novvus_sdk/files.py) envuelve las mismas rutas del kernel con el token de servicio y la org del contexto. Un módulo solo puede manejar adjuntos de sus propios modelos y jamás toca el almacenamiento directamente. En modo offline (tests) lanza RuntimeError.

from novvus_sdk import current_context, requires

@module.router.post("/opportunities/{opportunity_id}/quote", status_code=201)
@requires("crm.opportunities.write")
async def generate_quote(opportunity_id: UUID, session: SessionDep) -> dict:
    pdf_bytes = render_quote_pdf(...)               # tu lógica
    attachment = await module.files.attach(
        model="opportunities", record_id=opportunity_id,
        filename="cotizacion.pdf", content=pdf_bytes,
    )
    listed = await module.files.list(model="opportunities", record_id=opportunity_id)
    # module.files.download(attachment_id) y module.files.delete(attachment_id) completan la API
    return {"attachment_id": attachment["id"], "total": len(listed)}

Los cuatro métodos aceptan org_id= opcional para usarlos fuera de una petición de usuario (por ejemplo dentro de un handler de evento o cron, donde el contexto lo pone el kernel).

Qué ve el usuario

<AttachmentPanel moduleId model recordId> (components/generic/attachment-panel.tsx) se monta solo en GenericFormView cuando el meta dice capabilities.attachments y el registro ya existe. Ofrece zona de arrastre con barra de progreso (la subida usa XMLHttpRequest para tener eventos de progreso reales), icono por tipo, miniatura para imágenes, tamaño y fecha, descarga y borrado con confirmación. Está exportado para que lo uses en tus páginas a medida.

2. Chatter (colaboración sobre registros)

Contrato: documents/docs/CHATTER.md. Implementación: routes/chatter.rs. Es el equivalente de mail.thread de Odoo, pero con cuatro tablas separadas en core y sin que el módulo escriba una línea.

Shell <ChatterPanel/>         Gateway (kernel)                     Postgres
   │ GET/POST /api/core/chatter/…  │                                  │
   ├──────────────────────────────►│ permiso read del modelo padre    │
   │                               │ (resuelto vía meta, como files)  │
   │                               │ INSERT message ─────────────────►│ core.messages
   │                               │ fan-out síncrono (misma tx) ────►│ core.notifications
   │                               │ pg_notify('novvus_notify', …)    │
   │  GET /api/core/stream (SSE) ◄─┤ LISTEN compartido, filtra por    │
   │◄── evento "notification" ─────┤ org y usuario destinatario       │

Las cuatro tablas

TablaQué guarda
core.messagesHilo por registro (org_id, module_id, model, record_id). kind ∈ comment (visible a quien lee el registro) · note (interna) · system (cambio de campo rastreado o mensaje programático, con meta = {field, old, new}). author_id NULL = sistema/módulo. Adjuntos por ids. Edición solo del autor durante 15 minutos (NOVVUS_CHATTER_EDIT_WINDOW_MINUTES); borrado lógico.
core.followersPK (org, module, model, record, user). Auto-follow: quien comenta se suscribe.
core.activitiesPendientes con dueño: activity_type ∈ call | meeting | email | todo, summary, due_date, assigned_to, state ∈ open | done | canceled, done_by/done_at, note.
core.notificationsBuzón por usuario: kind ∈ mention | follower_message | activity_due | activity_assigned, payload (módulo, modelo, registro, id de mensaje, actor, extracto), read_at.

Diferencia con core.audit_log: el audit log registra acciones administrativas del kernel (login, habilitar módulos, roles) y es append-only; el chatter registra conversación y cambios de negocio que el módulo declaró con track. Nunca se copian entradas de un plano al otro.

Permisos, menciones y fan-out

1
Permiso heredado. Leer el hilo, comentar, seguir y listar actividades exigen el permiso read del modelo padre, que el kernel resuelve desde el meta del módulo (igual que los adjuntos). Editar o borrar un mensaje: solo el autor. Cerrar una actividad: el asignado o quien tenga write.
2
Menciones. Viajan en el cuerpo como @[user_id] (parse_mentions, chatter.rs:32). El kernel valida que cada usuario es miembro de la org y genera una notificación mention por usuario, sin duplicados. El compositor de la shell inserta @[uuid] (Nombre) para que la persona vea a quién mencionó.
3
Fan-out síncrono. En la misma transacción del INSERT del mensaje se insertan notificaciones follower_message para cada seguidor (menos el autor y los ya mencionados) y se emite pg_notify('novvus_notify', …). No pasa por el bus de eventos de módulos: ese bus exige un emisor con emits declarados y el chatter es plano del kernel.
4
Actividades vencidas. La pasada horaria del kernel (notify_due_activities) crea activity_due para actividades open con due_date pasada, una vez al día por actividad.

Tracking de campos y mensajes programáticos desde el SDK

Dos mecanismos, ambos en sdk/src/novvus_sdk/chatter.py (ChatterHelper), ambos best-effort: una caída del chatter nunca rompe la operación de negocio (se registra un warning y se devuelve None).

# 1) Tracking declarativo: la auto-API compara antes/después en cada PATCH
class Opportunity(NovvusModel):
    ...
    __novvus_views__ = {"label": "Oportunidades", "chatter": True, "track": ["amount", "stage_id"]}
# → por cada campo track que cambie, un mensaje system con body "amount: '1000' → '1500'"
#   y meta {"field": "amount", "old": "1000", "new": "1500"}   (autoapi.py:536-548)

# 2) Mensaje programático desde tu lógica de negocio
await module.chatter.post(
    model="opportunities", record_id=opportunity.id,
    body=module._("Cotización enviada al cliente"),
    meta={"quote_id": str(quote.id)},     # kind="system" por defecto
)
Solo en la auto-API. El tracking automático lo hace update_item de autoapi.py. Si cambias un campo rastreado desde un endpoint custom (por ejemplo /opportunities/{id}/move del CRM), publica tú el mensaje con module.chatter.post o llama a module.chatter.track_changes(resource, record_id, [(campo, viejo, nuevo)]).

Qué ve el usuario

<ChatterPanel moduleId model recordId> (components/generic/chatter-panel.tsx) aparece bajo el formulario cuando capabilities.chatter es verdadero: cabecera con contador de seguidores y botón Seguir / Dejar de seguir; filtros Todo · Conversación · Cambios; compositor con botón @ Mencionar (lista de miembros de la org) y casilla "Nota interna" (fondo ámbar); planificador de actividades (tipo, resumen, fecha; las vencidas en rojo; botón ✓ para cerrarlas); línea de tiempo donde los mensajes system se ven punteados con la etiqueta "sistema". El cuerpo se renderiza como texto plano (el render markdown sanitizado está en BACKLOG; nunca HTML crudo). El hilo se refresca cada 30 s como respaldo del SSE.

3. Notificaciones y tiempo real

El buzón

RutaEfecto
GET /api/core/notifications?unread=1&cursor={items, next_cursor, unread_count} del usuario autenticado.
POST /api/core/notifications/read {ids}Marca leídas.
POST /api/core/notifications/read-allMarca todo leído.

Retención: las notificaciones leídas con más de 90 días se purgan en la pasada horaria del kernel (main.rs:60-73). Las no leídas se conservan.

SSE: GET /api/core/stream?token=

1
Autenticación por query param. EventSource no puede enviar cabeceras, así que el JWT de acceso viaja en ?token= y se valida exactamente igual que un Bearer (routes/stream.rs:33). Es el mismo token corto de 15 minutos: al rotar, la shell reabre la conexión.
2
Un LISTEN por proceso. El gateway mantiene una única conexión LISTEN novvus_notify (spawn_notify_listener) y reparte en memoria a las conexiones SSE cuyo org_id y user_id coincidan con el payload {org_id, user_ids, kind, …}.
3
Heartbeat y reconexión. : ping cada 25 s mantiene vivo el canal a través de proxies; el navegador reconecta solo. Un receptor rezagado simplemente pierde avisos y se reconcilia por polling.
4
Fallback. La campana consulta /api/core/notifications cada 60 s aunque el SSE funcione (notifications-bell.tsx:44), y el hilo del chatter cada 30 s. Si el SSE cae, nada deja de funcionar: solo tarda más.
# Observar el stream desde la terminal (el token es el access JWT)
curl -N "http://localhost:8000/api/core/stream?token=$ACCESS"
: ping
event: notification
data: {"org_id":"…","user_ids":["…"],"kind":"notification","payload":{…}}

En la shell, subscribeNotifications() (lib/chatter.ts:121) mantiene un EventSource singleton compartido por todos los suscriptores, que solo se reemplaza cuando cambia el token de acceso, y escucha el evento notification. NotificationsBell invalida la consulta del buzón al recibirlo; al hacer clic en una notificación la marca leída y navega a /m/{module_id}/{model}/{record_id}.

Un detalle de implementación. El contrato prevé también eventos chatter para refrescar hilos abiertos; el kernel reenvía el kind que llegue por pg_notify, pero en v0.1.6 la shell solo se suscribe a notification y refresca los hilos por polling.

Qué ve el usuario

Una campana en la barra superior (tanto en la shell de plataforma como dentro de cada ModuleShell) con el contador de no leídas (9+ a partir de diez), un panel con las diez más recientes y etiquetas humanas por tipo: "Te mencionaron", "Nuevo mensaje", "Actividad vencida", "Actividad asignada". Enlace "Marcar todo leído".

Resumen: cómo se conectan las tres piezas

Quiero…Hago…
Que un modelo acepte archivos"attachments": True en __novvus_views__. El panel aparece en el formulario genérico y en cualquier página donde montes AttachmentPanel.
Adjuntar desde códigoawait module.files.attach(model, record_id, filename, content).
Conversación en un registro"chatter": True. Comentarios, notas, seguidores y actividades vienen de serie.
Que los cambios de etapa/importe queden en el hilo"track": ["stage_id", "amount"] (auto-API) o module.chatter.post() en endpoints custom.
Avisar a alguienMencionarlo con @[uuid] en un mensaje o asignarle una actividad: el kernel crea la notificación y la empuja por SSE.
Reaccionar desde otro módulo a un comentarioNo es posible por diseño: el chatter no emite eventos al bus de módulos. Usa los eventos de negocio (emits) del módulo dueño.
Ver más: fuera de alcance en v0.1.6

Antivirus, versionado de archivos, URLs presignadas públicas, vista previa de PDF/Office, correo saliente/entrante como canal del chatter, mensajes directos y canales, reacciones, hilos anidados, web push, purga dura de mensajes borrados y limpieza automática de adjuntos huérfanos al borrar el registro padre.
