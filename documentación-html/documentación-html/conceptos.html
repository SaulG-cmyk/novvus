Conceptos en 10 minutos

Nivel básico

El vocabulario mínimo para entender el resto de la documentación, explicado con analogías y sin suponer que conoces Rust, Python o bases de datos. Léelo una vez de corrido; el glosario del final te sirve después como chuleta.

El edificio: una analogía para todo lo demás

Imagina Novvus Core como un edificio de oficinas. El edificio tiene una recepción con un portero, un directorio de empresas, un sistema de correo interno y un almacén compartido. Cada empresa renta un piso y decide qué departamentos abre. Con esa imagen en la cabeza, cada concepto de abajo cae en su lugar.

                 EDIFICIO (la instalación de Novvus Core)
 ┌──────────────────────────────────────────────────────────────────┐
 │  Recepción / portero ........ kernel (autenticación, permisos)    │
 │  Directorio de empresas ..... organizaciones (tenants)            │
 │  Correo interno ............. bus de eventos                      │
 │  Almacén compartido ......... PostgreSQL (una sola base)          │
 │                                                                  │
 │  Piso 3: «Acme S.A.»   → tiene CRM y Proyectos                    │
 │  Piso 5: «Bravo S.C.»  → tiene solo CRM + Ventas México           │
 │                                                                  │
 │  Departamentos disponibles = módulos (apps) publicados            │
 └──────────────────────────────────────────────────────────────────┘

Organización (tenant)

Una organización es una empresa que usa la plataforma: «Acme S.A.» o «Bravo S.C.». Todos los datos de negocio (contactos, oportunidades, proyectos, archivos, conversaciones) pertenecen a una organización y son invisibles para las demás, aunque vivan en la misma base de datos. En jerga técnica a esto se le llama tenant («inquilino») y a la plataforma, multi-tenant.

Un mismo usuario puede pertenecer a varias organizaciones (como un contador que trabaja para dos empresas) y cambia entre ellas desde el menú de organización. Quien crea una organización recibe automáticamente el rol Owner, que lo puede todo dentro de ella.

Usuario, rol y permiso

Un usuario es una persona con correo y contraseña. Un rol es un gafete («Ventas», «Gerente de ventas») que agrupa permisos y se asigna a los miembros de una organización. Un permiso es una llave concreta con un nombre de tres partes:

{modulo}.{recurso}.{accion}

crm.contacts.read        # ver contactos del CRM
crm.opportunities.write  # crear, editar y mover oportunidades
crm.reports.read         # ver reportes del CRM
core.members.manage      # administrar miembros de la organización (kernel)
core.custom_fields.manage# crear campos personalizados

Los permisos los declara cada módulo en su manifiesto y los otorga el administrador a los roles. La interfaz oculta lo que no puedes hacer, pero la restricción real vive en el servidor: si intentas algo sin permiso recibes un 403. El rol Owner equivale al permiso comodín *.

Módulo (= una app de negocio)

Un módulo es una aplicación completa: el CRM, Proyectos, Ventas México. Es un programa en Python, en su propia carpeta, con tres piezas:

  • Un manifiesto novvus.toml: la ficha de identidad del módulo (id, nombre, versión, permisos que declara, eventos que emite y escucha, menú, configuración…). Es la única fuente de verdad sobre qué hace el módulo.
  • Modelos: las «tablas» del negocio (empresas, contactos, oportunidades) escritas como clases de Python.
  • Una API: rutas HTTP para leer y escribir esos modelos. La mayoría la genera el SDK automáticamente; el módulo solo añade las reglas de negocio especiales (por ejemplo «convertir un lead»).

Los módulos se instalan en el edificio una vez (nivel instancia) y después cada organización decide si los habilita en su piso (nivel organización), desde la tienda de aplicaciones. Un módulo puede depender de otro: Proyectos requiere CRM.

Kernel: el portero, el registro y el correo

El kernel es el programa central, escrito en Rust. Hace tres trabajos y no hace nada de negocio:

  • Portero: recibe todas las peticiones del navegador, verifica quién eres (autenticación) y qué puedes hacer (permisos), y solo entonces reenvía la petición al módulo correspondiente. Un módulo nunca está expuesto directamente a internet.
  • Registro: sabe qué módulos existen, en qué versión, qué permisos declaran, qué organizaciones los tienen habilitados y cómo se ven sus modelos (los metadatos). Aplica las migraciones de base de datos de cada módulo.
  • Correo interno (bus de eventos): cuando un módulo anuncia «se ganó una oportunidad», el kernel entrega ese aviso a los módulos suscritos, aunque estén momentáneamente apagados (lo reintenta).

Además presta servicios comunes que ningún módulo tiene que reinventar: archivos adjuntos, conversaciones (chatter), notificaciones, campos personalizados y configuración por organización.

SDK: la librería que hace el trabajo pesado

novvus-sdk es la librería de Python con la que se escriben los módulos. Tú declaras; ella ejecuta. A partir de una clase de modelo genera la API de lista, creación, lectura, edición, borrado, agrupación y exportación; aplica el aislamiento por organización en cada consulta; se presenta ante el kernel al arrancar (el handshake) y recibe los eventos. Sin el SDK, cada módulo tendría que reimplementar todo eso y, tarde o temprano, se equivocaría en seguridad.

Esquemas: core y mod_{id}

Toda la plataforma usa una sola base PostgreSQL, ordenada en «carpetas» llamadas esquemas. El esquema core pertenece al kernel (usuarios, organizaciones, roles, módulos, eventos, adjuntos, mensajes…). Cada módulo recibe su propio esquema mod_{id} (mod_crm, mod_projects) y solo puede tocar el suyo: el usuario de base de datos de los módulos no tiene permiso sobre core ni sobre el esquema de otro módulo. Toda tabla de negocio lleva una columna org_id que dice a qué organización pertenece la fila.

RLS en una frase

Row-Level Security. Es una regla de PostgreSQL que hace que cada consulta de un módulo solo vea las filas de la organización activa, y que si por error no se indica la organización, la consulta no devuelva nada en lugar de devolverlo todo («fail-closed»). El aislamiento entre inquilinos lo garantiza la base, no el código de cada programador.

Manifiesto novvus.toml

Es un archivo de texto sencillo, en formato TOML, con secciones. Un fragmento real del CRM:

[module]
id = "crm"
name = "CRM"
version = "0.1.0"

[[permissions]]
key = "crm.leads.write"
description = "Crear, editar y convertir leads"

[events]
emits = ["crm.lead.created", "crm.opportunity.won"]
listens = []

[runtime]
port = 8110

[[ui.nav]]
path = "/crm/leads"
label = "Leads"
icon = "user-plus"

El kernel lee este archivo al registrar el módulo y a partir de él crea los permisos, valida los eventos, pinta el menú de la app y sabe qué dependencias exigir. Otras secciones que verás más adelante: [presentation] (ficha en la tienda), [[config]] (ajustes por organización), [[cron]] (tareas programadas) y [extensions].

Token de servicio

Cuando un módulo se instala, el kernel le entrega una credencial secreta de una sola vista, el token de servicio (NOVVUS_SERVICE_TOKEN, empieza por nvk_). Es la «llave del empleado» con la que el módulo se identifica ante el kernel al arrancar y al publicar eventos. Se guarda en variables de entorno o en un volumen de Docker; nunca en el código. Si lo pierdes, se vuelve a desplegar el módulo. No lo confundas con el token de bootstrap (NOVVUS_BOOTSTRAP_TOKEN), un secreto de plataforma que solo usa el instalador para registrar módulos antes de que exista cualquier usuario.

Vistas genéricas: interfaz gratis desde metadatos

Un módulo describe sus modelos con un pequeño diccionario __novvus_views__: etiquetas en español, columnas de la lista, distribución del formulario, por qué campo agrupar el kanban, qué fecha usar en el calendario. Ese meta viaja al kernel en el handshake, el kernel lo guarda y lo entrega al navegador ya filtrado por permisos. Con eso, el frontend pinta solo la ruta /m/{modulo}/{modelo} con lista (búsqueda, filtros, orden, exportación CSV/XLSX), formulario, kanban y calendario. Nadie escribió una pantalla para «Contactos» del CRM: es una vista genérica.

Eventos entre módulos

Un evento es un aviso con nombre {modulo}.{entidad}.{accion}, por ejemplo crm.opportunity.won. El CRM lo emite cuando ganas una oportunidad; Proyectos lo escucha y crea un proyecto con tareas iniciales. Ninguno conoce al otro: solo conocen el nombre del evento y el contenido del mensaje. Las entregas son «al menos una vez», así que el módulo receptor ignora duplicados con ayuda del SDK.

Extensiones

Una extensión permite que un módulo aporte campos y trozos de formulario a los modelos de otro módulo sin tocar su código ni su esquema. El caso real: Ventas México (salesmx) añade «RFC» y «Régimen fiscal» a los contactos del CRM. Los valores se guardan en la columna ext de la tabla base y solo aparecen en las organizaciones que habilitaron el módulo extensor.

Campos personalizados

Un administrador puede agregar campos a un modelo desde la interfaz, sin programar y sin cambiar la base de datos: «Número de contrato» en oportunidades, «Zona» en empresas. Cada organización tiene los suyos. Se guardan en la columna custom y aparecen en el formulario bajo «Información adicional» y como filtros en la lista.

Chatter, adjuntos y notificaciones

Cualquier registro (un contacto, una oportunidad, un proyecto) puede tener una conversación al pie: comentarios visibles, notas internas, menciones con @, seguidores que reciben avisos, actividades planificadas (llamada, reunión, correo, tarea) y un historial automático de cambios de campos importantes. Junto a ella, un panel de adjuntos para subir archivos. Las menciones, las actividades y los mensajes a seguidores generan notificaciones que llegan en tiempo real a la campana de la interfaz. Todo esto lo provee el kernel: el módulo solo declara chatter = True y attachments = True en el meta del modelo.

Dos CLI que se llaman igual

Ojo con el nombre novvus. Hay dos herramientas de línea de comandos con el mismo nombre y no se parecen en nada:
  • El CLI administrativo (Rust, carpeta cli/): vive en el servidor del cliente. Comandos: sudo novvus install, sudo novvus update, novvus status, novvus version.
  • El CLI del SDK (Python, viene con novvus-sdk): vive en tu máquina de desarrollo y dentro de los contenedores de los módulos. Comandos: novvus new-module, novvus makemigration, novvus deploy, novvus run, novvus seed.
En un servidor de producción no se instala el SDK, así que nunca coexisten. Cuando esta documentación diga «CLI» sin más, mira en qué contexto está: servidor o desarrollo.

Cómo viaja una petición

Cuando un usuario abre la lista de contactos, esto es lo que pasa, de izquierda a derecha:

 Navegador            Web (Next.js)          Kernel (gateway)            Módulo CRM            PostgreSQL
 ─────────            ─────────────          ────────────────            ──────────            ──────────
 GET /api/crm/contacts ──► proxy same-origin ──► 1. valida el JWT
 (con tu token JWT)        /api/* → kernel       2. resuelve permisos
                                                 3. ¿crm habilitado en
                                                    tu organización?
                                                 4. firma headers
                                                    X-Novvus-* (HMAC) ──► 5. verifica la firma
                                                                          6. SET LOCAL app.org_id
                                                                          7. SELECT … ──────────► RLS filtra:
                                                                                                  solo filas de
                                                                          ◄─── filas ─────────── tu organización
 ◄──────────────────────── JSON ◄──────────────── respuesta ◄────────────  8. responde JSON

Tres cosas para recordar: el navegador solo habla con la web (en producción el kernel ni siquiera tiene puerto público); el módulo nunca ve tu contraseña ni tu JWT, solo headers firmados por el kernel; y la base de datos filtra por organización aunque el módulo lo olvidara.

Cómo viaja un evento

 CRM: «oportunidad ganada»                Kernel (bus)                         Proyectos
 ───────────────────────────              ────────────                         ─────────
 POST /api/core/events ───────────────►  guarda en core.events
   crm.opportunity.won                    crea una entrega por suscriptor
   payload {opportunity_id, …}            NOTIFY + barrido cada 5 s ─────────► POST /_novvus/events
                                                                               ¿ya lo procesé? no →
                                                                               crea proyecto + 3 tareas
                                          marca entrega OK ◄────────────────── 200 OK
