Contribuir y calidad

Nivel medio

Las reglas del juego para trabajar en el repositorio: contratos antes que código, convenciones de nombres y de idioma, cómo correr cada una de las suites, qué bloquea el CI, dónde están las trampas del entorno, cómo se propone un módulo nuevo y cómo se publica una versión.

La regla de oro: contratos primero

Los 19 documentos de documents/docs/ son la ley del proyecto (índice completo en Referencia técnica). Si tu cambio toca un contrato — un endpoint del kernel, una sección del manifiesto, una tabla de core, una garantía del bus, una regla del meta — edita primero el documento y después el código. Las decisiones que no ameritan contrato se anotan en una línea con fecha en DECISIONS.md (AAAA-MM-DD — [área] decisión — motivo); lo que pertenece al futuro va a BACKLOG.md y no se implementa hasta su fase.

No adelantes fases ni «mejores» el stack. Rust/axum/sqlx, FastAPI/Pydantic v2/SQLAlchemy 2, Postgres 16 y Next.js son fijos. Si detectas que algo se necesitará más adelante, documéntalo en BACKLOG.md y sigue. Un umbral de CI puede subirse editando el número; bajarlo exige una entrada en DECISIONS.md.
La carpeta documents/ está gitignorada. Los contratos y esta documentación HTML viven en local; el README.md del repo todavía enlaza docs/*.md (enlaces rotos conocidos).

Flujo de trabajo

1
Rama desde main. Commits pequeños con prefijo convencional: feat:, fix:, docs:, test:, chore:.
2
Contrato → código → tests. Nada se considera terminado sin tests que pasen; si un módulo necesita algo del SDK, se hace en el SDK con sus tests, nunca como parche dentro del módulo.
3
Corre localmente la suite que tocaste (abajo) y make lint. Recuerda que next build ya no ejecuta ESLint.
4
PR hacia main; los 8 jobs del CI deben quedar en verde. Un PR no se mezcla con CI rojo.

Convenciones

Idioma

  • Código, identificadores y comentarios en inglés. Comenta solo lo que el código no puede decir: restricciones, decisiones de contrato, porqués — nunca «qué hace la siguiente línea».
  • UI, textos de negocio, catálogos i18n y documentación en español. El idioma fuente es es-MX: la cadena en español es la clave de traducción; jamás claves artificiales tipo page.title. Los labels de campos personalizados son dato del usuario y no pasan por i18n.

Nombres (los valida el kernel y el SDK)

CosaFormaRegla
Id de módulo^[a-z][a-z0-9_]{1,31}$Reservados: core, api, internal, novvus. Define esquema mod_{id} y namespace /api/{id}.
Permiso{módulo}.{recurso}.{acción}Solo dentro del propio namespace. Los requisitos son concretos; los otorgamientos pueden usar comodines. Owner = *.
Evento{módulo}.{entidad}.{acción}emits solo del propio namespace; listens de cualquiera. Emitir algo no declarado es error.

Campo de extensión^[a-z][a-z0-9_]{0,63}$Máx. 32 campos por extensor y 16 extensores por modelo; el target debe estar en [dependencies] modules.
Campo personalizado^[a-z][a-z0-9_]{0,29}$name y type inmutables; 50 por modelo por defecto.
Ruta de [ui]/{id} o /{id}/…Nunca hacia otro módulo, la shell ni /m/…; iconos como slug [a-z0-9-].

Frontend

  • Next.js 16 no es el que conoces. Antes de escribir código lee la guía correspondiente en apps/web/node_modules/next/dist/docs/ (es la instrucción de apps/web/AGENTS.md) y respeta los avisos de deprecación.
  • Los componentes shadcn están construidos sobre Base UI: los triggers usan render={…}, no asChild.
  • La shell de plataforma es solo administrador de módulos (launcher, /apps, /settings, /admin). Toda UI de negocio vive bajo el chrome del módulo (ModuleShell) o en las vistas genéricas /m/{módulo}/{modelo}; el manifiesto gana sobre MODULE_REGISTRY, que es solo respaldo offline.
  • Lint con eslint src (ESLint 9 + eslint-config-next); tests con Vitest 4 + Testing Library en jsdom; E2E con Playwright.

Python y Rust

  • ruff con line-length = 100, reglas E F I UP B SIM RUF (se ignora B008 por Depends()); mypy estricto con el plugin de Pydantic sobre src/novvus_sdk.
  • autoapi.py no puede usar from __future__ import annotations: FastAPI necesita evaluar los esquemas Pydantic generados dinámicamente.
  • Rust: cargo fmt --check y clippy --all-targets -- -D warnings con cero tolerancia, en kernel/ y en cli/.

Preparar el entorno de desarrollo

Requisitos: Docker con Compose v2, Rust stable (cargo), Python ≥ 3.12 y Node 22. El flujo manual completo (equivalente a lo que automatiza start.bat en Windows):

cp .env.example .env                       # secretos de desarrollo; nunca los uses en producción
make up                                    # solo Postgres 16 (docker-compose.yml)
cd kernel && cargo run -p novvus-gateway    # :8000 — aplica sus migraciones core al arrancar

pip install -e "sdk[dev]"                  # trae el CLI `novvus` del SDK
cd modules/crm
novvus deploy --kernel http://127.0.0.1:8000 --token <JWT con core.modules.manage>
# → imprime NOVVUS_SERVICE_TOKEN=nvk_... UNA sola vez: guárdalo en modules/crm/.env
NOVVUS_SERVICE_TOKEN=nvk_... novvus run --port 8110
# projects igual, en 8120 (depende de crm habilitado)

cd apps/web && npm install && npm run dev   # :3000, rewrite /api → NOVVUS_KERNEL_URL

Atajos: make demo levanta todo en contenedores con datos de demostración (demo@novvus.dev), y python scripts/bootstrap.py con NOVVUS_DEMO=1 aprovisiona usuario, organización, roles, módulos y seed contra un kernel ya corriendo — exactamente lo que hace el job e2e. off.bat apaga todo en Windows.

Correr cada suite

Los tests de integración usan el Postgres de make up (DATABASE_URL con fallback a la BD dev) y crean bases efímeras por test que se destruyen al terminar: nunca ensucian tus datos. En Windows, sustituye python por sdk/.venv/Scripts/python.

# Kernel (Rust) — requiere Postgres arriba
cd kernel && cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings && cargo fmt --check

# SDK (Python)
pip install -e "sdk[dev]"                                   # una vez
cd sdk && python -m pytest -q --cov=novvus_sdk
python -m ruff check . ../modules/crm ../modules/projects ../modules/salesmx && python -m mypy

# Módulos: arnés con BD efímera + app en modo offline + peticiones firmadas como el gateway
cd modules/crm      && python -m pytest -q --cov=.
cd modules/projects && python -m pytest -q --cov=.
cd modules/salesmx  && python -m pytest -q                # módulo sin modelos: sin cobertura

# Web (Next.js 16)
cd apps/web && npm ci
npm run lint              # eslint src — OBLIGATORIO: next build NO corre ESLint
npm test                  # vitest run (npm run test:coverage para cobertura)
npm run build             # incluye chequeo de tipos
npm run test:e2e          # playwright test; exige el stack completo corriendo

# CLI administrativo (Rust)
cd cli && cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test && cargo build --release

# Instalador del CLI (bash): shellcheck sigue el `source` de los tests
shellcheck -x distribution/install.sh distribution/tests/run.sh
bash distribution/tests/run.sh   # servidor HTTP local + árbol de distribución falso; cero requests reales

Anatomía del arnés de tests de un módulo

El patrón canónico está en modules/projects/tests/conftest.py (y en modules/salesmx/tests/ para módulos sin modelos). Tres piezas:

  1. Base efímera por sesión. Con el DSN admin (DATABASE_URL) crea novvus_projects_test_<hex>, la prepara con el rol novvus_module (NOVVUS_MODULE_DB_PASSWORD) y la destruye al terminar. Si Postgres no está, pytest.skip: la suite nunca falla por infraestructura ausente.
  2. App en modo offline. El módulo arranca con NOVVUS_DATABASE_URL + NOVVUS_INTERNAL_HMAC_SECRET fijos por el test, sin kernel: los module.emit se registran con warning y module.call lanza RuntimeError; lo que dependa del kernel se simula con monkeypatch (Proyectos parchea dependency_statuses para probar el estado degradado).
  3. Peticiones firmadas como el gateway. Un helper signed_headers(method, path, org, perms, user) que usa novvus_sdk.security.sign con el mismo secreto. Así cada test elige tenant y permisos y se cubren los 401/403 sin tocar el kernel.
# modules/projects/tests/conftest.py (extracto real)
if sys.platform == "win32":
    asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())

FULL_PERMS = "projects.projects.*,projects.tasks.*"

def signed_headers(method, path, org, perms="", user=None):
    from novvus_sdk.security import sign
    timestamp = int(time.time())
    user_str = str(user) if user else ""
    return {
        "x-novvus-user": user_str, "x-novvus-org": str(org), "x-novvus-perms": perms,
        "x-novvus-timestamp": str(timestamp),
        "x-novvus-signature": sign(HMAC_SECRET, user_str, str(org), perms, timestamp, method, path),
    }

# En un test: el mismo registro con otra org debe ser 404 (RLS), sin permiso 403
r = await client.get(f"/api/projects/projects/{pid}",
                     headers=signed_headers("GET", f"/api/projects/projects/{pid}", other_org, FULL_PERMS))
assert r.status_code == 404

Los umbrales de cobertura de cada módulo (crm ≥ 95, projects ≥ 90) se miden con --cov=. sobre el directorio del módulo, de modo que business.py y los handlers de eventos cuentan.

Tests de integración del kernel

kernel/crates/novvus-gateway/tests/ levanta la app real en proceso contra Postgres (tests/common/mod.rs, con timeouts HTTP) y cubre un flujo por archivo: auth_flow, modules_lifecycle, org_modules, module_config, platform_bootstrap, events_flow, automation (cron y hooks), catalog, meta_flow, files_flow, extensions_flow, custom_fields_flow, chatter_flow y sse_flow. Un endpoint nuevo en lib.rs sin su test en esta carpeta no pasa revisión: es lo que mantiene el trinquete del 85 % y lo que cazó el bug del JOIN de org_lifecycle.

Añadir una migración del kernel o un idioma

  • Migración de core: archivo kernel/migrations/00NN_nombre.sql (la siguiente es 0012); sqlx::migrate! la embebe y el gateway la aplica al arrancar. Documenta la tabla en DATA_MODEL.md con la justificación de cada índice, y si añade permisos, insértalos ahí mismo como hace 0010_custom_fields.sql.
  • Migración de módulo: novvus makemigration -m nombre con NOVVUS_DATABASE_URL apuntando a una base donde ya corrió la anterior; revisa el SQL generado (RLS, org_id, ext/custom) antes de commitear.
  • Idioma nuevo: añade el locale a LOCALES y su catálogo a CATALOGS en apps/web/src/lib/i18n.tsx, y un i18n/{locale}.json por módulo. No hay extracción automática: los catálogos se mantienen a mano.

Ver más: el job e2e paso a paso (y cómo reproducirlo en local)
  1. cargo build -p novvus-gateway y arranque en background con NOVVUS_BIND_ADDR=127.0.0.1:8000; espera con curl --retry 60 a /health.
  2. pip install -e sdk y python scripts/bootstrap.py con NOVVUS_DEMO=1, NOVVUS_TOKENS_DIR, NOVVUS_MODULES_DIR y NOVVUS_DATABASE_URL del rol novvus_module (para el seed).
  3. source de crm.env / projects.env (los tokens que escribió el bootstrap) y novvus run --port 8110 / 8120; espera a ambos /health (esto valida también el handshake).
  4. npm ci && npm run build && npm run start; espera a http://localhost:3000/login.
  5. npx playwright install chromium --with-deps y npm run test:e2e (apps/web/e2e/smoke.spec.ts).
  6. En fallo: vuelca gateway.log, crm.log, projects.log, web.log y sube apps/web/test-results/ como artifact.

En local basta con tener el stack arriba (start.bat o el flujo manual de arriba, con datos demo) y ejecutar npm run test:e2e desde apps/web. Si el smoke se volviera inestable, la instrucción del propio workflow es bajarlo a continue-on-error: true documentando el porqué.

Mutation testing

  • Rust: cargo-mutants sobre novvus-registry/src/manifest.rs: 152 mutantes, 117 cazados, 0 vivos, 35 inviables → 100 % de kill rate de los viables (era 74 % antes de 16 kill-tests). La pasada con --test-workspace sobre lifecycle/org_lifecycle/catalog/migrations dejó solo 2 mutantes equivalentes demostrados.
  • Python: mutmut sobre manifest.py, solo en CI Linux (mutmut 3 exige fork).
  • Por qué paga: el kill-test de la iteración 7 encontró que org_lifecycle::view_for concatenaba AND m.id = $2 al ON del LEFT JOIN y, con ≥ 2 módulos, install/enable/disable podía responder la vista de otro módulo (QA.md §5).
Ver más: otros bugs que la auditoría de QA encontró
  • Tras el login SPA, /api/core/me nunca se pedía (query congelada en enabled: false en los providers raíz) y toda nav gateada por permiso se ocultaba hasta recargar. Fix: navegación dura al entrar. Detectado porque el trace de Playwright no mostraba la petición.
  • GET /api/crm/reports/conversion perdía leads nocturnos al oeste de UTC (ventana exclusiva sobre timestamps UTC). Fix: ventana inclusiva. El test solo fallaba después de las 18:00 hora de México: los tests dependientes de la hora del día son sospechosos por diseño.
  • 7 errores de ESLint invisibles porque next build ya no lo corre y npm run lint no apuntaba a src. Ahora el gate vive en CI.

Trampas conocidas del entorno

  • Windows + Rust GNU: el toolchain es stable-x86_64-pc-windows-gnu (sin Visual Studio Build Tools). Si WinLibs está en el PATH, dlltool falla al enlazar; sácalo del PATH para compilar.
  • No quites los opt-level = 3 de argon2, blake2, digest y sha2 en kernel/Cargo.toml: Argon2id de 19 MiB sin optimizar tarda minutos por hash y la suite «se cuelga».
  • psycopg async en Windows no funciona sobre el ProactorEventLoop; novvus run fuerza SelectorEventLoop vía loop_factory y los pytest.ini de los módulos silencian la deprecación de asyncio.set_event_loop_policy hasta que pytest-asyncio exponga loop_factory.
  • Cobertura Rust en Windows GNU: imposible (sin profiler_builtins). Mídela en Linux: CI o docker run rust:1 apuntando a la BD dev por host.docker.internal.
  • mutmut local en Windows: imposible (v3 exige fork; v2 rompe con pony + Python 3.14). Vive solo en CI.
  • Cobertura Python 3.12: el core settrace pierde código dentro de corutinas con pytest-asyncio 1.4 (business.py del CRM «caía» de 95 % a 52 %). Usa COVERAGE_CORE=sysmon como hace el CI.
  • El binario del kernel no se puede recompilar mientras corre: off.bat primero, luego cargo build/cargo test.
  • Tests de kernel que «no terminan»: el arnés de tests/common/mod.rs tiene timeouts HTTP y el CI acota el job a 30 min; si un test se cuelga en local, revisa primero que Postgres esté arriba en :5432 y que no haya otro gateway ocupando el puerto de prueba.
  • Secretos: los valores de .env.example son de desarrollo y públicos; nunca los copies a .env.prod.example ni a un servidor (el compose de producción exige que cada secreto esté definido).
  • novvus run del SDK y novvus del CLI Rust son dos programas homónimos; en tu máquina de desarrollo solo instalas el del SDK.

Proponer un módulo nuevo

Empieza con novvus new-module <id> y la guía BUILDING_MODULES.md. Antes de abrir el PR, verifica el criterio de conformidad de MODULE_CONTRACT.md §12 ampliado con lo que hoy exige el repo:

Versionado y releases

  • Fuente única de la versión de plataforma: el archivo VERSION en la raíz (hoy 0.1.6). kernel/crates/novvus-gateway/build.rs y cli/build.rs lo embeben como NOVVUS_VERSION; /health y novvus version lo reportan.
  • Kernel y SDK llevan semver independiente en CHANGELOG.md (Keep a Changelog, en español); cada módulo declara su propio semver en [module] version. Romper un contrato de módulo (manifiesto, headers internos, auto-API, meta) es major.
  • Las imágenes X.Y.Z y las carpetas versionadas de downloads.novvus.dev son inmutables: nunca se re-publica una versión; latest es el único puntero mutable.
# Secuencia de release
git push origin main                                   # todo mergeado y en verde
echo 0.1.7 > VERSION && git commit -am "Bump version to 0.1.7" && git push
git tag -a v0.1.7 -m "Novvus Core v0.1.7" && git push origin v0.1.7

El tag dispara release.yml: version (falla si el tag ≠ VERSION) → tests (todo ci.yml) → cli-build (binarios estáticos musl para linux-x64 y linux-arm64, este último compilado y ejecutado bajo QEMU) → cli-dist (latest, <v>/manifest.json con SHA-256, binarios, install.sh, verificado con un bootstrap real contra un servidor local) → build-push (imágenes ghcr.io/novvus/{core,web,bootstrap,crm,projects} con tags X.Y.Z y latest) → publish-downloads (Cloudflare R2 con put-object archivo por archivo, nunca sync --delete; verifica checksums en el dominio público y sube latest al final, solo si las imágenes ya existen). Detalle operativo en Actualización y releases.
