Extensiones, campos, config y cron

Nivel medio

Todo lo que un módulo puede hacer más allá de sus propios modelos: aportar campos y secciones a modelos de otros módulos, dejar que cada organización añada campos sin programar, declarar configuración por organización, programar trabajos, reaccionar al ciclo de vida, traducirse, hablar con otros módulos por eventos y distribuirse como paquete firmado.

1. Extensiones entre módulos ([extensions])

Contrato: documents/docs/EXTENSIONS.md. Es el reemplazo del _inherit de Odoo, con un contrato explícito en lugar de monkey-patching: un módulo declara en su novvus.toml qué campos y qué sección de formulario aporta a un modelo ajeno; el kernel valida y registra; el módulo base los aplica a través de su propio SDK sin saber que el extensor existe.

Principio rector: un solo escritor por esquema. Los datos de extensión viven en la tabla del módulo base, en la columna JSONB ext con forma {extensor: {campo: valor}}, y solo el base los lee y escribe. El extensor opera por la API pública del base o simplemente deja que los usuarios editen sus campos desde la UI del base. El rol de base de datos del módulo sigue sin privilegios fuera de mod_{id}: "no tocar tablas ajenas" continúa siendo imposibilidad técnica, no promesa.
salesmx (novvus.toml)           Kernel                            CRM (base)
   │ [extensions]                  │                                 │
   │ register / install            │                                 │
   ├──────────────────────────────►│ valida contra el meta del base; │
   │                               │ persiste core.model_extensions  │
   │                               │                                 │
   │                               │ GET /api/core/extensions ◄──────┤ ExtensionsRegistry (TTL 60 s)
   │                               ├────────────────────────────────►│ valida y aplica ext en su API
   │       GET /api/core/meta      │                                 │
   │  shell ◄── campos ext.salesmx.* fusionados en crm.contacts ──┘  │

Ejemplo completo: modules/salesmx/novvus.toml

[module]
id = "salesmx"
name = "Ventas México"
version = "0.1.0"
description = "Localización fiscal mexicana para el CRM (RFC y régimen)."

[dependencies]
modules = ["crm>=0.1"]            # extender exige depender: el target debe estar aquí

[presentation]
summary = "Agrega RFC y régimen fiscal a los contactos del CRM."
category = "Localizaciones"
icon = "landmark"
publisher = "Novvus"
license = "MIT"

[[extensions.fields]]
target = "crm.contacts"            # {módulo}.{resource del meta del base}
name = "rfc"                       # clave dentro de ext['salesmx']; ^[a-z][a-z0-9_]{0,63}$
type = "string"
label = "RFC"                      # texto fuente es-MX
config = { max_length = 13, pattern = "[A-ZÑ&0-9]{12,13}" }

[[extensions.fields]]
target = "crm.contacts"
name = "regimen"
type = "string"
label = "Régimen fiscal"
config = { choices = [
    { value = "601", label = "601 — General de Ley" },
    { value = "612", label = "612 — Personas Físicas con Actividades Empresariales" },
    { value = "626", label = "626 — RESICO" },
] }

[[extensions.ui]]
target = "crm.contacts.form"       # solo la vista form acepta contribuciones en v1
slot = "after:company_id"          # "after:{campo del layout base}" | "section:end"
group_label = "Datos fiscales"
fields = ["rfc", "regimen"]

El module.py de salesmx tiene dos líneas útiles: module = NovvusModule(...) y app = module.create_app(). No declara modelos ni migraciones; su valor entero está en el manifiesto. El runtime existe para que en el futuro pueda escuchar eventos del CRM o exponer endpoints propios.

Reglas y límites

ReglaDónde se aplica
Todo target pertenece a un módulo declarado en [dependencies] modules; extender el propio módulo es error ("usa columnas normales").manifest.py:370-386 (SDK) y validación espejo en el kernel al registrar.
Tipos v1: string, text, integer, decimal, boolean, date, datetime. choices vía config. Sin relation ni json.EXT_FIELD_TYPES, manifest.py:180.
Máximo 32 campos ext por módulo extensor y 16 extensores por modelo base.MAX_EXT_FIELDS (manifest.py:183); MAX_EXTENDERS_PER_MODEL (novvus-registry/src/lifecycle.rs:22).
[[extensions.ui]] solo referencia campos declarados para el mismo target; slot con forma after:{campo} o section:end; group_label obligatorio.manifest.py:408-437.
Si el base aún no hizo handshake cuando se registra el extensor, la validación del modelo se repite al servir: un target inexistente no se fusiona y se registra en log. El orden de arranque no rompe el registro.Kernel, routes/meta.rs.

Fusión en el meta y render

GET /api/core/meta[/{módulo}] añade a cada modelo del base, para los extensores habilitados en la org del usuario, campos planos con name = "ext.{extensor}.{campo}" y la marca "ext": "{extensor}". Flags: filterable y sortable verdaderos, groupable solo para boolean/choices, searchable falso. Las secciones de [[extensions.ui]] aterrizan en views.form.ext_sections; el GenericFormView las pinta justo debajo de la fila que contiene el campo del slot y, si el slot no existe en el layout, al final (degradación elegante, jamás rotura). La lista añade las columnas ext al final. El ETag del meta ya cubre el documento fusionado.

Cómo el módulo base lee y escribe ext

Nada que programar: lo hace la auto-API del base (sdk/src/novvus_sdk/extensions.py).

1
Definiciones. ExtensionsRegistry.for_org(org_id) consulta GET /api/core/extensions?org_id= con el token de servicio y cachea por organización DEFINITIONS_TTL = 60 segundos. Si el kernel no responde, sirve la copia anterior (o vacío) y sigue funcionando.
2
Escritura. POST/PATCH aceptan {"ext": {"salesmx": {"rfc": "XAXX010101000"}}}. validate_ext_payload() rechaza con 422 extensores no habilitados, campos no declarados, tipos incorrectos, max_length, pattern y choices incumplidos; null borra la clave; en create exige los required. El permiso es el del recurso base (crm.contacts.write).
3
Lectura. filter_ext_for_read() deja salir únicamente los namespaces de extensores habilitados para la org de la petición. Deshabilitar salesmx en una org hace desaparecer rfc de las respuestas sin borrar datos.
4
Filtros y export. El DSL acepta {"field": "ext.salesmx.rfc", "op": "ilike", "value": "XAXX%"} (traducido a ext -> 'salesmx' ->> 'rfc' con cast por tipo); el export añade las columnas ext al final con su label.
# Desde un endpoint custom del base, si alguna vez necesitas leer ext a mano:
defs = await module.extensions.for_org(current_context().org_id)   # {resource: {extensor: {campo: decl}}}
rfc = (contact.ext.get("salesmx") or {}).get("rfc")
# En tests, module.ext_definitions_override = {...} evita el kernel por completo.
Ciclo de vida del extensorEfecto sobre los datos
Habilitado en la orgSus campos aparecen en meta, respuestas y validación para esa org.
Deshabilitado en la orgDesaparecen del meta y de las respuestas; el JSONB se conserva intacto.
Desinstalado de la instanciaCae su fila de core.model_extensions (CASCADE); los datos huérfanos en ext se conservan. La purga es responsabilidad explícita del operador: el contrato prevé un comando de CLI que en v0.1.6 aún no existe.
Lógica extendida sin override de código ajeno. Datos → campos ext. Reacciones → eventos del base (crm.contact.created…). Consultas → module.call() con service_permissions. UI compleja → rutas propias del extensor bajo /salesmx/…. Inyectar React en vistas del base queda fuera por diseño (decisión de marketplace).

2. Campos personalizados por organización

Contrato: documents/docs/CUSTOM_FIELDS.md. Misma infraestructura que las extensiones, distinto dueño: aquí es el administrador de una organización quien agrega "número de contrato" a oportunidades desde la UI, sin programar, sin migraciones y sin tocar el esquema.

Extensiones (ext)Campos custom (custom)
Quién declaraUn módulo, en novvus.tomlEl admin de una org, en /settings/custom-fields
AlcanceToda la instancia (visible por org habilitada)Una organización
Columna JSONBext = {extensor: {campo: valor}}custom = {campo: valor} (plano)
Nombre en el metaext.{extensor}.{campo}custom.{campo}, marca "custom": true
Registrocore.model_extensionscore.custom_fields
LabelsTexto fuente es-MX, pasan por t()Texto del usuario, jamás se traduce

La tabla core.custom_fields y sus reglas duras

Columnas: id, org_id, module_id, model, name (^[a-z][a-z0-9_]{0,29}$, único por org/módulo/modelo, inmutable), field_type (inmutable: cambiar el tipo con datos existentes es corrupción garantizada; se crea otro campo), label, config (max_length, pattern, choices, help), required, position, active, created_by, deleted_at. Tipos: los siete de extensiones; select se modela como string + config.choices. Límite por modelo: 50 (DEFAULT_LIMIT_PER_MODEL, routes/custom_fields.rs:24). Cero DDL en runtime: crear campos no genera ninguna migración; la columna custom jsonb NOT NULL DEFAULT '{}' ya existe en toda tabla del SDK (models.py:59).

RutaPermisoEfecto
GET /api/core/custom-fields?module_id=&model=cualquier miembroDefiniciones vivas de la org (la shell las necesita para renderizar).
POST /api/core/custom-fieldscore.custom_fields.manageCrear: valida nombre, tipo, que module_id.model exista en el meta, módulo habilitado, límite y choices.
PATCH /api/core/custom-fields/{id}mismoSolo label, config, required, position, active.
DELETE /api/core/custom-fields/{id}mismoBorrado lógico; la definición se purga a los 30 días (main.rs:39-44).
GET /api/core/custom-fields/service?org_id=token de servicioVariante para el SDK del módulo.

En el SDK del módulo

CustomFieldsRegistry (sdk/src/novvus_sdk/custom_fields.py) es hermano de ExtensionsRegistry: caché por org con TTL 60 s del endpoint de servicio y degradación con copia anterior. validate_custom_payload() acepta {"custom": {"contract_number": "C-2026-118"}}, rechaza claves sin definición activa, coerciona por tipo, exige required al crear, hace merge por campo en PATCH y null borra. Incluye el barrido perezoso: al escribir un registro, las claves sin definición activa se descartan. El kernel nunca ejecuta SQL sobre mod_* para limpiar; ni para eso.

En la shell: el formulario genérico pinta los campos custom en una sección "Información adicional" al final, ordenados por position; la lista los añade como columnas finales; el DSL admite custom.{nombre} y /group?by=custom.{nombre} cuando el campo es boolean o tiene choices. El administrador los gestiona en /settings/custom-fields (selector módulo → modelo desde el meta, alta con vista previa, editar, desactivar, borrar con aviso).

3. Configuración por organización ([[config]])

Inspirada en res.config.settings, sin herencia de modelos: el módulo declara un esquema, el kernel persiste valores por organización en core.org_module_config, la shell renderiza un formulario genérico en /settings y el SDK lee los valores tipados.

# modules/crm/novvus.toml
[[config]]
key = "crm.default_currency"       # debe empezar por el id del módulo
type = "select"                     # string | number | boolean | select
label = "Moneda predeterminada"
description = "Moneda usada para nuevas oportunidades."
options = ["MXN", "USD", "EUR"]     # obligatorio para select
default = "MXN"                     # debe coincidir con type
permission = "crm.pipelines.manage" # default core.modules.manage; namespace del módulo

[[config]]
key = "crm.rotting_days"
type = "number"
label = "Días para marcar oportunidad estancada"
default = 14
permission = "crm.pipelines.manage"

La clave secret = true enmascara el valor en las respuestas para el frontend (sigue siendo escribible; devolver la máscara tal cual es un no-op, no un valor nuevo). El propio módulo, con su token de servicio, recibe el valor real: novvus-registry/src/config.rs:128.

RutaQuiénEfecto
GET /api/core/orgs/{org}/modules/{id}/configusuarioEsquema + valores efectivos; solo los campos cuyo permission tiene el usuario.
PUT /api/core/orgs/{org}/modules/{id}/configusuarioFija valores; cada clave exige su permiso; validación de tipo y opciones.
GET|PUT /api/core/configmódulo (token de servicio + x-novvus-org)El módulo lee/escribe su propia configuración para ese tenant.
# En el SDK (app.py:237-254): defaults del esquema fusionados con lo guardado por la org
settings = await module.config()                     # org del contexto actual
currency = settings["crm.default_currency"]         # "MXN" si la org no fijó nada
await module.set_config({"crm.rotting_days": 21}, org_id=org)

# En modo offline (tests) config() devuelve solo los defaults; set_config lanza RuntimeError.

4. Cron y hooks de ciclo de vida

Primitivas orquestadas por el kernel sobre el canal interno firmado: nunca ejecutan código arbitrario en el kernel, siempre hacen POST a tu runtime con cabeceras HMAC que llevan el tenant.

Trabajos programados

# novvus.toml
[[cron]]
name = "crm.rot_opportunities"     # {id}.{nombre}, único
interval_seconds = 86400            # ≥ 1
description = "Marca oportunidades estancadas"

# module.py — el handler corre dentro de la sesión de tenant de cada org habilitada
@module.cron("crm.rot_opportunities")
async def rot(session: AsyncSession) -> None:
    settings = await module.config()          # current_context().org_id es la org del disparo
    days = int(settings["crm.rotting_days"])
    ...
1
En install el kernel siembra las definiciones en core.cron_jobs (lifecycle.rs:347). @module.cron("x") falla al importar si x no está en [[cron]] (app.py:149).
2
El CronScheduler (novvus-events/src/cron.rs) mantiene una fila por job × organización habilitada en core.cron_runs y reclama las vencidas con FOR UPDATE SKIP LOCKED: dos instancias del kernel nunca duplican una ejecución.
3
Hace POST /_novvus/cron al runtime con {name, org_id}; el SDK abre tenant_session(org_id) y llama al handler (app.py:389-397). Éxito → next_run_at = now() + interval; fallo → reintento con el mismo backoff exponencial que los eventos.

Hooks por organización

@module.on_install
async def setup(session: AsyncSession) -> None:
    # datos iniciales del tenant: pipeline por defecto, etapas…
    ...

@module.on_enable
async def enabled(session): ...
@module.on_disable
async def disabled(session): ...
@module.on_uninstall
async def teardown(session): ...

El kernel los invoca en las transiciones por organización (POST /api/core/orgs/{org}/modules/{id}/{install|enable|disable|uninstall}) con POST /_novvus/hooks/{hook}. La entrega es best-effort: un fallo se registra pero no revierte la transición (la verdad vive en core.org_modules). on_uninstall se dispara antes de borrar la fila para que el runtime pueda resolver el tenant. Un hook no registrado responde {"status": "ignored"}.

5. Internacionalización

Contrato: documents/docs/I18N.md. Idioma fuente es-MX: escribes el texto en español y esa misma cadena es la clave. Sin catálogo, todo pasa sin cambios; un texto sin traducir devuelve la fuente, nunca una clave cruda ni un error. Resolución: locale exacto → locale base (en-US → en) → fuente.

// modules/crm/i18n/en-US.json
{ "Oportunidad de {name}": "Opportunity for {name}", "Empresas": "Companies", "Puesto": "Job title" }

# Python: module._ es alias de module.gettext; la interpolación es explícita
name = module._("Oportunidad de {name}").format(name=contact.name)
forced = module._("Oportunidad de lead", locale="en-US")
CapaCómo llega el locale
FrontendlocalStorage novvus.locale (default es-MX); lib/api.ts añade x-novvus-locale a cada petición; useI18n().t() traduce los textos de la shell y también los labels del meta.
Gatewayresolve_locale toma x-novvus-locale o el primer tag de Accept-Language, y lo reenvía al módulo en una cabecera fuera de la firma HMAC: es informativa y jamás autoriza.
SDKverify_request lo expone en RequestContext.locale (security.py:67). En cron, eventos y hooks no hay usuario: se usa es-MX. El export de la auto-API traduce las cabeceras con este locale.

Añadir un idioma: agregar el locale a LOCALES y su catálogo a CATALOGS en apps/web/src/lib/i18n.tsx, y un i18n/{locale}.json por módulo. No hay extracción automática: los catálogos se mantienen a mano. Los labels de campos personalizados son datos del usuario y no se traducen.

6. Eventos entre módulos (recordatorio)

Lo viste en el tutorial; aquí solo la chuleta. Contrato completo en documents/docs/EVENTS.md.

# modules/projects/module.py (recortado)
@module.on("crm.opportunity.won")                    # debe estar en [events] listens
async def create_project_from_won_opportunity(event: Event, session: AsyncSession) -> None:
    contact = await module.call("GET", f"/api/crm/contacts/{cid}", org_id=event.org_id)  # API pública, nunca tablas
    ...
    await module.emit("projects.project.created", {"project_id": str(project.id)}, org_id=event.org_id)
PiezaDetalle
emits / listensDeclarados en el manifiesto; module.emit de un tipo no declarado lanza ValueError; el kernel también lo valida.
IdempotenciaEntrega at-least-once. El SDK inserta event.id en mod_{id}._processed_events con ON CONFLICT DO NOTHING en la misma transacción del handler: duplicado → {"status": "duplicate"} sin reejecutar.
module.call(method, path, org_id, json)Llamada módulo→módulo por el gateway con token de servicio; el gateway inyecta los service_permissions del manifiesto. En modo offline lanza RuntimeError.
module.dependency_statuses()Estado de cada dependencia declarada (caché 10 s). GET /health responde status: "degraded" con degraded_dependencies cuando una no está enabled: el módulo sigue sirviendo, no "roto".

7. Empaquetado y catálogo (marketplace)

Para distribuir módulos fuera del monorepo (MODULE_CONTRACT.md §11, novvus-registry/src/package.rs). Un paquete es un JSON autocontenido, y se publica envuelto en una firma:

{
  "package": {
    "format_version": 1,
    "manifest_toml": "…contenido de novvus.toml…",
    "migrations": [{ "version": "0001_init", "sql": "…" }],
    "assets": [{ "path": "assets/icon.svg", "content_base64": "…" }]
  },
  "publisher": "ACME",
  "public_key": "<base64 clave pública Ed25519>",
  "signature": "<base64 firma Ed25519 de 64 bytes>"
}
ReglaDetalle
Sin código ejecutableassets son estáticos declarativos (iconos, capturas). La shell nunca corre JS de un módulo.
Firma sobre bytes canónicoscanonical_bytes() serializa con migrations y assets ordenados: determinista e independiente del orden de entrada. package_hash = SHA-256 hex de esos bytes.
Fail-closedLa clave pública del paquete debe estar en NOVVUS_TRUSTED_PUBLISHER_KEYS (lista de claves base64 separadas por coma). Clave ausente o firma inválida → 403. Lista vacía = nadie puede publicar.
GET /api/core/catalogMódulos disponibles para instalar (core.modules.read); no expone el blob package.
POST /api/core/catalogPublica un paquete firmado (core.modules.manage; re-verifica la firma). Persiste en core.module_catalog.
POST /api/core/catalog/{id}/registerCopia el paquete a core.modules por el flujo normal de register (re-verifica), y a partir de ahí aplica el ciclo de vida de siempre: install → enable → habilitar por organización desde la tienda /apps.
Dos cosas distintas. El catálogo guarda módulos disponibles; core.modules guarda módulos registrados/instalados. Y la firma del paquete es independiente de la verificación SHA-256 con la que el CLI administrativo descarga releases de la plataforma.
Ver más: checklist de un módulo "extensor"
  • Declara el base en [dependencies] modules con restricción de versión.
  • Un [[extensions.fields]] por campo, máximo 32; tipos v1; label en español.
  • Un [[extensions.ui]] por sección, solo .form, con slot válido.
  • Si necesitas reaccionar a datos del base, escucha sus eventos y consúltalo con module.call.
  • Pruebas: el arnés de modules/salesmx/tests arranca el runtime sin modelos ni migraciones contra una base efímera y comprueba que el manifiesto valida y el runtime responde.
