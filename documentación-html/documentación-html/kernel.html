El kernel por dentro

Nivel avanzado

El kernel es un workspace de Cargo con siete crates. Esta página lo recorre crate por crate a partir del código real de kernel/crates/: qué expone cada uno, qué reglas valida, qué constantes gobiernan su comportamiento y qué variables de entorno lo configuran. Está pensada para quien ya construyó un módulo y quiere entender qué pasa del otro lado de los headers X-Novvus-*.

El workspace y sus dependencias

kernel/Cargo.toml declara los siete miembros con resolver = "2", versión de workspace 0.1.0 y dependencias compartidas (axum 0.8 con multipart, sqlx 0.8 con runtime-tokio/postgres/migrate, tokio, tower-http con trace+cors, jsonwebtoken 9, argon2 0.5, ed25519-dalek 2, object_store 0.11 con aws, semver, toml 0.8, uuid con v7).

Solo el gateway depende de los seis restantes; ninguno de los crates de dominio depende de otro crate de dominio (todos bajan a novvus-common). El gateway también reexporta MIGRATOR, las migraciones de kernel/migrations embebidas en tiempo de compilación con sqlx::migrate!, y las aplica en init() antes de construir el estado.

novvus-common

Módulos: audit, config, error, ids, internal, telemetry.

Configuración (config.rs)

Config::from_env() lee variables con defaults de desarrollo. La tabla completa está al final de la página; tres detalles de diseño:

  • Las listas (NOVVUS_CORS_ORIGINS, NOVVUS_TRUSTED_PUBLISHER_KEYS) se parten por coma, se recortan y se descartan vacíos; lista vacía = función deshabilitada.
  • NOVVUS_BOOTSTRAP_TOKEN deliberadamente no tiene default: None desactiva el modo bootstrap (fail-closed).
  • Un TTL no numérico cae al default (parse().unwrap_or(...)): 900 s access, 1 209 600 s (14 días) refresh.

Errores (error.rs)

Todo handler devuelve AppResult<T>. AppError se serializa como {"error": {"code", "message"}}; los internos (Database, Internal) se loguean y responden "internal error" sin filtrar detalle.

Identificadores, firma interna y auditoría

  • ids::new_id() → Uuid::now_v7(): UUIDv7 generado por la aplicación, ordenable por tiempo.
  • internal.rs define los headers x-novvus-user/org/perms/timestamp/signature y x-novvus-locale (informativo), DEFAULT_LOCALE = "es-MX", MAX_SKEW_SECONDS = 60, y las funciones sign/verify sobre la cadena canónica user\norg\nperms\ntimestamp\nmethod\npath (HMAC-SHA256 hex, verificación en tiempo constante).
  • audit::record inserta en core.audit_log de forma best-effort: un fallo de auditoría se loguea pero jamás rompe la acción principal.

novvus-identity

Módulos: jwt, password, service, orgs.

FlujoQué hace el código (service.rs)
registerNormaliza el email (trim + minúsculas; debe contener @ y medir 5–254), exige contraseña ≥ 8 y display_name; hashea con Argon2id; email duplicado → 409. Audita auth.register.
loginBusca id, password_hash por email con is_active. Si no existe ejecuta dummy_verify() (quema el mismo CPU) y responde el mismo 401 "invalid credentials". Resuelve la org: la pedida (debe existir membresía) o la de la membresía más antigua, o None. Emite el par y audita auth.login.
issue_pairAccess con roles informativos y refresh sin roles, ambos con jti UUIDv7. Persiste sha256(refresh) en core.refresh_tokens con id = jti.
refreshDecodifica con typ=refresh, busca el hash. Si revoked_at o replaced_by no son nulos: detección de reuso → revoca todos los refresh vivos del usuario, audita auth.refresh_reuse y responde 401. Si expiró → 401. Si es válido: emite par nuevo (permite cambiar de org si hay membresía) y marca el presentado como rotado con replaced_by.
logoutAcepta refresh expirados (decode_token_allow_expired: firma y typ siguen verificándose) y marca revoked_at.
  • JWT (jwt.rs): HS256, claims sub, org_id?, roles, typ, jti, iat, exp; decode_token valida exp con leeway de 5 s y siempre compara typ.
  • Argon2id (password.rs): 19 456 KiB, t=2, p=1, tag 32 bytes, versión 0x13, salt aleatorio de OsRng; el hash almacenado es una cadena PHC que empieza por $argon2id$.
  • Orgs: crear una organización crea también el rol de sistema Owner con * y lo asigna al creador; GET /api/core/me devuelve identidad, org activa, roles y permisos efectivos.

novvus-rbac

Módulos: cache, service; funciones públicas grant_matches e is_allowed.

// lib.rs — un grant satisface una key requerida si:
granted == "*" || granted == required
|| (granted termina en ".*" && required empieza por ese prefijo seguido de '.')

Por eso crm.* cubre crm.contacts.read pero crm.con.* no: el comodín corta por segmento completo. Los endpoints siempre piden keys concretas.

RbacCache guarda (user_id, org_id) → Arc<HashSet<String>> con TTL de 30 s. La consulta une memberships → membership_roles → role_permissions → permissions. service.rs llama invalidate_org al mutar roles/permisos e invalidate_user al mutar membresías, así la revocación es efectiva en la siguiente petición. El gateway expone require_perm, has_perm (gating campo a campo) y perms_header_value (lista ordenada y separada por comas para X-Novvus-Perms).

Catálogo sembrado por el kernel en 0001_core.sql y 0010_custom_fields.sql: *, core.orgs.read/manage, core.members.manage, core.roles.read/manage, core.modules.read/manage, core.audit.read, core.custom_fields.manage.

novvus-registry

Módulos: manifest, lifecycle, migrations, meta, org_lifecycle, resolver, config, catalog, package.

Parseo y validación del manifiesto (manifest.rs)

Manifest::parse(toml) deserializa con serde (secciones opcionales con #[serde(default)]) y luego validate() aplica estas reglas; cualquier fallo rechaza el manifiesto completo con 422:

ElementoRegla real
module.id^[a-z][a-z0-9_]{1,31}$ (2–32 caracteres) y no reservado: core, api, internal, novvus.
module.name / versionNombre no vacío; versión SemVer válida.
[[permissions]] keyTres segmentos no vacíos y el primero igual al id del módulo.
[events] emits{id}.{entity}.{action} con segmentos [a-z0-9_]; listens solo exige tres segmentos no vacíos (puede ser de otro módulo).
[dependencies] modules"crm" o "crm>=1.0" (semver VersionReq); un módulo no puede depender de sí mismo.
[dependencies] service_permissionsTres segmentos y jamás core.*.
[presentation]icon es slug [a-z0-9-] (≤ 48); website debe ser http(s)://.
[ui]Toda path (entry, nav, dashboard, settings) es /{id} o empieza por /{id}/ (valid_ui_path); iconos slug; permission en el namespace {id}.*.
[[config]]key = {id}.{…} sin duplicados; tipo ∈ string|number|boolean|select; select exige options; el default debe coincidir con el tipo (y estar entre las opciones); permission del namespace del módulo o exactamente core.modules.manage.
[[cron]]name = {id}.{…} (≥ 2 segmentos, sin duplicados); interval_seconds ≥ 1.
[extensions]Máximo 32 campos (MAX_EXT_FIELDS); target = {módulo}.{modelo} de un módulo declarado en dependencies y distinto del propio; nombre ^[a-z][a-z0-9_]{0,63}$; tipo ∈ string|text|integer|decimal|boolean|date|datetime; label obligatorio; ui.target termina en .form, referencia solo campos declarados, slot = after:{campo} o section:end.

Ciclo de vida (lifecycle.rs)

FunciónDetalle del código
registerValida manifiesto y versiones de migración (NNNN_snake_case, 6–128 chars). En una transacción: upsert en core.modules (estado registered solo en inserción; el re-registro conserva el estado), compara checksum de cada fuente contra core.module_migrations (cambio en una aplicada → 409), upsert en module_migration_sources, y reemplaza las filas de core.model_extensions del extensor comprobando el tope de 16 extensores por modelo (MAX_EXTENDERS_PER_MODEL).
installSolo desde registered. ensure_module_role crea o ajusta novvus_module (LOGIN PASSWORD … NOBYPASSRLS, tolerando carreras) y hace GRANT novvus_module TO CURRENT_USER; CREATE SCHEMA IF NOT EXISTS mod_{id} + GRANT USAGE, CREATE; aplica migraciones; registra permisos y jobs de cron; genera el token de servicio nvk_ + 64 hex (32 bytes de OsRng) y guarda solo su SHA-256. El token en claro se devuelve una sola vez.
migrateCualquier estado salvo registered; aplica pendientes y audita si aplicó algo.
enableDesde installed o disabled. Cada dependencia debe estar registrada, enabled y satisfacer el VersionReq.
disableSolo desde enabled.
uninstallExige confirm=true (body JSON {"confirm": true} en la ruta); permitido desde disabled y también desde registered. DROP SCHEMA IF EXISTS mod_{id} CASCADE, borra permisos y la fila de core.modules (cascada a migraciones, fuentes, deliveries, extensiones, cron).
handshakeCompara el hash del token de servicio; exige estado installed o enabled; base_url debe ser http(s); si viene meta lo valida (un meta inválido rechaza todo el handshake; sin meta conserva el anterior). Guarda base_url sin barra final y responde internal_hmac_secret, el DSN reescrito para novvus_module (module_dsn) y schema.

Corredor de migraciones (migrations.rs)

-- por cada migración pendiente, en su propia transacción:
SET LOCAL ROLE novvus_module;
SET LOCAL search_path = mod_{id};
-- … el SQL del módulo (raw_sql, puede tener varias sentencias) …
RESET ROLE;
INSERT INTO core.module_migrations (module_id, version, checksum) VALUES ($1, $2, $3);
COMMIT;

Antes de aplicar, apply_pending busca drift: cualquier migración ya aplicada cuya fuente tenga otro checksum aborta con 409 ("applied migrations were modified"). Aplicación y registro comparten transacción: o ambas ocurren o ninguna. El checksum es SHA-256 hex del SQL.

Meta, ciclo por organización, resolver y catálogo

  • meta.rs: tipos serde con deny_unknown_fields; MAX_META_BYTES = 512 KiB (inclusive); los permisos del meta se validan contra el namespace del módulo.
  • org_lifecycle.rs: filas de core.org_modules (installed/enabled/disabled); enable exige dependencias habilitadas para la misma org; disable/uninstall se bloquean si otro módulo habilitado de la org lo requiere; uninstall borra la fila y nada más.
  • resolver.rs: función pura sobre un mapa de nodos; DFS con marcas Visiting/Done que produce enable_order (post-orden, solo módulos instance_ready), satisfied y problems (missing, unavailable, version_conflict, cycle con miembros a partir del inicio del ciclo).
  • package.rs: ModulePackage {format_version, manifest_toml, migrations, assets} con bytes canónicos (migraciones y assets ordenados); SignedPackage::verify exige que la clave pública esté en el allowlist y que la firma Ed25519 (64 bytes) valide. Lista vacía rechaza todo.
  • config.rs: esquema + valores efectivos por org con gating de permiso por campo y enmascarado de secret.

novvus-events

Módulos: publish, dispatcher, cron, backoff. Constantes: CHANNEL = "novvus_events", DELIVERY_PATH = "/_novvus/events", CRON_PATH = "/_novvus/cron".

PiezaComportamiento
publishComprueba con manifest->'events'->'emits' ? $2 que el emisor declara el tipo (404 si no está registrado, 403 si no lo declara). En una transacción inserta el evento, una delivery por módulo enabled o disabled que lo tenga en listens, y pg_notify; org inexistente → 404.
DispatcherAbre un PgListener sobre novvus_events. Bucle: drena lotes de 20 deliveries vencidas (FOR UPDATE OF d SKIP LOCKED, solo módulos enabled con base_url) y luego espera NOTIFY o 5 s. POST firmado con user="", perms="", timeout HTTP 10 s. Éxito → delivered; fallo → attempts+1, next_retry_at = now() + backoff, y failed al llegar a 25 intentos.
backoff_secondsbase^min(attempts,4) acotado a [1, 300] s; base por defecto 4 (los tests usan 1).
CronSchedulerCada 5 s: provision() inserta una fila en core.cron_runs por job × org con el módulo enabled (ON CONFLICT DO NOTHING, vencimiento inmediato) y procesa lotes de 20 filas vencidas (status='pending', módulo enabled en instancia y en la org, con base_url). POST {name, org_id} a /_novvus/cron firmado con el tenant. Éxito → next_run_at = now() + interval, attempts = 0, last_status='ok'; fallo → mismo backoff, last_status='error'.

Los hooks de ciclo de vida viven en el gateway (hooks.rs), no en este crate: hooks::fire hace POST /_novvus/hooks/{on_install|on_enable|on_disable|on_uninstall} con la misma firma y es best-effort (loguea y nunca revierte la transición).

novvus-files

Módulos: config, storage. Un FileStorage envuelve un Arc<dyn ObjectStore>: LocalFileSystem con prefijo o AmazonS3Builder (bucket, región default us-east-1, endpoint opcional con allow_http si empieza por http://, credenciales opcionales).

Layout de objetos:
  org/{org_id}/{sha[0..2]}/{sha[2..4]}/{sha256}   contenido definitivo
  org/{org_id}/tmp/{uuidv7}                       staging de subida

Subida (orquestada por routes/files.rs):
  stash()  ─ stream al staging, SHA-256 y tamaño al vuelo; supera max → borra y 413
  BEGIN
    attach_blob()  ─ upsert core.attachment_blobs (org, sha256) refcount+1 → ¿nuevo?
    cuota          ─ SUM(size_bytes) de blobs de la org > quota → rollback y 413
    INSERT core.attachments
  COMMIT
  promote_or_discard() ─ copia tmp → clave definitiva si es nuevo; borra tmp siempre

gc(retention_days) recorre en lotes de 500 los adjuntos con deleted_at < now() − retención, borra la fila y llama release_blob (refcount−1; al llegar a 0 borra la fila del blob y el objeto físico). Es idempotente; un objeto que no se pudo borrar solo deja un warning.

novvus-gateway

Módulos: extract, hooks, proxy, rate_limit, routes (auth, orgs, roles, modules, meta, files, extensions, custom_fields, chatter, stream, catalog, events, health), state.

Arranque (main.rs)

1
dotenvy + telemetry::init("info"); Config::from_env().
2
init(): pool de 10 conexiones, MIGRATOR.run (migraciones core), AppState::new (caché RBAC, cliente reqwest con timeout 30 s, rate limiter, FileStorage, canal broadcast de 256 para SSE).
3
Tareas de fondo: Dispatcher, listener de novvus_notify para SSE, CronScheduler, y un ticker horario que ejecuta GC de adjuntos, purga de definiciones de campos custom borradas hace > 30 días, notificaciones activity_due (una por día por actividad) y purga de notificaciones leídas hace > 90 días.
4
axum::serve en NOVVUS_BIND_ADDR con ConnectInfo<SocketAddr> (necesario para el rate limit por IP) y apagado gracioso con Ctrl+C / SIGTERM.

Rate limit de /auth (rate_limit.rs)

Ventana fija de 60 s por IP, en memoria (Mutex<HashMap<IpAddr, (u32, Instant)>>), límite NOVVUS_AUTH_RATE_LIMIT_PER_MINUTE (default 30). Al superar 10 000 entradas se limpian las ventanas vencidas. Se reinicia con el proceso: es un freno básico contra fuerza bruta, no un contador distribuido. Sin ConnectInfo la IP cae a 0.0.0.0.

Proxy (proxy.rs)

resolve_caller distingue módulo llamante (token de servicio + x-novvus-org obligatorio; permisos = service_permissions del manifiesto; usuario vacío) de usuario final (JWT + permisos vivos de la caché). resolve_locale toma x-novvus-locale si es una etiqueta BCP-47 bien formada (segmentos de 2–8 alfanuméricos unidos por -), si no el primer tag de Accept-Language, y si no es-MX. Comprobaciones de módulo enabled + base_url ocurren antes de validar credenciales. Un runtime inalcanzable responde 503; el cuerpo de la respuesta se lee completo antes de reenviarlo (sin streaming).

SSE (routes/stream.rs)

GET /api/core/stream?token= decodifica el access token, exige org activa y se suscribe al canal broadcast. Cada conexión filtra en memoria por org_id == org && user_ids.contains(user); los receptores rezagados descartan (la shell reconcilia con polling). Keep-alive : ping cada 25 s. spawn_notify_listener mantiene una sola conexión LISTEN novvus_notify por proceso, parsea {org_id, user_ids, kind} y reconecta con espera de 5 s si se cae.

Compilar y probar

# desde la raíz del repo; Postgres arriba en :5432 (docker compose up -d)
cd kernel
cargo build                       # perfil dev: opt-level 0 salvo argon2/blake2/digest/sha2 en 3
cargo test --workspace            # unitarios + integración de gateway contra Postgres
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --check
cargo run -p novvus-gateway       # o `make kernel-test` / targets del Makefile
  • Los tests de integración levantan la app en proceso y hablan con Postgres real; por eso kernel-test del Makefile exige la base arriba.
  • No quites los opt-level = 3 de los crates criptográficos en kernel/Cargo.toml: Argon2id de 19 MiB sin optimizar tarda minutos por hash y cuelga la suite (DECISIONS.md, 2026-07-12).
  • La máquina de desarrollo usa el toolchain stable-x86_64-pc-windows-gnu (sin Visual Studio Build Tools; DECISIONS.md, 2026-07-11). Trampas conocidas: WinLibs en el PATH puede hacer fallar dlltool, y la cobertura Rust (cargo llvm-cov) no se puede medir de forma nativa en Windows GNU (QA.md); el CI usa Linux y exige --fail-under-lines 85.
  • El binario del gateway no se puede recompilar mientras corre en Windows: detén el proceso (off.bat) antes de cargo build/cargo test.
