Mantenimiento

Nivel básico

Lo que haces después de instalar: revisar salud, leer logs, respaldar y restaurar, rotar secretos, entender qué limpia el kernel por su cuenta, manejar el ciclo de vida de los módulos y resolver los problemas que sí aparecen en la práctica.

Regla de oro

Antes de tocar un servidor compartido identifica tres cosas: qué tipo de instalación es (demo, cliente con CLI o manual), cuándo fue el último backup y quién está usando la plataforma ahora. En producción nunca hagas reset, nunca borres volúmenes y nunca cambies secretos sin avisar.

Los contenedores de producción corren con restart: unless-stopped: tras un reinicio del servidor vuelven solos. Un docker compose down los detiene de forma limpia (el kernel drena las conexiones en vuelo al recibir SIGTERM). Los servicios se llaman igual en los tres compose: postgres, kernel, bootstrap, crm, projects, web.

Respaldos

Hay tres volúmenes en una instalación de cliente o manual, y no todos valen lo mismo:

VolumenContenido¿Respaldar?
pgdataToda la base PostgreSQL: usuarios, organizaciones, datos de todos los módulos, chatter, definiciones de campos.Sí siempre, con pg_dump (no copiando el directorio en caliente).
filesAdjuntos (backend local del kernel). Si usas S3/R2/MinIO, los binarios viven allá y este volumen no importa.Sí
tokensTokens de servicio de los módulos (/run/novvus/<modulo>.env), publicados por bootstrap al instalar.No hace falta, pero no lo borres: sin él los módulos no arrancan y solo se regenera reinstalándolos.

Además del volumen, respalda el .env (contiene los secretos que hacen legibles esos datos) y el compose en uso. Es exactamente lo que novvus update guarda en cada /opt/novvus/backups/<fecha>-<de>-to-<a>/: postgres.dump, roles.sql, files.tar.gz, tokens.tar.gz, .env, el compose, novvus.json y un backup.json con SHA-256 de cada pieza. Esos backups nunca se borran solos: revísalos de vez en cuando y mueve los viejos fuera del servidor.

Dump de la base

# Cliente (CLI). El .env tiene POSTGRES_USER y POSTGRES_DB; cárgalo sin imprimirlo.
cd /opt/novvus
set -a; . ./.env; set +a
mkdir -p backups/manual
docker compose -f docker-compose.yml exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" > backups/manual/novvus-$(date +%F).dump

# Manual: igual, con -f docker-compose.prod.yml
# Demo: usuario novvus, base novvus, archivo docker-compose.full.yml

El formato -Fc (custom) se restaura con pg_restore y permite restaurar tablas sueltas. Verifica que el dump es legible antes de confiar en él:

docker compose -f docker-compose.yml exec -T postgres pg_restore --list < backups/manual/novvus-2026-09-04.dump | head

Volumen de adjuntos

# El nombre real del volumen lleva el prefijo del proyecto: míralo con `docker volume ls`
docker run --rm -v novvus_files:/data:ro -v "$PWD/backups/manual":/backup alpine \
  tar czf /backup/files-$(date +%F).tar.gz -C /data .

Backup programado (cron)

Para un servidor pequeño, un cron diario es un buen punto de partida. Guarda esto como /usr/local/bin/novvus-backup.sh (perm 700) y prográmalo:

#!/usr/bin/env bash
set -euo pipefail
cd /opt/novvus
set -a; . ./.env; set +a
DEST=/var/backups/novvus/$(date +%F)
mkdir -p "$DEST"; chmod 700 "$DEST"
docker compose -f docker-compose.yml exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB" > "$DEST/postgres.dump"
docker run --rm -v novvus_files:/data:ro -v "$DEST":/backup alpine \
  tar czf /backup/files.tar.gz -C /data .
cp .env "$DEST/.env"; chmod 600 "$DEST"/*
# Conserva 14 días en el servidor; lo demás debe vivir fuera (S3, R2, el backup del proveedor)
find /var/backups/novvus -maxdepth 1 -mtime +14 -type d -exec rm -rf {} +
sudo crontab -e
# todos los días a las 02:15
15 2 * * * /usr/local/bin/novvus-backup.sh >> /var/log/novvus-backup.log 2>&1
Un backup que solo vive en el mismo servidor no es un backup. Copia el directorio del día a almacenamiento externo. Y recuerda que el .env respaldado contiene secretos: trátalo con los mismos permisos que el original.

Restaurar

Restaurar la base pisa lo que hay. Detén primero los consumidores (kernel y módulos) para que no haya conexiones abiertas ni escrituras a medias:

cd /opt/novvus
set -a; . ./.env; set +a
docker compose -f docker-compose.yml stop kernel crm projects web bootstrap
docker compose -f docker-compose.yml exec -T postgres \
  pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists < backups/manual/novvus-2026-09-04.dump
docker compose -f docker-compose.yml up -d --wait

Para el volumen de adjuntos, con el stack detenido:

docker run --rm -v novvus_files:/data -v "$PWD/backups/manual":/backup alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/files-2026-09-04.tar.gz -C /data"

Si restauras un backup hecho por novvus update, usa también su .env y su compose: la base tiene que ir con la versión de imágenes con la que se hizo el dump. La forma más segura es dejar .env y docker-compose.yml del backup en /opt/novvus, restaurar la base y levantar; después vuelves a actualizar.

Secretos y rotación

En una instalación de cliente los secretos los generó el CLI con entropía del sistema y viven en /opt/novvus/.env (permisos 600). En un despliegue manual los generaste tú con openssl rand -hex 32. En ambos casos novvus update los preserva: jamás regenera un secreto que ya existe. Esta es la lista completa y qué pasa si rotas cada uno:

VariableQuién la usaConsecuencia de rotarla
POSTGRES_PASSWORDPostgres y el kernel (DATABASE_URL).Postgres solo lee la variable al inicializar el volumen. Para rotarla: ALTER USER novvus PASSWORD '…' dentro del contenedor, luego cambia el .env y reinicia el stack.
NOVVUS_JWT_ACCESS_SECRETKernel: firma los access tokens (15 min).Todas las sesiones activas expiran de inmediato; los usuarios vuelven a entrar. Rotación barata.
NOVVUS_JWT_REFRESH_SECRETKernel: firma los refresh tokens (14 días).Igual que el anterior, pero nadie podrá renovar sesión sin volver a autenticarse.
NOVVUS_INTERNAL_HMAC_SECRETKernel y todos los módulos: firma de los headers internos gateway → módulo.Los módulos reciben el secreto en el handshake, así que hay que reiniciar kernel y módulos juntos. Hasta entonces, cada petición a un módulo responde 401.
NOVVUS_MODULE_DB_PASSWORDRol novvus_module de Postgres; el kernel lo entrega en el DSN del handshake.El kernel provisiona el rol con CREATE/ALTER ROLE … PASSWORD al instalar módulos. Tras rotar: reinicia el stack; si algún módulo no conecta, ejecuta ALTER ROLE novvus_module PASSWORD '…' a mano y reinicia de nuevo.
NOVVUS_BOOTSTRAP_TOKENSolo el servicio bootstrap, en los 6 endpoints de ciclo de vida de instancia (x-novvus-bootstrap-token).Sin efecto sobre usuarios ni datos: no es una credencial de usuario. Rotarlo solo exige reiniciar (bootstrap vuelve a correr y es idempotente).
NOVVUS_FILES_S3_ACCESS_KEY / NOVVUS_FILES_S3_SECRET_KEYKernel, solo con NOVVUS_FILES_BACKEND=s3.Rotas en el proveedor, actualizas el .env, reinicias el kernel. Los metadatos siguen en Postgres; los objetos no se mueven.
NOVVUS_TRUSTED_PUBLISHER_KEYSKernel: allowlist de claves públicas Ed25519 para publicar paquetes en el catálogo.No es un secreto, pero es fail-closed: vacía = nadie puede publicar. Quitar una clave no desinstala nada ya registrado.
NOVVUS_SERVICE_TOKEN (por módulo)El runtime del módulo, en el handshake. Vive en el volumen tokens (Docker) o en tu shell (dev).No se rota: el kernel guarda solo el hash. Perderlo o quererlo nuevo = reinstalar el módulo (ver problemas comunes).
# Generar un valor nuevo
openssl rand -hex 32
Otras variables que lee el kernel y que puedes ajustar sin rotar nada: NOVVUS_AUTH_RATE_LIMIT_PER_MINUTE (30 por defecto), NOVVUS_CORS_ORIGINS, NOVVUS_CHATTER_EDIT_WINDOW_MINUTES, NOVVUS_CUSTOM_FIELDS_LIMIT, NOVVUS_FILES_MAX_SIZE_BYTES (50 MB), NOVVUS_FILES_ORG_QUOTA_BYTES (10 GB), NOVVUS_FILES_GC_RETENTION_DAYS (30) y NOVVUS_LOG_LEVEL. La lista completa está en Referencia técnica.

Lo que el kernel hace solo

Hay procesos que no tienes que programar: el kernel los corre en segundo plano desde que arranca. Conviene conocerlos para no "descubrirlos" en un log a las tres de la mañana.

ProcesoFrecuenciaQué haceDónde se ve
Despachador de eventosContinuo (LISTEN/NOTIFY + barrido cada 5 s)Entrega event_deliveries pendientes a los módulos suscritos, at-least-once, con backoff exponencial (1 s, 4 s, 16 s… tope 5 min). Tras 25 intentos marca la entrega failed.Tabla core.event_deliveries; logs del kernel.
Scheduler de cronContinuo (barrido cada 5 s)Reclama filas vencidas de core.cron_runs con FOR UPDATE SKIP LOCKED (dos kernels nunca duplican una ejecución) y hace POST /_novvus/cron al módulo, una vez por job × organización habilitada. Reprograma next_run_at al terminar.core.cron_jobs, core.cron_runs.
GC de adjuntosCada horaAdjuntos borrados (lógicamente) hace más de NOVVUS_FILES_GC_RETENTION_DAYS (30 por defecto): decrementa el refcount del blob y, si llega a 0, borra el objeto físico.Log attachment GC pass.
Purga de campos personalizadosCada horaBorra las definiciones de core.custom_fields con deleted_at mayor a 30 días. Los valores huérfanos en las tablas de los módulos los limpia el SDK al escribir cada registro; el kernel nunca ejecuta SQL sobre mod_*.Log custom-field purge pass.
Actividades vencidasCada horaGenera una notificación activity_due por actividad abierta con fecha pasada, una sola vez al día por actividad.Log overdue-activity pass; buzón del usuario.
Purga de notificacionesCada horaBorra notificaciones leídas hace más de 90 días. Las no leídas se conservan.Log notification purge pass.
Listener SSEContinuoUna conexión LISTEN novvus_notify por proceso que reparte notificaciones y mensajes de chatter a las conexiones SSE abiertas; heartbeat cada 25 s.GET /api/core/stream.

Consultas útiles para vigilar los dos primeros (con psql como usuario novvus):

-- entregas fallidas o atascadas: si crece, hay un módulo que rechaza eventos
SELECT module_id, status, count(*) FROM core.event_deliveries
 WHERE status <> 'delivered' GROUP BY 1, 2;

-- jobs de cron atrasados más de una hora o que fallaron
SELECT module_id, name, org_id, status, attempts, next_run_at, last_status
  FROM core.cron_runs
 WHERE status = 'failed' OR next_run_at < now() - interval '1 hour';
Una entrega failed no se reintenta sola: es visible para operación y re-encolable a mano (poniéndola de nuevo en pending). Antes de hacerlo, arregla la causa en el módulo: los consumidores son idempotentes, así que reintentar es seguro.

Ciclo de vida de los módulos

Hay dos niveles y confundirlos cuesta datos:

Nivel instanciaNivel organización
Quién lo manejabootstrap (token de plataforma) o un admin con core.modules.manage vía API.Cada organización desde la tienda /apps (o /api/core/orgs/{org}/modules/{id}/…).
EstadosREGISTERED → INSTALLED → ENABLED ⇄ DISABLED → (uninstall)Instalado / habilitado / deshabilitado para esa org, en core.org_modules.
disableEl gateway responde 503 module_disabled en /api/{id}/* para todos; los eventos se acumulan como pendientes, no se pierden.Solo esa organización deja de ver el módulo; el runtime sigue corriendo.
uninstallDestructivo e irreversible: DROP SCHEMA mod_{id} CASCADE, borra migraciones, permisos y suscripciones. Solo desde DISABLED (o REGISTERED) y con el cuerpo JSON {"confirm": true}.No destructivo: quita la fila de habilitación de la org. El esquema y las filas del tenant sobreviven; volver a habilitar las recupera.
Dependenciasenable falla si una dependencia no está ENABLED. Deshabilitar una dependencia deja a los dependientes en estado degraded (lo reportan en su /health), no rotos.La tienda calcula el plan transitivo (/plan) y habilita las dependencias en orden.
Hooks—on_install / on_enable / on_disable / on_uninstall del módulo, best-effort (un fallo no revierte la transición).
# Deshabilitar y desinstalar a nivel instancia (destructivo), con JWT de administrador
curl -X POST http://localhost:8000/api/core/modules/inventario/disable -H "Authorization: Bearer $JWT"
curl -X POST http://localhost:8000/api/core/modules/inventario/uninstall \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"confirm": true}'

Limpieza de Docker

Las actualizaciones dejan imágenes antiguas. Revisa antes de borrar:

docker system df
df -h
docker image prune          # imágenes sin etiqueta
docker image prune -a       # también imágenes con etiqueta que ningún contenedor usa (versiones viejas)
Nunca docker volume prune ni docker system prune --volumes en un servidor con datos. Ahí viven pgdata, files y tokens. Conservar la imagen de la versión anterior un tiempo tampoco es mala idea: un rollback manual la necesita.

Problemas comunes

SíntomaCausaSolución
El kernel no arranca; el compose dice Define NOVVUS_VERSION en .env o una variable required variable … is missing Falta una variable obligatoria en el .env (el compose de producción no tiene defaults para secretos). Compara tu .env con .env.prod.example; en una instalación CLI, novvus update añade las que falten.
El kernel arranca y muere; los logs mencionan DATABASE_URL o password authentication failed La contraseña del .env no coincide con la del volumen pgdata (se cambió después de inicializarlo). Vuelve al valor original o cambia la contraseña dentro de Postgres (ALTER USER) antes de tocar el .env.
503 module "crm" runtime is not connected El módulo está habilitado pero su proceso no hizo handshake: sin token, kernel inaccesible o proceso caído. Logs del módulo. En Docker verifica que existe /run/novvus/crm.env en el volumen tokens; en dev, que exportaste NOVVUS_SERVICE_TOKEN y que NOVVUS_KERNEL_URL apunta al kernel.
503 module "crm" is not enabled Módulo deshabilitado a nivel instancia, o no habilitado para esa organización. Instancia: POST /api/core/modules/crm/enable. Organización: tienda /apps → Habilitar.
Perdí el NOVVUS_SERVICE_TOKEN — en Docker bootstrap lo escribió en el volumen tokens y el kernel guarda solo el hash. Si el volumen se borró, bootstrap se detiene con ya estaba instalado pero no hay token. Restaura tokens.tar.gz del último backup. Si no hay, reinstala el módulo: disable → uninstall (con {"confirm": true}) (borra sus datos: restaura su esquema desde un dump después) → docker compose up -d para que bootstrap lo instale y publique el token nuevo.
Perdí el NOVVUS_SERVICE_TOKEN — en desarrollo novvus deploy lo imprimió una sola vez y no lo guardaste. Con un JWT admin: disable, uninstall (con {"confirm": true}) y novvus deploy de nuevo. Es tu base de desarrollo: perder el esquema del módulo no debería doler; si duele, novvus seed.
Port 8077 is already in use al instalar, o la web no levanta Otro proceso escucha en el puerto de la web. El CLI nunca elige otro por su cuenta. NOVVUS_WEB_PORT=8088 novvus install (o cambia NOVVUS_WEB_PORT en el .env y up -d). En la demo, los puertos son 3000 y 8000; install.py avisa si están ocupados.
error during connect / Docker Desktop no responde El daemon de Docker no está corriendo. Linux: sudo systemctl start docker. Windows/macOS: abre Docker Desktop; install.py intenta abrirlo solo y espera hasta ~4 minutos. Si sigue sin responder, reinicia Docker Desktop (en Windows, revisa que WSL2 esté sano con wsl --status).
novvus update terminó con Update failed. Novvus Core was restored to 0.1.5. Algo falló tras el backup (casi siempre una migración de módulo, que hace que bootstrap termine con error) y el rollback funcionó. Estás en la versión anterior y sana. Lee /opt/novvus/logs/update-*.log: incluye los últimos 80 renglones de los servicios que no levantaron. Corrige y reintenta.
CRITICAL: automatic rollback failed (exit 2) Falló la actualización y el rollback. No reintentes. novvus status muestra la fase y el backup; restaura a mano con los pasos de Restaurar y sigue Actualización → si sale 2.
Un servicio queda unhealthy o starting eternamente El healthcheck real falla: el proceso arrancó pero no responde (kernel sin base, módulo sin handshake, web sin kernel). docker compose … logs --tail=200 <servicio>. Los healthchecks tienen timeout de 300 s en install y 420 s en update; si se agotan, el CLI imprime un diagnóstico por servicio.
Abrí la web recién instalada y no hay usuario para entrar Es el first-run: en producción bootstrap no crea usuarios ni organizaciones. Normal. "Crear cuenta" (será Owner) → "Crear organización" → tienda /apps → habilitar CRM y Projects. Las credenciales demo@novvus.dev solo existen en la demo local.
Habilité un módulo en la tienda y no aparece en el launcher La caché del meta dura 60 s (ETag + max-age), o el usuario no tiene el permiso read de ningún modelo del módulo. Espera un minuto o recarga; revisa los roles del usuario en Administración.
Subir un adjunto responde 413 Archivo mayor a NOVVUS_FILES_MAX_SIZE_BYTES (50 MB) o cuota de la organización agotada (NOVVUS_FILES_ORG_QUOTA_BYTES, 10 GB). Sube el límite en el .env y reinicia el kernel, o libera espacio borrando adjuntos (el GC recupera el disco tras la retención).
Disco lleno Backups acumulados en /opt/novvus/backups/, imágenes viejas o logs. docker system df, mueve backups fuera, docker image prune -a. Los logs de contenedor ya rotan solos (10 MB × 3).
Windows dev: error calling dlltool al compilar el kernel Falta binutils para la toolchain GNU de Rust. Instala WinLibs y antepón su mingw64\bin al PATH.
Windows dev: Psycopg cannot use the 'ProactorEventLoop' Ejecutaste uvicorn directo en vez de novvus run. novvus run fuerza el SelectorEventLoop; en tests, conftest.py hace lo mismo.

Revisión mensual sugerida

  • [ ] novvus status (o ps) devuelve todo sano.
  • [ ] El cron de backup dejó archivos ayer y se copiaron fuera del servidor.
  • [ ] Probaste restaurar un dump en otra máquina al menos una vez este trimestre.
  • [ ] event_deliveries no acumula filas failed.
  • [ ] Hay una versión nueva publicada (novvus update te lo dice sin aplicar nada si lo cancelas en la confirmación).
  • [ ] /opt/novvus/backups/ no está creciendo sin control.
