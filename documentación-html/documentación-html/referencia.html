Los dos CLIs llamados novvus

Nunca coexisten en la misma máquina: el del SDK vive en tu entorno de desarrollo y en los contenedores de módulos; el administrativo, en el servidor de producción.

CLI del SDK (Python, sdk/src/novvus_sdk/cli.py)CLI administrativo (Rust, cli/)

Estructura de un módulo

modules/{id}/
├── novvus.toml        # manifiesto: la única fuente de verdad
├── module.py          # module = NovvusModule(); @module.model / .on / .seed / .cron / .on_install…; app = module.create_app()
├── models.py          # NovvusModel + __resource__, __novvus_api__, __novvus_views__
├── business.py        # endpoints custom sobre module.router (opcional)
├── seed.py            # datos demo (opcional)
├── i18n/              # es-MX.json (fuente) y en-US.json — patrón gettext
├── migrations/        # NNNN_nombre.sql: las ejecuta el kernel, con RLS + columnas ext/custom
├── tests/             # conftest con BD efímera, app en modo offline, peticiones firmadas
├── pytest.ini         # asyncio_mode=auto; silencia la deprecación del event loop policy
├── requests.http      # ejemplos contra el gateway (CRM)
└── .env               # NOVVUS_SERVICE_TOKEN (fuera de git)

El caso sin modelos. modules/salesmx/ solo tiene novvus.toml, module.py, pytest.ini y tests/: sin models.py ni migrations/. Un módulo así no crea tablas de negocio en mod_salesmx, no aparece en el meta y aporta valor exclusivamente por [extensions] (o por eventos y endpoints custom).

Glosario

TérminoSignificado en NOVVUS
Tenant / organizaciónEl espacio aislado de un cliente. Todo dato de negocio lleva org_id; un usuario puede pertenecer a varias y su JWT está ligado a una a la vez.
RLSRow-Level Security de Postgres en las tablas mod_*, con FORCE y política fail-closed: sin app.org_id en la sesión no sale ninguna fila. core no usa RLS: el kernel filtra explícitamente.
Kernel / gatewayEl proceso Rust: identidad, RBAC, registro y ciclo de vida de módulos, bus, archivos, chatter, y el reverse proxy firmado.
MóduloAplicación de negocio en Python sobre novvus-sdk, con esquema mod_{id}, namespace /api/{id} y un manifiesto.
Manifiestonovvus.toml: lo que un módulo declara (permisos, eventos, dependencias, UI, config, cron, extensiones, presentación). Los modelos no van ahí: viajan en el meta.
HandshakeEl saludo runtime → kernel al arrancar: token de servicio + base_url + meta a cambio del secreto HMAC y el DSN del rol de módulo.
Token de servicioCredencial nvk_… de un módulo, emitida una vez en install y guardada solo como hash. Autentica handshake, eventos, config y llamadas módulo→módulo.
Token de bootstrapSecreto de plataforma (NOVVUS_BOOTSTRAP_TOKEN) que permite al aprovisionamiento inicial operar el ciclo de vida de instancia antes de que exista usuario alguno. Nunca es usuario ni tiene organización.
Headers internos / HMACx-novvus-user/org/perms/timestamp/signature: cómo el gateway le dice al módulo quién llama y con qué permisos, firmado con HMAC-SHA256 sobre usuario, org, permisos, timestamp, método y ruta (±60 s).
First-runEstado de una instalación de producción recién hecha: sin usuarios ni organizaciones. El flujo es Crear cuenta → Crear organización → App Store.
Ciclo de vida de instancia vs. por organizaciónInstancia: register → install → enable → disable → uninstall (destructivo). Por organización: install/enable/disable/uninstall en core.org_modules (no destructivo), con hooks.
Plan de dependenciasRespuesta de /plan: cierre transitivo de dependencias con enable_order, satisfied y problems; la tienda lo muestra antes de habilitar.
Estado degradadoUn módulo cuya dependencia no está habilitada sigue sirviendo y lo reporta en /health (degraded_dependencies). Nunca «roto».
MetaDocumento tipado de modelos, campos (con flags searchable/sortable/filterable/groupable), vistas y permisos que el SDK construye desde __novvus_views__ y persiste en core.modules.meta. Inválido = handshake rechazado.
Vista genéricaLista, formulario, kanban o calendario que la shell renderiza en /m/{módulo}/{modelo} a partir del meta, sin React del módulo. Sustituible con registerViewOverride.
DSL de filtrosJSON en ?filter= con grupos and/or y condiciones {field, op, value}; whitelist de 10 operadores, profundidad ≤ 5, ≤ 50 condiciones.
Cursor keysetPaginación estable por (columna_de_orden, id): pides la siguiente página con el next_cursor anterior, sin OFFSET y sin saltos aunque entren filas nuevas.
Extensión (ext)Campos y secciones de formulario que un módulo aporta a un modelo de otro. Los datos viven en la columna JSONB ext del base (ext.{extensor}.{campo}) y solo el base los escribe.
Campo personalizado (custom)Campo definido por el administrador de una organización desde /settings/custom-fields, sin DDL: definición en core.custom_fields, valor en la columna JSONB custom (custom.{nombre}).
Un solo escritorRegla de extensiones: solo el módulo dueño de la tabla escribe en ella, aunque el campo lo haya declarado otro.
Adjunto / blobcore.attachments es la referencia (registro padre, nombre, MIME); core.attachment_blobs el contenido deduplicado por (org, sha256) con refcount. El binario vive en el backend object_store.
ChatterHilo de colaboración de cualquier registro: comentarios, notas internas y mensajes system (tracking de campos), en core.messages. El módulo solo declara chatter = True.
FollowerUsuario suscrito a un registro (core.followers); recibe follower_message por cada mensaje ajeno. El autor de un mensaje se auto-suscribe.
Mención@[uuid] dentro del cuerpo de un mensaje; solo cuenta si el usuario es miembro de la org; genera una notificación mention.
ActividadTarea planificada sobre un registro (call/meeting/email/todo) con vencimiento y asignado; notificaciones activity_assigned y activity_due; se cierra con done o cancel.
NotificaciónFila en core.notifications dirigida a un usuario en una org; buzón con contador de no leídas; las leídas de más de 90 días se purgan.
SSEServer-Sent Events en /api/core/stream?token=: el gateway escucha pg_notify('novvus_notify') una vez por proceso y reparte en memoria; heartbeat cada 25 s; la shell hace polling como respaldo.
LauncherLa home / de la shell: grid de apps habilitadas y widgets de dashboard. Desde ahí cada módulo se abre a pantalla completa.
ModuleShellEl chrome de un módulo: barra con icono y acento del manifiesto, ui.nav, app-switcher, campana y tema. Envuelve tanto las páginas propias (/crm/*) como las genéricas (/m/crm/*).
App Store / tienda/apps: módulos disponibles en la instancia con su estado por organización y acciones de habilitación; alimentada por GET /modules y [presentation].
Catálogo (marketplace)core.module_catalog: paquetes disponibles para instalar, distinto de core.modules (registrados en la instancia). Se llena por POST /catalog.
Paquete firmadoJSON {format_version, manifest_toml, migrations, assets} envuelto con publisher, public_key y firma Ed25519 sobre sus bytes canónicos; sin código ejecutable.
Editor de confianzaClave pública listada en NOVVUS_TRUSTED_PUBLISHER_KEYS; sin ella no se publica ni se registra desde el catálogo (fail-closed).
Cron y hooksAutomatización orquestada por el kernel: jobs de [[cron]] ejecutados por org con FOR UPDATE SKIP LOCKED, y hooks on_install/enable/disable/uninstall best-effort, ambos entregados por el canal firmado.
UUIDv7Identificador ordenable por tiempo generado por la aplicación (kernel y SDK); todas las PKs.
Borrado suavedeleted_at: la fila desaparece de la API y del meta pero se conserva; se aplica a modelos de módulos, adjuntos, mensajes y campos custom.
IdempotenciaProcesar dos veces el mismo evento produce el mismo resultado. El SDK la garantiza con mod_{id}._processed_events (ON CONFLICT DO NOTHING) en la transacción del handler.
At-least-onceGarantía del bus: cada evento llega una o más veces a cada suscriptor (event_deliveries + NOTIFY + barrido cada 5 s), sin orden global; por eso los consumidores son idempotentes.
Modo offlineRuntime de módulo sin kernel (NOVVUS_DATABASE_URL + NOVVUS_INTERNAL_HMAC_SECRET): los eventos se registran con warning y no se publican; base de los tests.
Trinquete de coberturaUmbral de CI fijado bajo el baseline real que solo puede subir; bajarlo exige una entrada en DECISIONS.md.
Backup de updateCarpeta /opt/novvus/backups/<ts>-<de>-to-<a>/ con pg_dump -Fc verificado, volúmenes files y tokens, .env, compose y backup.json con SHA-256; nunca se borra sola.
