El SDK por dentro

Nivel avanzado

novvus-sdk son 19 archivos Python (~3 600 líneas) en sdk/src/novvus_sdk/. Esta página los recorre uno a uno, sigue el ciclo de arranque de un módulo, muestra cómo se genera la API, cómo se verifica cada petición, cómo se aísla el tenant y cómo se prueba todo sin kernel. Con fragmentos del código real y su ubicación aproximada.

Ciclo de arranque de create_app()

1
Lifespan. FastAPI(title, version, lifespan); el lifespan llama startup() al iniciar y shutdown() al parar (cierra el pool y el cliente HTTP).
2
startup() decide el modo (app.py:260-286). Con NOVVUS_SERVICE_TOKEN: crea KernelClient(NOVVUS_KERNEL_URL, token), construye el meta y hace el handshake; del resultado toma internal_hmac_secret y database_url (el DSN del rol novvus_module). Sin token pero con NOVVUS_DATABASE_URL + NOVVUS_INTERNAL_HMAC_SECRET: modo offline. Ninguno de los dos: RuntimeError con el mensaje exacto de qué falta.
3
Middleware _internal_auth (app.py:321-335). Toda petición salvo el healthcheck debe traer cabeceras firmadas: si el runtime aún no tiene secreto → 503 "module runtime not ready"; si la firma no valida → 401; si valida, set_context() antes de seguir y reset_context() en finally. Solo el kernel puede originar tráfico.
4
Auto-API primero, router custom después (app.py:337-350): un build_router() por modelo y luego self.router con prefijo /api/{id}. En FastAPI gana la primera ruta que coincide, así que para sustituir un endpoint generado hay que deshabilitarlo en __novvus_api__["disabled"] —exactamente lo que hace Lead del CRM con create para que la creación pase por el endpoint que emite crm.lead.created.
5
Rutas internas. GET {runtime.healthcheck} (sin firma; reporta degraded si una dependencia no está enabled), GET /_novvus/meta, POST /_novvus/events, POST /_novvus/cron, POST /_novvus/hooks/{hook} (app.py:352-408). El gateway no expone ninguna.
# app.py:375-387 — recepción de eventos con idempotencia en la misma transacción
@app.post("/_novvus/events")
async def receive_event(event: Event) -> dict[str, Any]:
    handlers = self.events.handlers_for(event.event_type)
    if not handlers:
        return {"status": "ignored"}
    async with self.db.tenant_session(event.org_id) as session:
        first_time = await mark_processed(session, event.id)   # INSERT … ON CONFLICT DO NOTHING
        if not first_time:
            return {"status": "duplicate"}
        for handler in handlers:
            await handler(event, session)
    return {"status": "processed"}
Handler y marca comparten transacción. Si el handler lanza, la transacción se revierte y la marca de procesado también: el kernel reintentará y el evento se procesará entonces. Es el "exactly-once efectivo" dentro del módulo sobre un transporte at-least-once.

Por qué autoapi.py no usa from __future__ import annotations. Los endpoints anotan su cuerpo con clases Pydantic creadas dinámicamente y guardadas en variables locales; FastAPI solo las ve si las anotaciones se evalúan de forma inmediata (comentario en autoapi.py:9-12).

security.py y context.py: cada petición, verificada

# security.py:29-33 — la cadena canónica que firma el gateway (novvus_common::internal en Rust)
def sign(secret, user, org, perms, timestamp, method, path) -> str:
    canonical = f"{user}\n{org}\n{perms}\n{timestamp}\n{method}\n{path}"
    return hmac.new(secret.encode(), canonical.encode(), hashlib.sha256).hexdigest()

# security.py:36-70 — verificación
def verify_request(request: Request, secret: str) -> RequestContext:
    ...                                                   # faltan cabeceras → 401 "missing internal headers"
    if abs(time.time() - timestamp) > MAX_SKEW_SECONDS:   # 60 s → 401 "stale internal signature"
        raise HTTPException(status_code=401, detail="stale internal signature")

    if not hmac.compare_digest(expected, signature):      # comparación en tiempo constante

db.py: la sesión de tenant

# db.py:31-52
class Database:
    def __init__(self, dsn: str, schema: str) -> None:
        self.engine = create_async_engine(
            to_async_dsn(dsn),                          # postgres:// → postgresql+psycopg://
            pool_size=5, max_overflow=5,
            connect_args={"options": f"-csearch_path={schema}"},   # nombres sin calificar → mod_{id}
        )
        self._sessions = async_sessionmaker(self.engine, expire_on_commit=False)

    @asynccontextmanager
    async def tenant_session(self, org_id: UUID) -> AsyncIterator[AsyncSession]:
        async with self._sessions() as session, session.begin():
            await session.execute(text("SELECT set_config('app.org_id', :org, true)"), {"org": str(org_id)})
            yield session                               # commit al salir sin excepción

El tercer argumento true de set_config equivale a SET LOCAL: la variable muere con la transacción y no contamina conexiones del pool. La política RLS que genera migrations.rls_block() usa current_setting('app.org_id')::uuid en USING y WITH CHECK, con FORCE ROW LEVEL SECURITY: sin tenant fijado la consulta falla en lugar de devolver todo (fail-closed). El DSN que entrega el handshake pertenece al rol novvus_module, sin BYPASSRLS y sin privilegios fuera de su esquema.

El SDK genera, el kernel ejecuta. Ningún módulo aplica sus propias migraciones: el kernel las corre en install/migrate, una transacción por archivo, con el rol de módulo y search_path fijado, y guarda el checksum. Cambiar un archivo ya aplicado aborta.

Modo offline: probar sin kernel

Es el modo de todos los arneses de prueba del repositorio (modules/crm/tests/conftest.py, modules/salesmx/tests/conftest.py, sdk/tests/). Requisitos: un Postgres accesible y dos variables de entorno.

1
Base efímera. El fixture de sesión crea novvus_crm_test_{hex}, se asegura de que exista el rol novvus_module con NOBYPASSRLS, crea mod_crm, y aplica migrations/*.sql en orden con SET LOCAL ROLE novvus_module y search_path = mod_crm, igual que haría el kernel. Al terminar, DROP DATABASE … WITH (FORCE).
2
Arranque offline. NOVVUS_DATABASE_URL = DSN con las credenciales del rol de módulo, NOVVUS_INTERNAL_HMAC_SECRET = un secreto cualquiera, y sin NOVVUS_SERVICE_TOKEN. load_module(root) importa module.py, create_app() + await module.startup(), y httpx.AsyncClient(transport=ASGITransport(app=app)) habla con la app en memoria.
3
Peticiones firmadas. No hay gateway, así que el test firma como lo haría el gateway: signed_headers() usa novvus_sdk.security.sign con el mismo secreto; OrgClient(client, org, perms) añade esas cabeceras a cada llamada y firma el path sin query string (path.split("?")[0]), porque verify_request firma request.url.path.
# modules/crm/tests/conftest.py:57-72 y 148-170 (recortado)
def signed_headers(method, path, org, perms, user=None):
    from novvus_sdk.security import sign
    timestamp = int(time.time())
    user_str = str(user) if user else ""
    return {
        "x-novvus-user": user_str, "x-novvus-org": str(org), "x-novvus-perms": perms,
        "x-novvus-timestamp": str(timestamp),
        "x-novvus-signature": sign(HMAC_SECRET, user_str, str(org), perms, timestamp, method, path),
    }

class OrgClient:
    def __init__(self, client: httpx.AsyncClient, org: UUID, perms: str): ...
    async def request(self, method, path, **kwargs):
        headers = signed_headers(method, path.split("?")[0], self.org, self.perms)
        return await self.client.request(method, path, headers=headers, **kwargs)

Ver más: qué NO hace el SDK (y por qué)
  • No abre conexiones a otros esquemas: el DSN es del rol restringido y search_path apunta a mod_{id}.
  • No emite JWT ni valida contraseñas: solo verifica HMAC de cabeceras que únicamente el gateway sabe firmar.
  • No aplica migraciones ni ejecuta DDL en runtime: genera SQL y lo entrega al kernel.
  • No hace push de invalidación de cachés (extensiones, custom fields, dependencias): TTLs cortos con degradación a copia anterior, decisión registrada en DECISIONS.md.
  • No reexporta el meta después del arranque: el documento viaja una vez en el handshake; un cambio de modelos exige reiniciar el módulo (y, si hay columnas nuevas, una migración).
