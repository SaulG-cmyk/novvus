Seguridad

Nivel avanzado

Cómo protege NOVVUS CORE credenciales, sesiones, la frontera kernel↔módulos, los archivos, la colaboración en tiempo real y la cadena de distribución. Cada afirmación está contrastada con el código del kernel (kernel/crates/); donde el contrato formal (documents/docs/SECURITY.md) y el código difieren, se indica y prevalece el código.

Recomendación OWASP para servicios interactivos. Detalles ya resueltos en service.rs::login: si el email no existe se ejecuta dummy_verify() con un hash estático para que el tiempo de respuesta no revele qué cuentas existen, y el error es siempre el mismo 401 "invalid credentials". La verificación es en tiempo constante (crate argon2). Registro: email normalizado a minúsculas, contraseña mínima de 8 caracteres.

Sesiones: JWT con rotación y detección de reuso

Dos tokens HS256 firmados con secretos distintos (NOVVUS_JWT_ACCESS_SECRET, NOVVUS_JWT_REFRESH_SECRET; mínimo 32 bytes aleatorios en producción):

TokenTTL (default)ClaimsNotas
Access900 s (15 min), NOVVUS_ACCESS_TOKEN_TTL_SECONDSsub, org_id?, roles, typ="access", jti, iat, exproles es informativo para la UI. Leeway de 5 s en exp.
Refresh1 209 600 s (14 días), NOVVUS_REFRESH_TOKEN_TTL_SECONDSsub, org_id?, roles=[], typ="refresh", jti, iat, expEn la base solo se guarda sha256(token) con id = jti.

El gateway rechaza cualquier token cuyo typ no corresponda al uso: un refresh jamás sirve como access ni al revés.

login ─────────────► refresh_1  (fila en core.refresh_tokens, hash SHA-256)
refresh_1 usado ───► par nuevo: refresh_2; refresh_1.revoked_at = now(), replaced_by = refresh_2
refresh_1 usado OTRA VEZ ─► reuso detectado ─► UPDATE … SET revoked_at = now()
                             WHERE user_id = ? AND revoked_at IS NULL   (todas las sesiones)
                             audit "auth.refresh_reuse" · 401
  • /auth/refresh acepta un org_id destino: cambiar de organización es pedir un par nuevo, siempre respaldado por una membresía.
  • /auth/logout revoca el refresh presentado aunque esté expirado (firma y typ se siguen verificando).
  • Un usuario sin organización recibe org_id = null y solo puede usar identidad (/auth/*, POST /orgs); todo endpoint tenant responde 403.
  • Los tokens viven en localStorage del navegador y cruzan a la web por el rewrite same-origin de Next; en producción el kernel no está expuesto.

Rate limit en /auth/*

rate_limit_middleware envuelve solo register, login, refresh y logout. Implementación: ventana fija de 60 s por IP en memoria; límite NOVVUS_AUTH_RATE_LIMIT_PER_MINUTE = 30 por defecto (novvus-common/src/config.rs:75); exceso → 429 rate_limited.

Nota de consistencia. SECURITY.md §8 habla de "p. ej. 10 req/min" y de un token bucket; el código implementa ventana fija con default 30. Esta documentación usa el valor del código. El contador se reinicia con el proceso y no es distribuido: es un freno básico contra fuerza bruta, no sustituye un WAF.

RBAC: permisos con comodines

Clave de permiso {module}.{resource}.{action}. Los roles (por organización) pueden otorgar comodines; los endpoints siempre exigen claves concretas. Implementación en novvus-rbac/src/lib.rs::grant_matches:

Otorgado al rol¿Satisface crm.contacts.read?
crm.contacts.readsí exacto
crm.contacts.*sí comodín de recurso
crm.*sí comodín de módulo
*sí el rol Owner
crm.con.*no el prefijo debe ir seguido de .: corta por segmento completo

La autorización nunca se decide con los roles del token: el gateway resuelve los permisos vigentes desde la caché (user, org) con TTL de 30 s e invalidación inmediata al editar roles/permisos (invalidate_org) o membresías (invalidate_user). Revocar surte efecto en la siguiente petición. Permisos del kernel: core.orgs.*, core.members.manage, core.roles.*, core.modules.*, core.audit.read, core.custom_fields.manage.

La frontera kernel ↔ módulos: headers firmados

El JWT jamás llega a un módulo. El proxy traduce la identidad a headers internos:

X-Novvus-User:      <uuid del usuario>   (vacío en llamadas de servicio, eventos, cron y hooks)
X-Novvus-Org:       <uuid de la org>
X-Novvus-Perms:     <claves efectivas, ordenadas, separadas por coma>
X-Novvus-Timestamp: <unix seconds>
X-Novvus-Signature: hex(HMAC-SHA256(secret, user + "\n" + org + "\n" + perms + "\n" + timestamp + "\n" + method + "\n" + path))
X-Novvus-Locale:    es-MX | en-US …        (informativo, FUERA de la firma)
  • secret = NOVVUS_INTERNAL_HMAC_SECRET, entregado a cada módulo en el handshake.
  • El SDK rechaza cualquier petición sin firma válida o con |now − timestamp| > 60 s (MAX_SKEW_SECONDS); la verificación es en tiempo constante.
  • Incluir method y path impide reutilizar una firma válida contra otro endpoint; el path firmado es el de la petición original (la query no entra en la firma).
  • El proxy reenvía solo content-type, accept y accept-language del cliente: cualquier X-Novvus-* entrante muere en el gateway. Cuerpo máximo 10 MiB.
  • X-Novvus-Locale solo elige idioma; el SDK jamás debe usarlo para autorizar.
  • Defensa en profundidad: aunque un atacante alcanzara la red interna, sin el secreto no puede forjar identidad ni permisos, y sin app.org_id válido RLS no entrega datos.

Token de servicio de módulo

Emitido una sola vez en install: nvk_ + 64 hex (32 bytes de OsRng). El kernel guarda solo sha256 en core.modules.service_token_hash; en Docker el claro vive en el volumen tokens. Lo usan el handshake, POST /api/core/events, GET /modules/status, la config de servicio y las llamadas módulo→módulo por el proxy.

  • En el proxy, un llamante con token de servicio debe indicar x-novvus-org; sus permisos son exactamente los service_permissions del manifiesto (validados al registrar: tres segmentos, nunca core.*), y el usuario viaja vacío.
  • Sobre archivos y chatter (OrgActor::Service) un módulo solo puede actuar sobre sus propios modelos; cualquier otro module_id → 403.
  • Revocación: disable del módulo corta el proxy y el bus; uninstall borra la fila (y con ella el hash). Reinstalar emite un token nuevo.

El módulo llamante es confiable a nivel instancia (lo instaló un administrador), pero sus permisos cross-módulo quedan declarados y acotados en su propio manifiesto; nunca hereda los permisos de un usuario.

Aislamiento por organización en core

Las tablas del kernel no usan RLS; la garantía la dan tres controles en cada handler:

ControlDónde
Filtro explícito WHERE org_id = $1 con la org del token (AuthUser::org()) o del header de servicio.Todos los endpoints tenant de core (org_modules, config, files, custom-fields, chatter, notifications).
El {org_id} de la ruta debe coincidir con auth.org(); si no, 403.ensure_same_org en routes/modules.rs (/orgs/{org}/modules/{id}/*) y comprobación inline en routes/orgs.rs (/orgs/{org}/members).
Un recurso de otra organización responde 404, nunca 403: no se revela existencia.Adjuntos (fetch_owned), mensajes, actividades, campos custom.

Los tests de integración tests/org_modules.rs, module_config.rs, files_flow.rs y chatter_flow.rs verifican que una org no ve ni afecta el estado de otra.

Configuración por organización y valores secretos

  • Cada campo de [[config]] puede declarar permission; si no, el gate es core.modules.manage. GET …/config solo devuelve los campos que el usuario puede leer (has_perm campo a campo) y PUT exige el permiso de cada clave escrita.
  • secret = true enmascara el valor en las respuestas de la API; sigue siendo escribible. Úsalo para claves de APIs externas que el módulo lee con su token de servicio (GET /api/core/config + x-novvus-org).
  • Los valores se validan contra el tipo declarado y las opciones de select antes de persistirse en core.org_module_config.

Token de bootstrap de plataforma

NOVVUS_BOOTSTRAP_TOKEN (32 bytes aleatorios, generado por novvus install) permite al servicio one-shot bootstrap registrar/instalar/migrar/habilitar módulos a nivel instancia antes de que exista usuario u organización (first-run). Límites verificados en extract.rs::PlatformActor y tests/platform_bootstrap.rs:

  • Solo lo aceptan los seis endpoints de ciclo de instancia: POST /api/core/modules y /modules/{id}/{install,migrate,enable,disable,uninstall}. AuthUser, OrgActor y todo endpoint tenant lo rechazan con 401.
  • No es un usuario ni pertenece a una org: en auditoría actor_id = None.
  • Fail-closed: sin valor configurado, presentar el header responde "platform bootstrap is disabled".
  • Comparación en tiempo constante: se comparan los SHA-256 de ambos valores con OR acumulado de XOR, sin cortocircuito.
  • Nunca se loguea ni se expone al frontend; los usuarios con core.modules.manage siguen pudiendo usar los mismos endpoints (novvus deploy).

Tiempo real: SSE

GET /api/core/stream?token=<access>. EventSource no permite headers, así que el access token viaja por query; es el mismo token de corta vida, no un secreto nuevo, y se valida exactamente igual que el Bearer (typ=access, org activa obligatoria). Cada conexión filtra en memoria por org_id y user_id: un usuario nunca recibe eventos de otro. Un canal LISTEN novvus_notify por proceso; heartbeat cada 25 s.

Query strings y logs. Un token en la URL puede terminar en logs de proxies intermedios. En producción el kernel no está expuesto y el rewrite de Next es same-origin; aun así, configura el proxy HTTPS para no registrar la query de /api/core/stream.

Chatter

  • Leer y comentar exige el permiso read del modelo padre (resuelto vía meta, como en archivos); un módulo con token de servicio solo publica mensajes system sobre sus modelos.
  • Cuerpo de 1 a 10 000 caracteres (MAX_BODY_CHARS). Se almacena como texto; hoy la shell lo renderiza como texto plano seguro (el render markdown con sanitizado por allowlist está en BACKLOG.md). Jamás HTML crudo.
  • Menciones @[user_id]: el kernel valida cada id contra core.memberships de la org y descarta las ajenas; una notificación por usuario, con deduplicación.
  • Edición y borrado solo por el autor; edición dentro de NOVVUS_CHATTER_EDIT_WINDOW_MINUTES (15 por defecto).
  • El fan-out es síncrono en la transacción del mensaje y nunca pasa por el bus de módulos.

Paquetes firmados y allowlist fail-closed

Un paquete es {format_version, manifest_toml, migrations, assets}; sus bytes canónicos (migraciones y assets ordenados) se firman con Ed25519 y se hashean con SHA-256 (package_hash). SignedPackage::verify:

  1. La clave pública (base64, 32 bytes) debe estar en NOVVUS_TRUSTED_PUBLISHER_KEYS; si no, 403 "not signed by a trusted publisher key". Lista vacía = nadie puede publicar.
  2. La firma (base64, 64 bytes) debe validar sobre los bytes canónicos; si no, 403.

Se verifica al publicar (POST /api/core/catalog, core.modules.manage) y de nuevo al registrar desde el catálogo. GET /api/core/catalog exige core.modules.read y no expone el blob package.

Integridad de la distribución

  • install.sh y novvus update descargan latest → <v>/manifest.json → binario, y exigen que el SHA-256 coincida antes de ejecutar o instalar nada; si no coincide, se borra y aborta.
  • Las carpetas versionadas de downloads.novvus.dev son inmutables (put-object archivo por archivo, nunca sync --delete); latest se publica al final y solo si las imágenes GHCR existen.
  • Los secretos de producción los genera el CLI en /opt/novvus/.env con permisos 600; el binario del CLI no contiene credenciales.
  • Pendiente: firma criptográfica de releases (minisign/Ed25519) verificada por install.sh y novvus update. Hoy la integridad depende de un manifest servido por el mismo origen que los binarios.

CORS y errores

  • CORS solo se activa si NOVVUS_CORS_ORIGINS no está vacío: orígenes explícitos, métodos y headers Any. En producción no hace falta: el navegador habla con la web y esta reescribe /api/* al kernel (same-origin).
  • Todos los errores de auth devuelven mensajes genéricos; los errores internos y de base se loguean y responden "internal error" sin detalle.
  • Logs: telemetry::init configura tracing_subscriber con filtro novvus=info,info (o RUST_LOG) y salida compacta; TraceLayer registra método, ruta y estado, no cabeceras. SECURITY.md §9 afirma que el kernel redacta Authorization y headers internos; en el código no hay una capa de redacción explícita, así que no confíes en ella: no actives logging de cabeceras en el proxy HTTPS delante de la web.

Checklist para producción

  • ☐ NOVVUS_JWT_ACCESS_SECRET, NOVVUS_JWT_REFRESH_SECRET, NOVVUS_INTERNAL_HMAC_SECRET y NOVVUS_BOOTSTRAP_TOKEN generados con CSPRNG (32+ bytes), distintos por entorno, fuera del repositorio (novvus install lo hace).
  • ☐ NOVVUS_MODULE_DB_PASSWORD distinta del default; procesos de plataforma nunca como superusuario; novvus_module sin BYPASSRLS; TLS a Postgres fuera de localhost.
  • ☐ HTTPS terminado delante de la web; HSTS; no registrar la query de /api/core/stream.
  • ☐ Solo la web expuesta en el host (NOVVUS_WEB_PORT); kernel y Postgres en la red interna de Docker.
  • ☐ NOVVUS_TRUSTED_PUBLISHER_KEYS vacío salvo que uses el catálogo.
  • ☐ Backend de archivos con cuotas acordes; volumen files respaldado; volumen tokens nunca borrado.
  • ☐ Revisar core.audit_log (login, auth.refresh_reuse, cambios RBAC, ciclo de vida) y las deliveries failed.
  • ☐ Tras el first-run, tener presente que el registro público sigue abierto (ver pendientes).

Reglas para autores de módulos

  • No implementes login, tokens ni contraseñas; confía solo en los headers firmados que verifica el SDK.
  • Exige la clave concreta de permiso en cada endpoint custom; no compares contra comodines ni contra roles.
  • Nunca leas org_id del body o la query: el SDK lo ignora y RLS lo haría fallar.
  • No uses x-novvus-locale para decidir nada más que el idioma de la respuesta.
  • Trata los payloads de eventos y los valores ext/custom como entrada no confiable: valida con Pydantic.
  • Declara en service_permissions solo lo que de verdad llamas; jamás core.*.
  • Guarda el token de servicio como secreto de despliegue (volumen tokens en Docker); si se filtra, deshabilita y reinstala el módulo para rotarlo.
