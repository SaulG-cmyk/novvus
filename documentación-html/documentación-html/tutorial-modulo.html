Tutorial: tu primer módulo

Nivel medio

De cero a un módulo Inventario funcionando dentro de NOVVUS CORE: dos modelos con relación, interfaz completa sin escribir React, API automática, un endpoint de negocio que emite eventos, un consumidor de eventos del CRM, cron, seed, tests e i18n. Todo el código es real y coherente con el SDK 0.1.6; puedes copiarlo tal cual.

Qué vas a construir

Un módulo inventario con un almacén (Warehouse) y productos (Product) que apuntan a un almacén. Cuando el CRM gane una oportunidad, Inventario creará un producto "kit" para ese cliente. Un endpoint POST /products/{id}/restock aumentará existencias y emitirá inventario.product.restocked. Un cron horario avisará de productos agotados. Al terminar tendrás:

modules/inventario/
├── novvus.toml            contrato: permisos, eventos, puerto, config, cron
├── module.py              entrypoint: NovvusModule + registro de modelos + app
├── models.py              Warehouse, Product, ALL_MODELS
├── business.py            endpoints custom (restock, reporte de bajo stock)
├── seed.py                datos demo por organización
├── i18n/en-US.json        traducciones (es-MX es el idioma fuente)
├── migrations/0001_init.sql
└── tests/
    ├── conftest.py        arnés: BD efímera + módulo en modo offline
    └── test_products.py
Un módulo no es una app pegada al sistema. El kernel es dueño de identidad, permisos, ciclo de vida, eventos y ruteo; el módulo declara y el SDK genera. Si sientes que necesitas tocar tablas ajenas, login o la shell de Next.js, falta un evento, una API pública o una extensión (ver Extensibilidad). Si aún no leíste Conceptos, hazlo antes: aquí los damos por sabidos.
1

Requisitos y entorno de desarrollo

Usa el modo desarrollador de Instalación: Postgres en Docker con puerto expuesto, kernel corriendo en tu máquina y el SDK instalado en un venv. Lo necesitas así porque makemigration incremental y seed se conectan a Postgres por localhost:5432, y porque el kernel debe poder alcanzar tu módulo en 127.0.0.1:8130.

# Desde la raíz del repo, una sola vez
cp .env.example .env
make up                                   # Postgres en :5432 (docker-compose.yml raíz)
pip install -e sdk                        # Python >= 3.12; instala el comando `novvus` del SDK

# En una terminal aparte, el kernel en :8000
cd kernel && cargo run -p novvus-gateway

# En otra, la web en :3000 (para ver la UI generada al final)
cd apps/web && npm install && npm run dev

En Windows, start.bat levanta todo eso en ventanas separadas. Verifica que el kernel responde: curl localhost:8000/health debe devolver "version": "0.1.6".

¿Prefieres la demo Docker (python install.py)? Funciona para deploy y para la UI, pero el kernel vive dentro de Docker: al correr tu módulo exporta NOVVUS_MODULE_BASE_URL=http://host.docker.internal:8130 para que el kernel lo encuentre, y ten en cuenta que ese compose no expone Postgres al host (sin makemigration incremental ni seed desde tu máquina).
2

Scaffolding: novvus new-module

cd modules
novvus new-module inventario
# Módulo 'inventario' creado en .../modules/inventario
# Migración inicial: .../modules/inventario/migrations/0001_init.sql
cd inventario

El id debe cumplir [a-z][a-z0-9_]* y no ser core, api, internal ni novvus. El comando genera cuatro archivos: un novvus.toml mínimo, un module.py con un modelo de ejemplo Item, tests/test_smoke.py y migrations/0001_init.sql generado a partir de ese Item.

Como vamos a reemplazar el modelo de ejemplo por los nuestros, borra ahora migrations/0001_init.sql: lo regeneraremos en el paso 6 con los modelos reales. Es seguro porque aún no se ha aplicado en ningún kernel (una migración aplicada nunca se edita ni se borra).

3

Es la única fuente de verdad sobre lo que tu módulo hace; el kernel lo valida al registrarlo y rechaza cualquier cosa fuera de tu namespace. Sustituye el generado por este:

4

Los modelos: models.py

Todo modelo hereda de NovvusModel, que aporta las columnas de sistema (id UUIDv7, org_id, ext, custom, created_at, updated_at, deleted_at). Tú solo escribes las de negocio. El atributo __novvus_views__ es lo que convierte el modelo en pantallas: etiquetas es-MX, columnas de la lista, layout del formulario, kanban, calendario, y los flags de adjuntos, chatter y tracking.

"""Modelos de Inventario. Las columnas de sistema vienen del SDK."""

from datetime import datetime
from decimal import Decimal
from enum import StrEnum
from uuid import UUID

from sqlalchemy import Enum as SAEnum
from sqlalchemy import ForeignKey, Numeric, String, UniqueConstraint
from sqlalchemy.dialects.postgresql import UUID as PgUUID
from sqlalchemy.orm import Mapped, mapped_column

from novvus_sdk import NovvusModel


# Miembros en minúsculas: SQLAlchemy persiste el NOMBRE del miembro y así coincide con la API.
class ProductCategory(StrEnum):
    general = "general"
    raw_material = "raw_material"
    finished = "finished"


def _enum(enum_cls: type[StrEnum]) -> SAEnum:
    # native_enum=False: VARCHAR con CHECK, sin tipos ENUM de Postgres que complican migraciones.
    return SAEnum(enum_cls, native_enum=False, length=20)


class Warehouse(NovvusModel):
    __resource__ = "warehouses"            # segmento de URL y nombre del modelo en el meta

    name: Mapped[str] = mapped_column(String(120))
    city: Mapped[str] = mapped_column(String(120), default="")
    is_active: Mapped[bool] = mapped_column(default=True)

    __novvus_views__ = {
        "label": "Almacenes",
        "display": "name",
        "labels": {"name": "Nombre", "city": "Ciudad", "is_active": "Activo"},
        "list": {"columns": ["name", "city", "is_active"], "default_order": "name"},
        "form": {"layout": [["name", "city"], ["is_active"]]},
    }


class Product(NovvusModel):
    __resource__ = "products"
    __table_args__ = (UniqueConstraint("org_id", "sku"),)   # un SKU por organización

    name: Mapped[str] = mapped_column(String(200))
    sku: Mapped[str] = mapped_column(String(40))
    category: Mapped[ProductCategory] = mapped_column(
        _enum(ProductCategory), default=ProductCategory.general
    )
    stock: Mapped[int] = mapped_column(default=0)
    min_stock: Mapped[int] = mapped_column(default=5)
    price: Mapped[Decimal] = mapped_column(Numeric(12, 2), default=Decimal("0"))
    # FK dentro del propio esquema: el nombre de tabla es el snake_case de la clase.
    warehouse_id: Mapped[UUID | None] = mapped_column(
        PgUUID(as_uuid=True), ForeignKey("warehouse.id", ondelete="SET NULL"), nullable=True
    )
    restocked_at: Mapped[datetime | None] = mapped_column(nullable=True)

    __novvus_api__ = {"search": ["name", "sku"]}   # columnas que responden a ?q=

    __novvus_views__ = {
        "label": "Productos",
        "display": "name",               # campo representativo en títulos y relaciones
        "attachments": True,             # panel de adjuntos en el formulario
        "chatter": True,                 # hilo de comentarios, notas y seguidores
        "track": ["stock", "price", "warehouse_id"],   # cambios → mensaje system en el chatter
        "labels": {
            "name": "Nombre", "sku": "SKU", "category": "Categoría",
            "stock": "Existencias", "min_stock": "Mínimo", "price": "Precio",
            "warehouse_id": "Almacén", "restocked_at": "Último reabasto",
        },
        "list": {
            "columns": ["name", "sku", "category", "stock", "price", "warehouse_id"],
            "default_order": "name",
        },
        "form": {
            "layout": [["name", "sku"], ["category", "warehouse_id"],
                       ["stock", "min_stock", "price"], ["restocked_at"]],
        },
        "kanban": {"group_by": "category", "card": ["name", "stock"]},
        "calendar": {"date_field": "restocked_at", "title": "name"},
    }


# El orden importa: las tablas referenciadas van primero (la migración 0001 crea en este orden).
ALL_MODELS: list[type[NovvusModel]] = [Warehouse, Product]
Clave de __novvus_views__Para qué
label, labelsNombre del modelo y de cada campo, en es-MX (la cadena es la clave de traducción).
displayCampo representativo: título del registro y texto en relaciones/autocomplete.
list, formColumnas de la lista y filas del formulario (1-3 campos por fila). Si los omites, el SDK deriva una lista y un form básicos: todo modelo es navegable.
kanbangroup_by debe ser un campo agrupable (string, boolean, date o relación). Arrastrar una tarjeta hace PATCH de ese campo.
calendardate_field debe ser date/datetime.
attachments, chatter, trackActivan el panel de adjuntos, el hilo de colaboración y los mensajes automáticos de cambio (ver Colaboración).

La validación es fail-fast: un campo que no existe en labels, un group_by no agrupable o una clave desconocida hacen que el módulo no arranque, con el mensaje exacto del error. Los detalles del meta están en Vistas genéricas y metadatos.

5

El entrypoint: module.py

El CLI del SDK exige que module.py viva junto a novvus.toml y defina module = NovvusModule(). Aquí registramos modelos, colgamos los endpoints de negocio, el consumidor de eventos, el cron y el seed, y creamos la app FastAPI:

"""Inventario — módulo NOVVUS. Construido exclusivamente con novvus-sdk."""

import logging
from pathlib import Path
from uuid import UUID

import business
import seed as seed_module
from models import ALL_MODELS, Product
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from novvus_sdk import NovvusModule
from novvus_sdk.events import Event

logger = logging.getLogger("novvus.inventario")

module = NovvusModule(Path(__file__).with_name("novvus.toml"))

for model in ALL_MODELS:
    module.model(model)          # tabla + RLS en migraciones, CRUD en la API, entrada en el meta

business.register(module)        # endpoints custom (paso 12)
module.seed(seed_module.seed)    # datos demo (paso 15)


# --- Consumidor de eventos (paso 13): el CRM ganó una oportunidad → producto "kit" -----------
@module.on("crm.opportunity.won")
async def create_kit_for_won_opportunity(event: Event, session: AsyncSession) -> None:
    opportunity_id = event.payload.get("opportunity_id")
    if not opportunity_id:
        return
    sku = f"KIT-{opportunity_id[:8].upper()}"

    # El SDK ya descartó duplicados por event.id; esto es cinturón y tirantes de negocio.
    existing = await session.scalar(select(Product).where(Product.sku == sku))
    if existing is not None:
        return

    # Dato de otro módulo: SOLO por su API pública, vía gateway (paso 14). Degradar, nunca romper.
    contact_name = ""
    contact_id = event.payload.get("contact_id")
    if contact_id and module.kernel is not None:
        try:
            contact = await module.call("GET", f"/api/crm/contacts/{contact_id}", org_id=event.org_id)
            contact_name = str(contact.get("name", ""))
        except Exception as error:
            logger.warning("CRM no disponible al resolver el contacto %s: %s", contact_id, error)

    session.add(
        Product(
            org_id=event.org_id,
            name=(f"Kit de bienvenida — {contact_name}" if contact_name else "Kit de bienvenida"),
            sku=sku,
            stock=1,
        )
    )
    await session.flush()


# --- Cron (declarado en [[cron]]): corre dentro del tenant de cada organización habilitada ---
@module.cron("inventario.check_out_of_stock")
async def check_out_of_stock(session: AsyncSession) -> None:
    rows = (
        await session.scalars(
            select(Product).where(Product.stock <= 0, Product.deleted_at.is_(None))
        )
    ).all()
    for product in rows:
        await module.emit(
            "inventario.product.out_of_stock",
            {"product_id": str(product.id), "sku": product.sku},
        )


# --- Hook por organización (best-effort): un almacén inicial al instalar ---------------------
@module.on_install
async def create_default_warehouse(session: AsyncSession) -> None:
    from models import Warehouse
    from novvus_sdk import current_context

    session.add(Warehouse(org_id=current_context().org_id, name="Almacén principal"))
    await session.flush()


app = module.create_app()

Genera la migración: novvus makemigration -m init

Antes de esto, crea business.py y seed.py aunque sea vacíos (con def register(module): pass y async def seed(session, org_id): pass), porque module.py los importa y el CLI carga module.py para leer los modelos.

novvus makemigration -m init
# Migración generada: .../modules/inventario/migrations/0001_init.sql

La primera migración no necesita base de datos: se genera del metadata de tus modelos. Ábrela. Verás, por cada tabla, el CREATE TABLE con tus columnas más las de sistema, el índice por org_id y el bloque de aislamiento por tenant:

CREATE TABLE product (
    name VARCHAR(200) NOT NULL,
    sku VARCHAR(40) NOT NULL,
    category VARCHAR(20) NOT NULL,
    stock INTEGER NOT NULL,
    min_stock INTEGER NOT NULL,
    price NUMERIC(12, 2) NOT NULL,
    warehouse_id UUID,
    restocked_at TIMESTAMP WITHOUT TIME ZONE,
    id UUID NOT NULL,
    org_id UUID NOT NULL,
    ext JSONB DEFAULT '{}'::jsonb NOT NULL,       -- datos que otros módulos te extienden
    custom JSONB DEFAULT '{}'::jsonb NOT NULL,    -- campos personalizados por organización
    created_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT now() NOT NULL,
    deleted_at TIMESTAMP WITH TIME ZONE,
    PRIMARY KEY (id),
    UNIQUE (org_id, sku),
    FOREIGN KEY(warehouse_id) REFERENCES warehouse (id) ON DELETE SET NULL
);

CREATE INDEX ix_product_org_id ON product (org_id);

ALTER TABLE product ENABLE ROW LEVEL SECURITY;
ALTER TABLE product FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON product
    USING (org_id = current_setting('app.org_id')::uuid)
    WITH CHECK (org_id = current_setting('app.org_id')::uuid);

-- idempotent event consumption (documents/docs/EVENTS.md §4)
CREATE TABLE IF NOT EXISTS _processed_events (
    event_id uuid PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);
¿Qué pasó por dentro? RLS y el rol del módulo

El SQL no lleva nombre de esquema: el kernel lo ejecuta con search_path = mod_inventario y con el rol novvus_module, que solo tiene privilegios sobre esquemas mod_* y no tiene BYPASSRLS. Cada tabla queda con FORCE ROW LEVEL SECURITY y una política que compara org_id con current_setting('app.org_id'). El SDK abre cada sesión con SET LOCAL app.org_id = '<org del request>', así que una consulta sin tenant no devuelve "todo": falla (fail-closed). Por eso no escribes WHERE org_id = … en ninguna parte. La tabla _processed_events es la memoria de idempotencia del paso 13.

Las migraciones posteriores se generan por diff contra tu base de desarrollo (NOVVUS_DATABASE_URL=… novvus makemigration -m add_campo) y se numeran solas; lo verás en Actualización → actualizar un módulo.

7

Obtén un JWT de administrador

Registrar e instalar módulos exige el permiso core.modules.manage en la organización activa (el Owner de una organización tiene *). En el entorno de desarrollo no hay usuario demo: créalo, crea una organización y pide un token con esa organización activa. Necesitas jq:

K=http://localhost:8000

# 1) Cuenta (una vez). Si ya existe, el kernel responde error de duplicado y sigues al login.
curl -s -X POST $K/api/core/auth/register -H "Content-Type: application/json" \
  -d '{"email":"dev@ejemplo.test","password":"una-clave-larga-de-dev","display_name":"Dev"}'

# 2) Login → access + refresh
TOKENS=$(curl -s -X POST $K/api/core/auth/login -H "Content-Type: application/json" \
  -d '{"email":"dev@ejemplo.test","password":"una-clave-larga-de-dev"}' | jq -c .tokens)
ACCESS=$(echo $TOKENS | jq -r .access_token)

# 3) Organización (una vez); el creador queda como Owner
curl -s -X POST $K/api/core/orgs -H "Authorization: Bearer $ACCESS" -H "Content-Type: application/json" \
  -d '{"name":"Taller Dev","slug":"taller-dev"}'
ORG=$(curl -s $K/api/core/orgs -H "Authorization: Bearer $ACCESS" | jq -r '.[0].id')

# 4) Refresh con org_id: el JWT resultante lleva la organización activa
JWT=$(curl -s -X POST $K/api/core/auth/refresh -H "Content-Type: application/json" \
  -d "{\"refresh_token\":$(echo $TOKENS | jq .refresh_token),\"org_id\":\"$ORG\"}" | jq -r .tokens.access_token)
echo $JWT | cut -c1-20

Es exactamente la secuencia que ejecuta scripts/bootstrap.py en modo demo. En la demo Docker puedes saltarte 1 y 3 usando demo@novvus.dev / demo-password-123. El access token dura 15 minutos: si más adelante recibes 401, repite el login.

Despliega: novvus deploy

cd modules/inventario
novvus deploy --kernel http://127.0.0.1:8000 --token $JWT
# Registrado: inventario
# Instalado. Migraciones aplicadas: ['0001_init']
# Habilitado.
#
# Token de servicio del módulo (guárdalo, se muestra UNA sola vez):
#   NOVVUS_SERVICE_TOKEN=nvk_...

Tres transiciones en un comando: register (valida el manifiesto y guarda el SQL de las migraciones), install (crea mod_inventario, aplica 0001_init en su propia transacción, registra tus cinco permisos en core.permissions, siembra el cron en core.cron_jobs y emite el token de servicio) y enable (verifica que crm está ENABLED; si no, falla aquí).

Guarda el token ahora. El kernel almacena solo su hash; no se puede volver a mostrar. Si lo pierdes tendrás que deshabilitar, desinstalar (destruye mod_inventario) y desplegar de nuevo. Lo cómodo en dev es un modules/inventario/.env (ignorado por Git) con NOVVUS_SERVICE_TOKEN=nvk_..., que start.bat ya sabe leer.

Errores típicos de register: permiso o evento fuera de inventario.*, id reservado, service_permissions con core.*, o una path de [ui] fuera de /inventario. El mensaje del kernel dice cuál.

9

Arranca el runtime: novvus run --port 8130

NOVVUS_SERVICE_TOKEN=nvk_... novvus run --port 8130
# INFO: Uvicorn running on http://127.0.0.1:8130

El puerto sale de --port, o de NOVVUS_MODULE_PORT, o de [runtime] port, o 8100. En Windows el CLI fuerza el SelectorEventLoop (psycopg async no funciona con el Proactor). Comprueba el módulo directamente: curl localhost:8130/health → {"status": "ok", "module": "inventario", "version": "0.1.0", "degraded_dependencies": {}}. Si el CRM estuviera deshabilitado verías "status": "degraded".

¿Qué pasó por dentro? Handshake, meta y HMAC

Al arrancar, module.startup() ve NOVVUS_SERVICE_TOKEN y llama a POST /api/core/modules/handshake con {module_id, version, base_url, meta}. El meta es el documento JSON que build_module_meta() construye desde tus modelos y sus __novvus_views__. El kernel valida ese documento con tipos estrictos (tamaño ≤ 512 KB, nombres ^[a-z][a-z0-9_]{0,63}$, permisos dentro del namespace del módulo) y lo persiste en core.modules.meta; un meta inválido rechaza el handshake, así que el módulo no arranca "a medias". En la respuesta recibe dos cosas que guarda en memoria: el secreto HMAC con el que el gateway firma los headers internos, y el DSN del rol novvus_module. Desde ese momento, todo request que no sea /health pasa por un middleware que exige x-novvus-user, x-novvus-org, x-novvus-perms, x-novvus-timestamp y x-novvus-signature (HMAC-SHA256 sobre usuario, org, permisos, timestamp, método y ruta; ventana de 60 s). Sin firma válida: 401. Por eso curl localhost:8130/api/inventario/products directo falla, y por eso solo el gateway puede originar tráfico. El endpoint /_novvus/meta te deja inspeccionar el meta en dev, pero la copia autoritativa es la que viajó en el handshake.

Habilítalo para la organización desde la tienda

deploy habilitó el módulo a nivel instancia. Cada organización decide además si lo usa. Tu usuario es Owner (*), así que ya tiene todos los permisos inventario.*. Para otros usuarios crearás roles en Administración con, por ejemplo, inventario.products.read e inventario.warehouses.read.

Un endpoint de negocio: business.py

El CRUD no cubre "reabastecer": es una operación con regla (cantidad positiva), efecto (actualiza restocked_at) y consecuencia (un evento). Va en el router del módulo, bajo el mismo namespace /api/inventario, con @requires y la sesión con tenant del SDK:

"""Reglas de negocio de Inventario: endpoints más allá del CRUD generado."""

from datetime import UTC, datetime
from typing import Annotated, Any
from uuid import UUID

from fastapi import Depends, HTTPException
from models import Product
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from novvus_sdk import NovvusModule, requires


class Restock(BaseModel):
    model_config = ConfigDict(extra="forbid")

    quantity: int = Field(gt=0)
    note: str = ""


def _serialize(product: Product) -> dict[str, Any]:
    return {
        "id": str(product.id), "sku": product.sku, "name": product.name,
        "stock": product.stock, "min_stock": product.min_stock,
        "restocked_at": product.restocked_at.isoformat() if product.restocked_at else None,
    }


def register(module: NovvusModule) -> None:
    router = module.router                                   # se monta con prefijo /api/inventario
    SessionDep = Annotated[AsyncSession, Depends(module.session_dependency())]

    @router.post("/products/{product_id}/restock")
    @requires("inventario.products.write")              # después del decorador de ruta, siempre
    async def restock(product_id: UUID, payload: Restock, session: SessionDep) -> dict[str, Any]:
        product = await session.scalar(
            select(Product).where(Product.id == product_id, Product.deleted_at.is_(None))
        )
        if product is None:
            raise HTTPException(status_code=404, detail="product not found")

        product.stock += payload.quantity
        product.restocked_at = datetime.now(tz=UTC)
        await session.flush()
        await session.refresh(product)

        # Hecho ya ocurrido, payload mínimo: quien lo necesite consulta nuestra API.
        await module.emit(
            "inventario.product.restocked",
            {"product_id": str(product.id), "sku": product.sku,
             "quantity": payload.quantity, "stock": product.stock},
        )
        return _serialize(product)

    @router.get("/reports/low-stock")
    @requires("inventario.reports.read")
    async def low_stock(session: SessionDep) -> dict[str, Any]:
        config = await module.config()                       # [[config]] de la org activa
        threshold = int(config["inventario.low_stock_threshold"])
        rows = (
            await session.scalars(
                select(Product)
                .where(Product.stock < threshold, Product.deleted_at.is_(None))
                .order_by(Product.stock)
            )
        ).all()
        return {"threshold": threshold, "items": [_serialize(p) for p in rows]}
curl -s -X POST $B/products/$P/restock -H "$A" -H "$J" -d '{"quantity": 24}'
curl -s $B/reports/low-stock -H "$A"

Reglas que no se negocian: todo endpoint custom lleva @requires con una clave concreta (los grants pueden ser comodines, los requisitos no); la sesión viene del SDK (ya trae tenant y transacción; no hagas commit, el SDK confirma al terminar el request); nunca aceptes org_id en el body. Reinicia novvus run para cargar el archivo nuevo.

Escucha un evento del CRM y llama a su API

Ya lo escribiste en module.py (paso 5). Pruébalo de verdad: en el CRM (habilitado en tu organización) mueve una oportunidad a la etapa "Ganado". El CRM emite crm.opportunity.won; el despachador del kernel crea una fila en core.event_deliveries por cada módulo habilitado que lo escucha y hace POST /_novvus/events firmado a tu runtime. Segundos después aparece "Kit de bienvenida — <contacto>" en tu lista de productos.

# Con la API: crea un lead, conviértelo y mueve la oportunidad a la etapa ganada (ver api.html)
curl -s -X POST $K/api/crm/opportunities/$OPP/move -H "$A" -H "$J" -d "{\"stage_id\":\"$WON_STAGE\"}"
¿Qué pasó por dentro? At-least-once e idempotencia

El bus garantiza at-least-once: si tu módulo estaba caído, la entrega queda pending y se reintenta con backoff (1 s, 4 s, 16 s… tope 5 min, 25 intentos). Si respondiste 2xx pero el kernel no lo vio (timeout), lo volverás a recibir. Por eso /_novvus/events abre una sesión con el tenant del evento y hace INSERT INTO _processed_events (event_id) … ON CONFLICT DO NOTHING en la misma transacción que tu handler: si la fila ya existía responde duplicate sin ejecutarte; si tu handler lanza, la marca tampoco se guarda y el kernel reintentará. Tu UNIQUE (org_id, sku) es la segunda línea de defensa. Y module.call("GET", "/api/crm/contacts/…") sale por el gateway autenticado con tu token de servicio, con exactamente los permisos de service_permissions y el org_id del evento: nunca lees mod_crm.contact.

async def seed(session: AsyncSession, org_id: UUID) -> None:
    north = Warehouse(org_id=org_id, name="Bodega Norte", city="Monterrey")
    south = Warehouse(org_id=org_id, name="Bodega Sur", city="Oaxaca")
    session.add_all([north, south])

            warehouse_id=(north.id if index % 2 == 0 else south.id),
        )
        for index, (name, sku, category, stock, price) in enumerate(PRODUCTS)
    )
    await session.flush()

Checklist de conformidad

  • [ ] novvus.toml válido: permisos, eventos emitidos, config y cron bajo inventario.*; nada de core.* en service_permissions.
  • [ ] register → install → enable sin pasos manuales (novvus deploy de una sola pasada).
  • [ ] Todas las tablas en mod_inventario con org_id, ext, custom y RLS (el generador lo hace; si escribes SQL a mano, no lo olvides).
  • [ ] Ningún SQL hacia core ni hacia otro mod_*; los datos ajenos llegan por module.call o por eventos.
  • [ ] Todo endpoint custom con @requires y sesión del SDK; org_id nunca viene del cliente.
  • [ ] Eventos emitidos son hechos (restocked), no comandos; consumidores idempotentes con constraint de respaldo.
  • [ ] Dependencias declaradas; el módulo degrada (no rompe) si el CRM no está.
  • [ ] Migraciones nuevas para cada cambio; jamás editas una aplicada.
  • [ ] Tests de permisos, RLS y reglas de negocio pasan contra Postgres real.
  • [ ] uninstall no deja tablas huérfanas (el kernel lo garantiza con DROP SCHEMA … CASCADE).
