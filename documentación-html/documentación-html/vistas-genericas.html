Vistas genéricas y metadatos

Nivel medio

Cómo un módulo obtiene lista, formulario, kanban, calendario, filtros visuales y exportación sin escribir una línea de React: declaras __novvus_views__ en el modelo, el SDK construye un documento de metadatos, el kernel lo valida y lo sirve filtrado por permisos, y la shell lo convierte en pantallas bajo /m/{módulo}/{modelo}.

Por qué existe este pipeline

En el tutorial anterior tu módulo ya tenía API REST automática. Lo que faltaba era la interfaz. En otras plataformas eso significa escribir vistas XML o componentes por cada modelo. En NOVVUS CORE la interfaz nace del propio modelo Python: el SDK sabe qué columnas tienes, de qué tipo son, cuáles son obligatorias y qué permisos las protegen. Con esa información —el meta— la shell puede renderizar una tabla, un formulario y un kanban correctos para cualquier módulo, incluso uno de terceros que la shell nunca ha visto.

Regla de oro. El genérico es el default, nunca una jaula. Si un modelo necesita una pantalla a medida, registras un override o creas una página bajo /{módulo}/… dentro del mismo chrome. Nada te obliga a usar el genérico, pero siempre lo tienes.

El pipeline de metadatos, paso a paso

     │                            │                                     │ /m/crm/contacts

1
Declaración. Cada clase registrada con @module.model puede llevar el atributo opcional __novvus_views__. Al registrar, validate_views() (sdk/src/novvus_sdk/meta.py:183) revisa la declaración y falla con ValueError si algo no cuadra: el módulo no arranca "a medias".
2
Construcción. En startup() el SDK llama build_module_meta(self.id, version, self.models) (app.py:275) y obtiene un JSON con meta_version, module, module_version y la lista models.
3
Handshake. KernelClient.handshake() (kernel.py:44) envía {module_id, base_url, meta} a POST /api/core/modules/handshake con el token de servicio. El meta viaja empujado: el kernel no lo consulta después. GET /_novvus/meta del runtime existe solo para depurar.
4
Validación en el kernel. kernel/crates/novvus-registry/src/meta.rs deserializa con deny_unknown_fields (una clave desconocida rechaza el handshake), exige meta_version = 1, tamaño serializado ≤ 512 × 1024 bytes, module igual al módulo que hace handshake, nombres de modelo y campo con ^[a-z][a-z0-9_]{0,63}$, permisos con prefijo {módulo}. (del módulo, no del modelo: stages del CRM vive bajo crm.pipelines.read) y tipos del catálogo cerrado. Si pasa, se guarda en la columna JSONB core.modules.meta. Un handshake sin meta conserva el documento anterior.
5
Exposición. GET /api/core/meta y GET /api/core/meta/{módulo} (novvus-gateway/src/routes/meta.rs) devuelven solo modelos de módulos habilitados en la org activa sobre los que el usuario tiene el permiso read; capabilities.create/update/delete se recortan según write. Aquí se fusionan además los campos de extensiones y los campos personalizados de la org. Respuesta con ETag y Cache-Control: private, max-age=60; con If-None-Match devuelve 304.
6
Render. apps/web/src/lib/meta/use-meta.ts cachea el índice con TanStack Query (staleTime: 60_000, alineado al max-age) y las rutas /m/{módulo}/{modelo} y /m/{módulo}/{modelo}/{id} montan los componentes genéricos dentro del ModuleShell del módulo dueño.

Qué deriva el SDK de cada columna

field_specs() (meta.py:110) recorre model.__table__.columns y produce un spec por campo. Conviene saber las reglas para no pelearte con los defaults:

PropiedadRegla
Columnas ocultasorg_id, deleted_at, ext y custom nunca salen en el meta (HIDDEN_COLUMNS). Las dos últimas llegan a la shell fusionadas por el kernel como ext.{extensor}.{campo} y custom.{campo}.
Solo lecturaid, created_at, updated_at.
typeMapeo desde SQLAlchemy (_meta_type): FK → relation; Enum → string + choices; Text → text; String → string; Boolean, DateTime, Date, Integer, Numeric → decimal, UUID → uuid, JSON → json.
relation"{módulo}.{resource}" del modelo destino, respetando su __resource__ (una FK a company.id se resuelve como crm.companies).
choicesPara Enum: [{value, label}] con label = value. Traduce los labels con el catálogo i18n del módulo si quieres texto distinto.
requiredNo nullable, sin default, sin server_default y no readonly.
searchableSi el modelo declara __novvus_api__["search"], exactamente esa lista. Si no: columnas string/text que no sean Enum ni de sistema.
sortable / filterableTodo salvo json.
groupableTipos string, boolean, date, relation, excepto id.
Modelos sin superficieUn modelo con list en __novvus_api__["disabled"] no entra al meta (tablas de unión como contact_tags).

__novvus_api__: el hermano mayor

Configura la auto-API y, por tanto, lo que el meta puede prometer:

class Stage(NovvusModel):
    __resource__ = "stages"
    __novvus_api__ = {
        "permissions": {"read": "crm.pipelines.read", "write": "crm.pipelines.manage"},
        "disabled": [],                 # list | create | get | update | delete
        "search": ["name"],             # columnas que responde ?q=
        "export_max_rows": 20000,       # default EXPORT_MAX_ROWS = 100 000
    }

Los permisos por defecto son {módulo}.{resource}.read y .write. El meta publica exactamente los que resulten, y el kernel filtra el modelo entero cuando el usuario no tiene el de lectura.

Los endpoints genéricos de la auto-API

Todos viven bajo /api/{módulo}/{resource}, exigen enforce(read_perm) y corren dentro de la sesión de tenant (RLS). Lista, agrupación y exportación comparten la misma función searched_and_filtered() (autoapi.py:203): es imposible exportar filas que la lista no muestre.

RutaParámetrosRespuesta
GET /{resource}limit (1–200, default 50) · cursor · order_by ([-]columna, default -id; solo columnas reales, 422 si no existe) · q (ILIKE sobre los campos searchable) · filter (DSL JSON) · filtros planos columna=valor por compatibilidad (coerción por tipo; 422 si el valor no cabe).{items, next_cursor}. El cursor es keyset: base64url de {o: {t, v}, id}; nunca hay page/offset.
GET /{resource}/group?by=by (campo groupable o custom.{nombre} con choices/boolean) · q · filter.{groups: [{value, label, count}]} ordenado por conteo descendente. Alimenta las columnas del kanban.
GET /{resource}/exportformat=csv|xlsx · q · filter · order_by.Descarga con Content-Disposition: attachment; filename="{resource}.{format}". Cabeceras = labels traducidos según x-novvus-locale; columnas de extensiones y custom al final. Si el conteo supera export_max_rows responde 422 pidiendo acotar el filtro. CSV se transmite fila a fila; XLSX usa openpyxl en modo write-only.

El DSL de filtros JSON (?filter=)

Sustituye a los domains de Odoo con JSON componible y validado (sdk/src/novvus_sdk/filters.py). Gramática:

Filter    := Group | Condition
Group     := {"and": [Filter, …]} | {"or": [Filter, …]}     (1..N hijos, una sola clave)
Condition := {"field": nombre, "op": operador, "value": json}
OperadorTipos admitidosSemántica
eq, netodos los filtrablesigualdad / desigualdad
intodos los filtrablespertenencia; value es un array no vacío de ≤ 100 elementos
is_nulltodosvalue booleano; es la única forma de preguntar por nulos (un null en otro operador → 422)
gt, gte, lt, lteinteger, decimal, date, datetimecomparación
betweenlos mismos comparablesvalue = [min, max], rango inclusivo
containsstring, textILIKE %v% con %, _ y \ escapados
ilikestring, textpatrón ILIKE literal del cliente

Límites y garantías: profundidad máxima 5 (MAX_DEPTH), 50 condiciones (MAX_CONDITIONS), solo campos filterable (las columnas ocultas ni siquiera están en los specs, así que org_id/deleted_at no se pueden nombrar), coerción por tipo del campo, traducción exclusiva a expresiones de columna de SQLAlchemy (jamás text()). Los campos ext.{extensor}.{campo} y custom.{campo} también se aceptan: se traducen a ext -> 'x' ->> 'y' con cast al tipo declarado. Todo rechazo es 422 con la ruta del nodo: {"detail": {"message": "…", "path": "and[1].or[0]"}}.

# Contactos con puesto que contiene "gerente" y sin empresa asignada
curl -G "http://localhost:8000/api/crm/contacts" \
  -H "Authorization: Bearer $ACCESS" \
  --data-urlencode 'filter={"and":[{"field":"job_title","op":"contains","value":"gerente"},{"field":"company_id","op":"is_null","value":true}]}' \
  --data-urlencode "order_by=name" --data-urlencode "limit=25"

# Oportunidades de este trimestre por importe, agrupadas por prioridad
curl -G "http://localhost:8000/api/crm/opportunities/group" \
  -H "Authorization: Bearer $ACCESS" \
  --data-urlencode "by=priority" \
  --data-urlencode 'filter={"field":"expected_close_date","op":"between","value":["2026-07-01","2026-09-30"]}'

# Exportar a XLSX el mismo filtro (misma consulta, mismo permiso)
curl -G "http://localhost:8000/api/crm/opportunities/export" \
  -H "Authorization: Bearer $ACCESS" -H "x-novvus-locale: en-US" \
  --data-urlencode "format=xlsx" \
  --data-urlencode 'filter={"field":"priority","op":"in","value":["high","medium"]}' -o oportunidades.xlsx

# Filtro sobre un campo de extensión (salesmx aporta rfc a crm.contacts)
curl -G "http://localhost:8000/api/crm/contacts" -H "Authorization: Bearer $ACCESS" \
  --data-urlencode 'filter={"field":"ext.salesmx.rfc","op":"ilike","value":"XAXX%"}'
En producción el kernel no está expuesto. Los ejemplos usan :8000 del entorno de desarrollo. Con una instalación real llama a http://<servidor>:8077/api/…: la web hace el rewrite same-origin hacia el kernel.

Los componentes de la shell

Viven en apps/web/src/components/generic/ y solo conocen el meta: ninguno importa nada de un módulo concreto.

ComponenteQué hace con el meta
GenericListView
list-view.tsx		Tabla con views.list.columns más las columnas ext/custom al final; buscador (q); FilterBuilder; orden al hacer clic en cabeceras sortable (no en ext/custom: order_by solo acepta columnas reales); paginación infinita por cursor de 25; botón Exportar (CSV/XLSX vía fetch con Bearer, porque un <a href> no puede llevar la cabecera); botón Nuevo si capabilities.create → /m/{módulo}/{modelo}/new.
GenericFormView
form-view.tsx		Filas de views.form.layout como grid de N columnas; secciones de extensores (ext_sections) justo debajo de la fila que contiene su after:{campo}, o al final si el slot no existe; sección "Información adicional" con los campos custom; validación cliente de required; el payload se reconstruye con nestExtValues() (ext.x.y → ext.x.y anidado). Con capabilities.attachments/chatter monta AttachmentPanel y ChatterPanel (solo al editar, no al crear). Eliminar pide confirmación y respeta capabilities.delete.
GenericKanban
kanban-view.tsx		Columnas de GET /group?by=kanban.group_by (primero los choices declarados, luego los valores encontrados, incluida una columna para nulos); cada columna lista con filter {eq|is_null} y limit 50; arrastrar hace PATCH {group_by: valor}.
GenericCalendar
calendar-view.tsx		Mes con lunes primero; consulta filter {between} sobre calendar.date_field con limit 200; 3 entradas por día y "+N"; la vista semanal está en BACKLOG.
FilterBuilder
filter-builder.tsx		Constructor visual: v1 construye un AND plano de condiciones sobre campos filterable no readonly; los operadores ofrecidos por tipo salen de opsForType() (lib/meta/types.ts).
FieldInput
field-input.tsx		Un input por tipo: switch para boolean, Select si hay choices, RelationPicker para relation (busca con q en el modelo destino y muestra su display), textarea para text, number/date/datetime-local para el resto. Mantiene los valores en la forma que espera la API.

Las dos rutas son app/(protected)/m/[moduleId]/[model]/page.tsx (lista con conmutador Lista / Kanban / Calendario según lo que declare el meta) y …/[model]/[id]/page.tsx (formulario; id = "new" crea). El layout.tsx intermedio envuelve todo en <ModuleShell moduleId={params.moduleId}>, así que una vista genérica se ve dentro del chrome del módulo dueño, con su icono, su nav y el app switcher.

Sustituir una vista: registerViewOverride

El registro vive en apps/web/src/lib/meta/overrides.tsx. La clave es "{módulo}.{modelo}.{vista}" con vista ∈ list | form | kanban | calendar; el componente recibe {moduleId, model, recordId?} (recordId solo para form). Las páginas genéricas llaman renderViewOverride() antes de montar el genérico y, si hay override, usan el tuyo.

// apps/web/src/app/(protected)/crm/overrides.tsx (archivo tuyo, importado por el layout del módulo)
"use client";
import { registerViewOverride, type GenericViewProps } from "@/lib/meta/overrides";
import { GenericListView } from "@/components/generic/list-view";

function OpportunitiesBoard({ moduleId, model }: GenericViewProps) {
  // Tu pantalla: puedes reutilizar piezas genéricas y añadir lo tuyo.
  return (
    <div className="space-y-4">
      <PipelineSummary moduleId={moduleId} />
      <GenericListView moduleId={moduleId} model={model} />
    </div>
  );
}

registerViewOverride("crm.opportunities.list", OpportunitiesBoard);
Los módulos no envían JavaScript. Un override es código de la shell (repositorio de la plataforma), no del paquete del módulo: el marketplace transporta solo manifiesto, migraciones y estáticos. En v0.1.6 no hay overrides registrados en el repositorio; el mecanismo existe para cuando lo necesites.

Páginas a medida bajo /{módulo}/…

Cuando un modelo necesita una experiencia propia completa (el pipeline del CRM, por ejemplo), la opción es una ruta bespoke en la shell. El patrón es el de app/(protected)/crm/layout.tsx:

"use client";
import { ModuleShell } from "@/components/module-shell";

export default function CrmLayout({ children }: { children: React.ReactNode }) {
  return <ModuleShell moduleId="crm">{children}</ModuleShell>;
}

Desde esas páginas puedes usar el cliente tipado records de lib/meta/api.ts (list/one/create/update/remove/group) y los mismos paneles (AttachmentPanel, ChatterPanel), que se exportan precisamente para vistas custom.

La regla de ui.nav

Toda path de [ui] debe vivir bajo /{id} (valid_ui_path en kernel/crates/novvus-registry/src/manifest.rs:309, espejo en sdk/src/novvus_sdk/manifest.py:315). Por tanto un item de nav no puede apuntar a /m/…: eso sería inyectar navegación en la shell. Cómo se resuelve en la práctica:

SituaciónQué hace la shell
El módulo declara [[ui.nav]]Pinta esos items en la barra superior del ModuleShell. Cuando el usuario está en /m/crm/contacts, el item /crm/contacts se marca activo (la shell quita el prefijo /m al comparar).
El módulo no declara nav (o el usuario no tiene permiso para ningún item)Deriva un item por modelo visible del meta apuntando a /m/{id}/{modelo} (module-shell.tsx:144-151). El botón "Abrir" del launcher usa resolveOpenRoute(): ui.entry si existe, si no la primera vista genérica.
Módulo sin páginas ni modelos (p. ej. salesmx)No hay a dónde abrir: el app switcher lo omite y la tienda lo muestra sin botón Abrir.
Ver más: qué NO hace el meta todavía

Permisos por campo (hoy la unidad es el modelo), filtros sobre columnas json, búsqueda libre ?q= sobre campos ext/custom, resolución del display de relaciones en la tabla (la lista muestra el UUID; el picker del formulario sí resuelve el nombre), vista semanal del calendario, grupos anidados en el constructor visual y selector de columnas. Todo está en documents/docs/BACKLOG.md. Regla del proyecto: detectado ≠ implementado.
